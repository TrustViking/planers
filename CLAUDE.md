# CLAUDE.md — planers (планер)

Инструкции для агента (Claude Code / Cowork / Codex), работающего в `D:\_projects\planers`.
Этот файл — единственный документ требований и правил работы: отдельного технического задания в репо нет (удалено 14-09-2026). Расхождение кода с этим файлом — доложить, не решать молча.

## Что это

Планер — локальная Windows-программа у владельца YouTube-канала, машина №2 в пайплайне broadcaster → **planer** → стример. Берёт пакет `*.bcast` от броадкастера, сверяет его с эфирами, уже запланированными на каналах владельца, создаёт недостающие эфиры (и исправляет те, у которых изменились название/описание), получает ключи потока, пишет их в `keystreams\keys.txt` и отправляет в Google-форму ключей, в конце — отчёт.

Площадки v1 — только YouTube. Facebook — этап 6. Rumble — нет.

Планер **не**: стримит и не трогает расписание (источник — Google Sheets броадкастера); не обходит Google-форму; не трогает эфиры, которые не соответствуют ни одному слоту (ручные/чужие); не хранит логины и пароли площадок; сам ничего не скачивает и в Telegram не ходит (пакет владельцу пересылает оператор руками).

| # | Машина | Кто | Делает | Проект |
|---|--------|-----|--------|--------|
| 1 | Броадкастер | оператор (Артур) | Sheets → yt-dlp → LLM → анонсы в Docs/Telegram → после всех анонсов пакет для планера в Telegram | `broadcaster` |
| 2 | Планер | владелец канала | пакет → сверка с YouTube → эфиры → ключи → `keys.txt` → форма → отчёт | `planers` |

## Сквозной сценарий

1. Оператор запускает броадкастер; после публикации всех дат он отправляет пакет документом в тот же Telegram-канал, куда ушли анонсы.
2. Оператор пересылает пакет владельцу. Владелец сохраняет файл в `bcast\` папки планера.
3. Владелец запускает `planer.bat`. Планер:
   1. читает `secrets\channels.json` и `secrets\planer.json`; проверяет каналы с токеном без браузера (`channels.list`, раздел «Сверка каналов при старте»): ник и название, сменённые на YouTube, выравнивает по id сам, токен, ведущий на чужой канал, удаляет; у каждого канала — статус (готов / нужен вход / отказ / сбой);
   2. читает **все** пакеты в `bcast\`, сливает слоты в одну карту по `slot_id`, выбрасывает прошедшие; пакетов нет — код 3, каналы не трогаются; читает формы ключей этих пакетов — один раз на форму;
   3. отбирает будущие слоты под языки своих каналов — объекты запланированных эфиров;
   4. фаза входов: каналы, у которых есть объекты и нужен вход, входят подряд, один за другим (браузер, проверка канала ник → id по паспорту → название, не тот канал — ещё один вход); после неё браузер не открывается;
   5. допуск: каждый объект получает объект своего канала и объект своей формы, строит ответы формы без ключа и адреса и сам решает, допущен ли он (канал подтверждён, форма прочиталась, для даты, языка и прочих полей в форме есть варианты); не допущенный объект на YouTube ничего не создаёт и не исправляет, в форму ничего не шлёт, но остаётся в отчёте, консоли и `keys.txt`, код выхода 1;
   6. каждому допущенному объекту подтягивает его запись из памяти планера `secrets\planer.sqlite3` (только результаты: что форма уже подтвердила); по каждому подтверждённому каналу с объектами запрашивает у YouTube запланированные эфиры и сверяет все параметры, которые планер диктует эфиру: нет эфира → создать; есть, но исправимое поле отличается → исправить; есть и совпадает → копия; неисправимое расхождение — в лог, консоль и отчёт; не допущенный объект только опознаёт свой эфир и берёт ключ;
   7. записывает допущенные объекты в память; по каждому объекту по очереди: действия (создать, привязать поток, исправить, настройки видео, факты) → запись результатов (эфир, поток, ключ) → объект решает, должен ли ключ уйти (одно правило: память не хранит подтверждения ровно этой тройки «ключ, форма, ответы») → ключ в форму → подтверждение в память; затем следующий объект; в конце перегенерирует `keys.txt`;
   8. выводит результат: сводку — в консоль, отчёт — в `logs\{DD-MM-YYYY}_{HHMMSS}_report.md`, диагностику — в `logs\{DD-MM-YYYY}_{HHMMSS}_planer.log`; попутно удаляет старьё (файлы и записи памяти старше `keep_days`).
4. Владелец смотрит отчёт. Что-то не так с эфиром — правит или удаляет его на YouTube руками; следующий запуск это увидит.

## Инварианты — не нарушать без явного согласования с Артуром

0. **Рабочая единица — объект запланированного эфира** (`app\pipeline\plan.py`): один объект = один эфир одного слота на одном канале. Из пакета — слот, канал и спека; со сверки — найденный эфир и его спека; дальше — результаты. После фазы входов объект держит объект своего канала (`channel_object`), объект своей формы (`key_form`, `form_failure`), текущие ответы формы (`form_answers`) и причины недопуска (`admission_reasons`); правило допуска — только `PlannedBroadcast.admit`. **Память планера** — `secrets\planer.sqlite3` (`app\records\`): одна запись на (`slot_id`, id канала на YouTube), колонки поиска и поля объекта одним JSON; обратно читаются только результаты (эфир, поток, ключ, подтверждение формы), задания из памяти не берутся — что делать, каждый запуск решают свежие пакеты, форма и `channels.json` (решения 17-09-2026). Таблицы каналов в памяти нет: `channels.json` и паспорт остаются файлами.
1. **Истина об эфирах — на YouTube; ключ потока и ссылка на эфир читаются только с площадки.** Память планера — истина только о том, что форма подтвердила; существование эфира и его ключ по памяти не решаются. Перед любым созданием — сверка `liveBroadcasts.list(broadcastStatus=upcoming)` (без `mine` — фильтры взаимоисключающие); совпадение по минуте старта (UTC) + маркер `slot_id` в `liveStreams.snippet.title`. Опознанный эфир сверяется по **всем** параметрам, которые планер диктует площадке (название, описание, категория, видимость, маркер потока, обложка, автостарт, автостоп, задержка): расхождение исправимого поля — эфир исправляется на месте только теми вызовами, которых требуют разошедшиеся поля (`FIX_CALLS`), пакет в приоритете; неисправимое — строка в лог, «внимание:» в консоли и строка в отчёте, на ручную правку владельцем планер не рассчитывает. Эфира нет — создание; решения «создать заново» нет. Слот внутри `min_lead_minutes` сверяется только на чтение, ради ключа. К площадке обращаемся только по каналам, у которых есть объекты; вход и проверка канала (ник → id → название) — в фазе входов, до сверки, подряд по всем каналам, которым нужен вход; до пакетов — только сверка каналов с токеном без браузера (выравнивание ника и названия, решение 17-09-2026).
1a. **В форму уходит ключ, который в этом запуске должен дойти до стримера** (`should_send_key`) — одно правило, метод объекта-слота `PlannedBroadcast.decide_key_delivery`: объект допущен, не too_late, ключ и адрес потока взяты с площадки в этом запуске и в памяти **нет** подтверждения ровно этой тройки — тот же `stream_key`, тот же адрес формы (`KeyForm.structure.response_url`), те же ответы (`entry_id` → значение, `RecordResults.has_confirmed`). Вид действия не важен. Следствия: создан или привязан поток — ключ новый — уходит; совпал и подтверждение есть — не уходит; совпал без подтверждения (обрыв, прошлая отправка не прошла, объект не был допущен) — уходит; исправлен с теми же ответами — не уходит; исправлен, и ответы другие (например, название канала после выравнивания) — уходит; эфир удалён руками и создан заново — уходит; сменились адрес или вопросы формы (переход на боевую) — уходит в новую форму. Ошибка другого шага объекта отправку уже взятого ключа не отменяет. Полны ли ответы — `is_key_ready_to_send`: неполные — ключ «должен был уйти и не ушёл». Момент отправки — сразу после действий по своему объекту (`runner._Executor._deliver_key`), финального прохода нет; подтверждение формы сразу пишется в память (`PlannedBroadcast.confirm_key`). Эфир старше памяти (любой запуск): у допущенного объекта без записи, с решением MATCH или UPDATE, найденным потоком с меткой этого слота и эфиром, созданным на площадке (`UpcomingBroadcast.published_utc`, `snippet.publishedAt`) раньше памяти (`RecordStore.created_utc`), подтверждение записывается как есть (`bootstrap_confirmation(now, memory_created_utc)`, `is_bootstrap`), ключ не отправляется, INFO `record_bootstrap`; ручной эфир без метки, эфир без времени создания, созданные после памяти и этим запуском — по общему правилу (прогон 17-09-2026 17:39: память создана в 17:32 с одним пакетом, к 17:39 правило «файла не было» уже не срабатывало, и восемь ключей Osvald.X / Oktavian.X ушли в боевую форму повторно). too_late и не допущенные объекты ключ не шлют. Задвоение строки у стримера допустимо (решение 15-09-2026): стример берёт последнюю строку по дате, каналу и языку — README этапа 5 обязан объяснить это стримеру.
2. **Google-форма — единственный канал передачи ключей стримеру.** Никаких обходных путей. URL формы, названия вопросов и тексты вариантов — только из пакета (`form.url`, `form.fields`, `form.values`, `form.date_format`), у каждого слота своя форма (пакета-победителя его `slot_id`): в коде и в конфигах `secrets\` ссылок на формы нет. `entry.*`-ID не хардкодятся и не конфигурируются — читаются из HTML формы; отправка только после проверки, что для всех обязательных вопросов есть данные. Поля с `null` в `form.fields` не отправляются. Планер никогда не отправляет значение, которого нет среди вариантов вопроса: нет даты в «Время стрима» → объект не допущен; форма не подтвердила ключ — подтверждения в памяти нет, следующий запуск отправит ключ снова, а до того он передаётся из `keys.txt` вручную.
3. **Пакет — только чтение.** Все решения — по `manifest.json`, никогда по имени файла. Читаются все пакеты из `bcast\` — сколько бы их там ни было, подпапок нет; пакетов нет — код 3, каналы не трогаются; слоты сливаются в одну карту по `slot_id`, более новый пакет побеждает, прошлое отбрасывается. Планер пакеты не двигает и не переписывает; удаляет только старьё по `keep_days`.
4. **Даты `DD-MM-YYYY`, время `HH:MM` по Киеву** — во всех файлах, именах и отчётах планера. Исключения: `start` в манифесте и `slot_start_utc` в памяти планера — ISO-8601 (со смещением / UTC), только для сравнения моментов; значения, уходящие в форму, — в `form.date_format` из пакета, и отчёт, цитируя вариант формы, приводит дату как в форме.
5. **Никаких паролей.** Авторизация — OAuth, скоуп только `https://www.googleapis.com/auth/youtube`, один токен на канал: `secrets\<handle>.token.json`. Ключ канала — ник `handle` из `secrets\channels.json` (`ChannelConfig.key` — без «@», NFC, без регистра): все словари, кеши, группы вывода и память отказов — по нему; `account_name` — название для людей и формы, одинаковые названия допустимы (решение 17-09-2026). Id канала на YouTube не меняется никогда: паспорт каналов `secrets\channels_passport.json` связывает ник ↔ id ↔ файл токена. Проверка канала — ник → id по паспорту → название; ник или название сменились, а id подтверждён — планер сам выравнивает `channels.json`, файл токена и паспорт, повторный вход владельцу не нужен; не подтверждён — ошибка объектов этого канала до конца запуска, остальные каналы работают. `client_secret.json` — общий, поставляется с exe.
6. **Ключи потока в логах маскируются** (последние 4 символа). В `keys.txt` — полностью. Формат ключа YouTube проверяется по `YOUTUBE_STREAM_KEY_PATTERN` в `platforms/youtube.py`.
7. **Настройки эфира задаёт планер, а не канал.** Аудитория — всегда «не для детей», категория — из `planer.json` (`category_id`, одна на все каналы; оттуда же `auto_start` и `set_thumbnail`), язык — из слота. Все три и видимость (`privacyStatus` из `channels.json`) правятся одним проходом по ресурсу `videos` (`part=snippet,status`, read-modify-write целиком) у каждого своего эфира на каждом запуске; совпало всё — записи нет. Живой чат и модерация комментариев в API отсутствуют — это настройки Студии. Возрастное ограничение 18+ через API **только читается**: попытка записать `contentDetails.contentRating` даёт 400, снимать его владелец должен руками в Студии.
8. **Эфиры не удаляются автоматически.** Эфиры без соответствия слоту (ручные/чужие) не трогаются и в отчёт не попадают. Исправление изменившегося эфира — `liveBroadcasts.update` на месте, ключ и ссылка сохраняются.
9. **Один сбой не валит запуск.** Ошибка изолируется в объект и уходит в отчёт; остальные обрабатываются. Недоступный канал и отказ проверки канала (ник, id) — ошибка всех объектов этого канала, другие каналы работают. Отказ YouTube обрабатывается по причине (`platforms\youtube.py::REASON_BEHAVIORS`, пары «операция, причина» — `OPERATION_REASON_BEHAVIORS`, решение — только `_error_behavior`), пять поведений: повторить с нарастающей паузой (5xx, сеть, лимиты частоты); не повторять этот вызов (в том числе создающий вызов — `liveBroadcasts.insert`, `liveStreams.insert`, `CREATING_OPERATIONS` — с неизвестным исходом: обрыв связи или 5xx; повтор мог бы завести второй эфир или поток, объект остаётся несозданным, его доделает следующий запуск; лимит частоты у создающего вызова повторяется как у всех); не вызывать эту операцию на этом канале до конца запуска (лимит загрузки обложек, трансляции выключены…); не обращаться к каналу (доступ отозван, канал закрыт…); не обращаться к YouTube (квота). Между любыми двумя обращениями к YouTube API — не меньше `youtube_pause_seconds` из `planer.json` (число ≥ 0, можно дробное; в поставке 0.5); картинки i.ytimg.com — не API, без паузы.
10. **Всё владельца — в одной папке `secrets\`; `logs\` — диагностика и отчёты запусков.** В корне владелец видит только своё: `secrets\` (`channels.json`, `planer.json`, `client_secret.json`, токены каналов), `bcast\` (пакеты), `keystreams\` (ключи потоков), `logs\`; всё остальное — в `app\`. Единственный файл состояния — память планера `secrets\planer.sqlite3`: пишет только планер, в git и в сборку не попадает, повреждённый файл переименовывается в `planer.sqlite3.broken-<DD-MM-YYYY_HHMMSS>` (не удаляется) и создаётся новый. Конфиги — два JSON, все поля обязательные, умолчаний в коде и примеров рядом с программой нет; конфиги в `secrets\` планер не пишет — кроме одного случая: выравнивание ника и названия в `channels.json` по id YouTube (прежний файл — `channels.previous.json`); паспорт каналов пишет только планер. Отчёт — такой же производный файл, как лог: имя по шаблону «дата_время_наименование», старьё уходит по `keep_days`.
11. **Новые зависимости — только с явного согласования.** Разрешённый набор: `google-api-python-client`, `google-auth`, `google-auth-oauthlib`, `requests` + stdlib (PyYAML убран в задаче 5b: конфиги — JSON); инструмент сборки — `pyinstaller==6.19.0` (в том же `.venv_planers`, в код приложения не импортируется).
12. **Форма и канал для разработки — тренировочные** (копия боевой формы, тестовый канал). Тренировочная форма — https://forms.gle/UjVo2gftZdHsEdpZ7, таблица ответов — https://docs.google.com/spreadsheets/d/1YM1ydbTrpU1T7Vgp6oUreNDpJK-Khwle3RJXL8wbASE/edit. Боевая форма — https://forms.gle/MA6D898sT86Tvsyw7, только на этапе 5.

```json
      "previews": ["previews/16-09-2026_1900_uk_1.jpg", "previews/16-09-2026_1900_uk_2.jpg"],
      "sources": ["https://www.youtube.com/watch?v=…"]
    }
  ]
}
```

- Пакет — весь прогон броадкастера: все даты, все языки; `period` — min/max дат слотов, другого смысла нет.
- `slot_id` = `{DD-MM-YYYY}_{HHMM}_{lang}`; `date` — для людей и формы, `time` — для людей (в форму не уходит), `start` — момент для сравнения с YouTube (UTC) без базы часовых поясов.
- `title`/`description` — ровно те тексты, что ушли в анонс Telegram; в пакет попадает каждая пара (слот, язык), по которой был анонс.
- `previews` — 1..N файлов одного эфира; обложкой ставится **одно случайное**.
- `form.url` — ссылка как есть (forms.gle), планер идёт по редиректу; `form.fields` — названия вопросов символ в символ, `null` — вопроса нет; `form.values` — тексты вариантов радио-вопросов по кодам; `form.date_format` — strftime-формат даты в начале варианта «Время стрима».
- Неизвестная `schema_version` — пакет не читается, строка в отчёте. `generator` — информационное поле. Прошлое планер фильтрует сам, даже если броадкастер уже отфильтровал.

### Конфиги: `secrets\channels.json` и `secrets\planer.json`

Оба JSON. **Все поля обязательные, умолчаний в коде нет, примеров рядом с программой нет, планер ничего не копирует.** Неизвестное или повторённое поле — ошибка с его именем.

**`secrets\channels.json` — заполняет владелец**, ровно шесть полей на канал; канал — две строки (так же файл пишет планер: `config\loader.py::render_channels_file`):

```json
{
  "channels": [
    {"platform": "youtube", "account_name": "Название канала на YouTube", "handle": "@ник_канала", "google_account": "you@gmail.com",
     "languages": ["ru"], "privacy": "unlisted"}
  ]
}
```

- `platform` — только `youtube`; `facebook` — ошибка «появится на этапе 6», прочее — ошибка со списком допустимых.
- `account_name` — название канала как на YouTube: уходит в форму как «Название канала»; в выводе (консоль, отчёт, `keys.txt`, описание ключа потока) рядом с ним всегда ник. Перед проверками приводится к NFC. Ошибка — только: пусто, длиннее 100 символов, управляющий символ (перевод строки, табуляция), пробел в начале или в конце. **Уникальность не проверяется**: одинаковые названия у разных каналов допустимы («Українка я» @TheImpact-r2b и «Українка Я» @Ukrainian_girl25 — Windows не различает регистр в именах файлов, поэтому ключ канала — не название). Название, сменённое на YouTube, планер выравнивает сам.
- `handle` — ник канала на YouTube (Студия -> аватар вверху справа), **ключ канала**: файл токена `secrets\<handle>.token.json`, `--auth`, пробники `--channel`. Проверка: строка в NFC, начинается с «@», после «@» от 3 до 30 символов, без пробельных и управляющих символов и без `< > : " / \ | ? *`. Повтор ника без учёта регистра — `CONFIG_PROBLEM_HANDLE_DUPLICATE`. Ник как в файле — `ChannelConfig.handle`; единственная нормализация — `core\text.py::normalize_handle` (`ChannelConfig.key`). Ник, сменённый на YouTube, планер выравнивает сам, если паспорт подтверждает id.
- `google_account` — почта аккаунта Google, в котором живёт канал: подсказка браузеру при входе (`login_hint`) и строка в консоли перед браузером. Проверка минимальная: непустая строка, ровно один `@`, части вокруг него непустые и без пробелов.
- `languages` — непустой список кодов строчными без повторов. Канал может обслуживать несколько языков (например `["uk", "ru"]`): слот размножается по всем каналам своего языка, единица работы по-прежнему «слот на канале» — у многоязычного канала слоты разных языков одной минуты дают отдельные объекты и отдельные эфиры. Язык стримов назначает **оператор** здесь; язык канала на YouTube только показывается в `--check`. Коды со справочником не сверяются: язык без варианта в форме даст эфир и ключ, но отправка вернёт `missingOption`.
- `privacy` — `public` | `unlisted`.

**`secrets\planer.json` — технический, поставляется со сборкой заполненным**, действует на все каналы:

```json
{"min_lead_minutes": 60, "keep_days": 30,
 "auto_start": true, "set_thumbnail": true, "category_id": "22",
 "youtube_pause_seconds": 0.5}
```

`min_lead_minutes` (целое ≥ 0) — слоты, до старта которых меньше, не планируются; `keep_days` (целое ≥ 1) — срок хранения файлов в `bcast\` и `logs\`; `auto_start` — эфир стартует сам, когда пошёл поток; `set_thumbnail` — ставить превью из пакета; `category_id` — категория YouTube (`"22"` — People & Blogs), по справочнику не проверяется; `youtube_pause_seconds` (число ≥ 0, можно дробное: `0`, `0.5`, `2`; `PlanerSettings.youtube_pause_seconds: float`, проверка — `loader._number`, ошибка — `CONFIG_PROBLEM_NUMBER_MIN`; в поставке `0.5`) — наименьший промежуток в секундах между любыми двумя обращениями планера к YouTube API (`_execute`); паузы повторов входят в него, а не складываются с ним. Картинки обложек с i.ytimg.com (`_picture_sha`) — не API и квоту не тратят: паузы перед ними нет, отсчёт паузы они не сдвигают. Решение 21-09-2026 (прогон 0.1.9 12:55: из 690 с работы пауза 2 с заняла 612 с, запросы — 69 с; ответ YouTube по Console — чтение 0,04–0,3 с, запись 0,6–1,6 с, обложка 3,4 с; от `uploadRateLimitExceeded` пауза не защищает — отказы были и при 2 с): пауза остаётся настройкой, в поставке 0.5.

`secrets\planer.json` в git — один источник и для dev, и для сборки; остальное в `secrets\` git не видит (`.gitignore`: `/secrets/*` и исключение `!/secrets/planer.json`). Шаблон каналов для репо и README — `app\examples\channels.example.json` (в коде не упоминается, в сборку не идёт). Нет файла или обязательного поля — код 2, ошибка и точный шаблон файла в консоли («Создайте файл … с таким содержимым и впишите свои значения», для `planer.json` — «Восстановите файл…»); у `channels.json` между этой строкой и шаблоном — подсказка по полям (`CONFIG_CHANNELS_FIELDS`, `main._say_channels_fields`): что вписать в каждое поле, допустимые значения — из тех же `allowed_values(Privacy)` / `allowed_values(Platform)` и `CONFIG_LANGUAGES_RULE`, что проверяет `config\loader.py`; прочая ошибка — код 2 и строка с путём поля (`channels[1].languages`). Сначала читается `channels.json`, затем `planer.json`. Логинов, паролей, URL формы, entry-ID и путей к токенам в конфигах нет.

Планер переписывает `channels.json` только при выравнивании (раздел «Сверка каналов при старте»): прежний файл байт в байт — в `secrets\channels.previous.json` (перезаписывается), новый — атомарно (временный файл + `os.replace`, `paths.py::write_text_atomically`), текст — только `render_channels_file`, затем конфиг перечитывается. Ник и название, которые не прошли бы проверку загрузчика (`handle_problem`, `account_name_problem`), не пишутся — предупреждение.

### Файлы `secrets\` — кто пишет

| Файл | Пишет | Что это |
|---|---|---|
| `planer.json` | сборка (в git) | настройки планера |
| `channels.json` | владелец; планер — только выравнивание ника и названия | каналы |
| `channels.previous.json` | планер | `channels.json` до последнего выравнивания |
| `channels_passport.json` | только планер | паспорт каналов: ник ↔ id YouTube ↔ файл токена |
| `planer.sqlite3` | только планер | память планера: что сделано на YouTube и что подтвердила форма (таблица `slots`) и статистика запусков (таблица `runs`, строка на каждый запуск в любом режиме); в git и в сборку не попадает |
| `client_secret.json` | оператор (поставка) | паспорт программы |
| `<handle>.token.json` | планер (вход, обновление; переименование при выравнивании ника) | пропуск канала |

### Паспорт каналов `secrets\channels_passport.json`

`platforms\passport.py` (`ChannelPassport`: `load`, `find_by_key`, `find_by_channel_id`, `record`, `record_verified`, `save`; записи — `PassportEntry`). Путь — `PlanerPaths.channels_passport_file`. Формат — `{"channels": [ … ]}`, UTF-8 без экранирования, отступ 2, записи по `account_name`, затем `handle`; запись атомарно. Поля записи: `handle`, `account_name` (как в `channels.json` после выравнивания), `youtube_channel_id`, `youtube_title`, `youtube_handle_raw` (`snippet.customUrl` как пришёл), `google_account`, `token_file`, `channel_url` (`https://www.youtube.com/channel/<id>`), `handle_url` (`https://www.youtube.com/<handle>`), `first_verified_at`, `last_verified_at` (`DD-MM-YYYY HH:MM`, местное время), `previous_handles`, `previous_titles` (прежние значения без повторов). Шаблоны ссылок — `CHANNEL_URL_TEMPLATES` / `HANDLE_URL_TEMPLATES` в `platforms\base.py`. Одна запись на канал: запись того же id или того же ника заменяется; записи каналов, которых нет в `channels.json`, не удаляются (по ним находится токен после ручной смены ника). Нет файла — пустой паспорт; не читается или не той формы — WARNING `passport_unreadable`, предупреждение запуска `WARNING_PASSPORT_UNREADABLE`, паспорт пустой и перезаписывается; запись не удалась — WARNING `passport_write_failed`, `WARNING_PASSPORT_WRITE_FAILED`, запуск продолжается. Запись создаётся или обновляется после каждой успешной проверки канала (`first_verified_at` сохраняется) и сохраняется сразу. Паспорт — не вход для решений об эфирах.

### Сверка каналов при старте

`platforms\channel_sync.py::ChannelSync.run` через `platforms\channel.py::ChannelBook.check_without_login` — в `main.py` после загрузки конфига и до `run` в обычном запуске, `--dry-run`, `--status` и `--check` (в `--dry-run` файлы каналов тоже выравниваются: к эфирам это не относится); `--auth` её не делает. Тот же экземпляр `YouTubePlatform` потом обёрнут в `VerifiedPlatform`. Результат — конфиг после выравнивания, строки предупреждений (они идут в `run(..., channel_warnings=)` → `build_warning_lines` → консоль и отчёт; в `--check` — строками в консоль) и объекты `Channel` со статусом (`ChannelSync.take_channels`, конфиг объекта — после выравнивания). Что делать с каналом, решает `Channel.check` (ник → id по паспорту → название: `CONFIRMED` / `ALIGN` / `REFUSED` с кодом); `ChannelSync` — механика файлов. По каждому каналу `channels.json`, **без браузера** (`describe_channel(allow_login=False)` → `load_credentials(allow_login=False)`, нужен вход — `AuthErrorReason.LOGIN_REQUIRED` / `loginRequired`, отказ не запоминается):

1. Токен `secrets\<handle>.token.json` есть. Нужен вход (токен отозван) — `NEEDS_LOGIN`; другой сбой (`PlatformError`) — `FAILED` с этой ошибкой (INFO `channel_sync_skipped`). `CONFIRMED` — запись паспорта создать или обновить, `READY`. `ALIGN` (ник совпал, название другое; или ник другой, а паспорт по нику подтверждает тот же id) — выровнять ник и/или название, `READY`. `REFUSED` и паспорт id этого канала не подтверждает (`channelHandleMismatch`, `channelIdMismatch`, `channelHandleMissing` без записи паспорта) — **токен чужой**: `drop_login`, файл токена удаляется (`google\auth.py::drop_token`), WARNING `token_rejected` (канал, ник, что прислал YouTube, код), предупреждение запуска `WARNING_TOKEN_REJECTED`, статус `NEEDS_LOGIN`; других удалений токенов нет. `REFUSED`, а паспорт id подтверждает (у канала на YouTube пропал ник) — токен свой, статус `REFUSED` с текстом `AUTH_CHANNEL_HANDLE_MISSING`, ERROR `channel_refused`.
2. Токена по нику нет — ищутся записи паспорта, чьего ника нет в `channels.json` и чей `token_file` есть; канал за таким токеном (временный канал из записи) с ником из `channels.json` — тот же канал после ручной правки ника: токен переименовывается, запись паспорта переключается на новый ник, название выравнивается, `READY`. Не нашлось — `NEEDS_LOGIN`: вход — в фазе входов, если у канала есть объекты.

Выравнивание ника — переименование файла токена без перезаписи (другой файл с таким именем уже есть — WARNING `token_rename_skipped`, `WARNING_TOKEN_RENAME_SKIPPED`, файлы не трогаются); `handle` — ник из `customUrl` после `unquote` (`handle_from_custom_url`) в написании YouTube; прежний — в `previous_handles`. Выравнивание названия — `account_name` = `snippet.title` (NFC, края сняты), прежнее — в `previous_titles`. За старт: токены → один раз `channels.json` (не записался — токены возвращаются, `WARNING_CHANNEL_ALIGN_FAILED`) → паспорт → конфиг перечитывается. Лог — INFO `channel_aligned` (ник, название, id, файл токена до и после); владельцу — `WARNING_CHANNEL_ALIGNED`. Так же каналы выравнивает вход в фазе входов (`ChannelSync.align_in_run`): файлы и паспорт — сразу, в выводе и форме этого запуска — прежние значения (хвост `WARNING_CHANNEL_ALIGNED_IN_RUN`), предупреждения — через `take_notices` (`PlatformNoticeKind.CHANNEL`).

### Секреты и вход в канал

- **`secrets\client_secret.json` — «паспорт программы»**: OAuth-клиент типа Desktop из GCP-проекта оператора, один на всех владельцев, лежит рядом с exe. Нет файла — код 2, к YouTube планер не обращается.
- **`secrets\<handle>.token.json` — «пропуск канала»**, появляется после первого подтверждённого входа в канал. Имя файла — `core\text.py::token_file_stem(handle)` (ник как в `channels.json`: `@Ukrainian_girl25.token.json`), путь — только через `google\auth.py::token_file_for(secrets_dir, handle)`: каждый символ `\ / : * ? " < > |` и каждый управляющий символ → `_`; пробелы и точки в начале и в конце → `_` каждый (длина не меняется); зарезервированное имя Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1–9`, `LPT1–9`, без учёта регистра) получает `_` в конце. Токены, названные по `account_name` до задачи 5l, переименованы в ники 17-09-2026. Токен обновляется сам (обновление пишет файл сразу); отозван — статус «нужен вход».
- **Токен — только после подтверждения канала** (живой прогон 17-09-2026: вход «Українка Я» @Ukrainian_girl25 отдал канал «Lisa Thomson», проверка отказала, а токен уже был записан — дальше каждый запуск получал тот же отказ без браузера). `google\auth.py::load_credentials` файл после входа не пишет (`_run_flow` только возвращает учётные данные); `force_reauth` — вход мимо токена, файл не удаляется. Запись — `save_token`: её зовёт `YouTubePlatform.keep_login` (учётные данные нового входа до этого живут в памяти клиента канала). `BroadcastPlatform.keep_login(channel)` — записать токен нового входа; `drop_login(channel)` — забыть клиент, учётные данные, `ChannelInfo` и запомненные отказы канала: следующий `describe_channel(allow_login=True)` открывает браузер, токен на диске не читается. Браузер открывает только `describe_channel(allow_login=True)`; все прочие обращения `YouTubePlatform._execute` идут с `allow_login=False`. `FakePlatform` ведёт себя так же (`login_answers`, `fail_login`, `kept_logins`, `dropped_logins`, `secrets_dir`).
- **Объект-канал** (`platforms\channel.py`). `Channel` — изменяемый: `config`, `token_file`, `passport_entry`, `info` (что прислал YouTube), `status` (`ChannelStatus`: `READY` — подтверждён; `NEEDS_LOGIN` — токена нет, он отозван или убран как чужой; `REFUSED` — вход был, но канал не тот после всех попыток; `FAILED` — сбой площадки или входа), `error` (готовый текст для отчёта), `login_attempts`. Правило проверки — `Channel.check(info)` → `ChannelCheck` (`CONFIRMED` / `ALIGN` / `REFUSED` + код), по порядку:
  1. ника у канала на YouTube нет — `channelHandleMissing` (`AUTH_CHANNEL_HANDLE_MISSING`);
  2. ник другой: паспорт по нику из `channels.json` подтверждает тот же id — `ALIGN`; иначе — `channelHandleMismatch` (`AUTH_CHANNEL_HANDLE_MISMATCH`);
  3. ник совпал, а в паспорте у этого ника другой id — `channelIdMismatch` (`AUTH_CHANNEL_ID_MISMATCH`);
  4. название другое при совпавшем нике — `ALIGN` (отказа по названию нет).
  Тексты отказов (`Channel.refusal` → `ChannelBindingError`) показывают значение из `channels.json` и то, что прислал YouTube (название, ник, id), и заканчиваются `AUTH_NEXT_RUN_HINT` («при следующем запуске планер снова предложит вход; ник сменили на YouTube — впишите новый ник в channels.json»); подсказки `planer.bat --auth` в них нет.
- **`ChannelBook`** — все каналы запуска, один экземпляр (`main._build_dependencies`), канал — `channel(config)` по `ChannelConfig.key`. Порядок запуска: проверка без браузера (`check_without_login`) → пакеты → формы → объекты → **фаза входов** (`log_in_needed`, `runner.run(..., logins=)`, между `build_planned` и `Reconciler.reconcile`): каналы, у которых есть объекты (включая объекты внутри `min_lead_minutes`) и статус `NEEDS_LOGIN`, входят подряд, один за другим (INFO `login_phase_done`) → сверка. После фазы входов браузер в этом запуске не открывается ни при каких обращениях. `--status` и `--check` — фаза входов по всем каналам `channels.json`.
- **Вход одного канала** — `ChannelBook.log_in(config, force=False)`, одно место для запуска, `--check` и `--auth`: `drop_login` → INFO `login_started` (попытка n из `LOGIN_MAX_ATTEMPTS`) → консоль (`LoginConsole.on_login`: `AUTH_STARTING`, `AUTH_CHOOSE_ACCOUNT`, `AUTH_CHOOSE_RIGHT_CHANNEL`, `AUTH_UNVERIFIED_APP_WARNING` — Advanced → Go to ... (unsafe) → Continue) → браузер → `describe_channel` → `Channel.check`:
  - подтверждён или выровнен — `keep_login` (токен записан до выравнивания: выравнивание ника переименовывает уже записанный файл; не записался — WARNING `token_save_failed`, `WARNING_TOKEN_SAVE_FAILED`, канал в этом запуске работает), выравнивание или запись паспорта (`ChannelSync.confirm`), `READY`, INFO `login_confirmed`, `AUTH_OK`;
  - канал не тот — `drop_login`, WARNING `login_wrong_channel`, в консоль `AUTH_WRONG_CHANNEL_RETRY` («… в браузере выбран канал «…» … — нужен «…» …; вход ещё раз») и новый вход; попыток на канал за запуск — `LOGIN_MAX_ATTEMPTS` = 2; после второй неудачи — `AUTH_WRONG_CHANNEL_GIVE_UP`, ERROR `channel_refused`, `REFUSED`, токен не записан;
  - сбой входа (браузер закрыт, `AuthError`) — ERROR `login_failed`, `FAILED` с причиной, `AUTH_FAILED` и `AUTH_SCOPE_HINT`, токен не записан;
  - вход не завершён за `google\auth.py::LOGIN_TIMEOUT_SEC` (600 с: живой первый вход 17-09-2026 занял 8,5 минуты; прогон 16:38 без предела висел до закрытия окна) — `run_local_server(timeout_seconds=…)` бросает `WSGITimeoutError` (наследник `AttributeError`, ловится отдельно) → `AuthError(AuthErrorReason.LOGIN_TIMEOUT)`; `ChannelBook._fail` — WARNING `login_timeout channel="…" handle=… timeout_sec=…`, `FAILED` с текстом `AUTH_REASON_TEXT["login_timeout"]` (минуты — `LOGIN_TIMEOUT_MINUTES`, подставляет `channel.py::login_failure_text`), **второй попытки в этом запуске нет** (человека нет у компьютера), `AUTH_FAILED` без `AUTH_SCOPE_HINT`; объекты канала не допущены, остальные каналы работают; токена нет — следующий запуск снова предлагает вход.
- **Тексты входа в браузере** — `run_local_server(authorization_prompt_message=msg.AUTH_OPEN_LINK, success_message=msg.AUTH_BROWSER_DONE)`: строка «Если браузер не открылся — откройте ссылку: {url}» (плейсхолдер — формат библиотеки, печатает сама библиотека) и страница «Вход выполнен. Вернитесь в окно планера.» вместо английских текстов библиотеки.
- **Шлюз площадки** (`platforms\verified.py::VerifiedPlatform(platform, book)`) сам не входит и не проверяет: канал не `READY` — каждый метод поднимает ошибку из объекта (`Channel.access_error`: `REFUSED` — `ChannelBindingError`, `FAILED` — сбой, `NEEDS_LOGIN` — `loginRequired`); сверка изолирует её как любой сбой канала — все объекты канала ошибка, остальные каналы работают. `describe_channel` через шлюз отдаёт `Channel.info` без второго обращения.
- **`--auth <handle>|all`** — `log_in(force=True)` без проверки при старте: прежний токен не удаляется до подтверждения нового входа; подтверждён — перезаписывается; не подтверждён — остаётся как был; отказ — `CHECK_CHANNEL_REFUSED`, код 1.
- **Экран выбора канала Google** — `google\auth.py::PROMPT = "select_account consent"` (одна константа), `login_hint` = `google_account`.
- Механика — `InstalledAppFlow.run_local_server` (порт 0), как в броадкастере; скоуп другой, токен — на канал. В git из `secrets\` — только `planer.json`.

### Файл ключей `keystreams\keys.txt`

Нужен, когда форма не сработала и ключ передают руками. Перегенерируется на каждом запуске: блок на каждый будущий эфир с ключом, **включая слоты внутри `min_lead_minutes`**; ключ читается с площадки (у чужих эфиров тоже). Шапка из девяти строк, блоки через пустую строку, сортировка по дате, времени, языку, **ключ — первым полем блока**. Формат `.txt`, значков ✅/❌ нет.

```
# Ключи трансляций. Сгенерировано планером 13-09-2026 12:00.
# Файл перезаписывается на каждом запуске — не править.
# Строка «форма»:
#   «отправлен в форму» — форма подтвердила ключ в этом запуске;
#   «передан в форму» — форма подтвердила этот ключ раньше (память планера);
#   «передан до появления памяти планера» — эфир уже стоял с меткой планера, когда память создавалась;
#   «НЕ отправлен» — ключ должен был уйти и не ушёл: передайте его стримеру вручную;
#   «НЕ отправлен: не допущено» — форма этот эфир не принимает (нет даты или варианта) или канал не подтверждён: …;
#   «нет подтверждения в памяти планера» — планер не знает, получил ли стример этот ключ.

16-09-2026 19:00  uk  Канал UA @kanal_ua
  ключ   xxxx-xxxx-xxxx-xxxx-xxxx
  поток  rtmp://a.rtmp.youtube.com/live2
  эфир   https://www.youtube.com/watch?v=abc123
  форма  отправлен в форму 13-09-2026 12:00
```

Строка «форма» — что сделано в этом запуске, а если ничего — что знает память о текущем ключе; шесть состояний (тексты — в `messages_ru`; цитаты в шапке — те же `KEY_FORM_*_LEAD`, что начинают строки; `keys_file.form_status_text`, `confirmation_text`): «отправлен в форму <дата время>» — подтверждён в этом запуске; «передан в форму <дата время>» — подтверждение из памяти про текущий ключ; «передан до появления памяти планера» — подтверждение записал первый запуск с памятью (`is_bootstrap`); «НЕ отправлен — <причина>; передайте стримеру вручную» — ключ должен был уйти и не ушёл; «НЕ отправлен: не допущено — <причины>» — объект не допущен, а его эфир на канале есть; «нет подтверждения в памяти планера» — записи нет или она про другой ключ (так же в `--status`, если памяти о ключе нет). Прежнего «эфир уже стоял с этим ключом» больше нет: без памяти планер этого не знал.

### Консоль, отчёт и лог

| Поверхность | Читатель | Что в ней |
|---|---|---|
| консоль | владелец, во время и сразу после запуска | шапка при старте и строка на каждый долгий шаг; затем перечень блоками сверху вниз: что требует внимания, что опубликовано, исправлено, какие ключи ушли стримеру, что уже стояло и что не публиковалось; без markdown и значков; один эфир — ровно одна строка без переносов |
| `logs\{DD-MM-YYYY}_{HHMMSS}_report.md` | владелец; можно переслать оператору | то же с подробностями |
| `logs\{DD-MM-YYYY}_{HHMMSS}_planer.log` | разработка | диагностика `key=value` |

Одно и то же в двух местах не печатается. Счётчики считаются один раз (`build_totals`) — для «Итога» отчёта и для консоли.

**Терминал — только тексты для владельца** (`messages_ru`, печатает `main.py`). Сырой лог (`… | WARNING | …`) в терминал идёт только с `--debug` (обработчик stderr уровня DEBUG); без `--debug` обработчика лога на терминал нет вовсе (`observability\logging_setup.py::setup_logging`). Логгеры сторонних библиотек (корневой логгер Python: googleapiclient, google_auth_oauthlib, urllib3…) и `warnings.warn` (`logging.captureWarnings`) от WARNING пишутся в тот же файл лога; у корневого логгера есть свой обработчик, поэтому `logging.lastResort` в терминал не печатает; `close_logging` снимает с корневого логгера только свои обработчики. Каждое WARNING/ERROR планера — либо диагностика (только лог: повтор запроса, отказ, уже показанный объектом или каналом), либо у него есть строка владельца в ВНИМАНИЕ консоли и в отчёте (предупреждения запуска, исходы, `RUN_CRASHED`); новых строк лога, требующих внимания владельца, без текста из `messages_ru` не заводить. `RUN_INTERRUPTED` и `RUN_CRASHED` печатаются через `_say`, трассировка — только в лог.

**Консоль** — порядок вывода сверху вниз:
1. **Шапка** «Planer <версия> — <дата время>» (у `--dry-run` и `--status` — с пометкой режима, у `--check` и `--auth` — обычная): её печатает `main.py` сразу после настройки логов, до чтения конфигов и любого обращения к сети, во всех режимах; время — то же, что в отчёте запуска.
2. **Строки прогресса** (`output\progress.py`: Protocol `RunProgress`, `NoProgress` — умолчание для тестов и вызовов без консоли, `ConsoleProgress` — в `main`; отступ два пробела, `flush=True`, тексты `PROGRESS_*` в `messages_ru`): пакеты прочитаны — сколько пакетов, слотов всего и под мои языки (числа — `build_totals` по `build_package_lines`, тем же подсчётом, что отчёт; `runner` сразу после `scan_bcast` и `build_planned`); даты формы ключей — одна строка на форму до входов и до YouTube (`form_dates_checked`: все даты есть — `PROGRESS_FORM_DATES_OK`, дата текстом — `PROGRESS_FORM_DATES_ANY`, каких-то нет — `PROGRESS_FORM_DATES_MISSING`; раздел «Отправка в форму» п.1); по каждому каналу — «запрашиваю» до `list_upcoming` (вход в канал происходит внутри него) и «запланированных эфиров N» после ответа (`reconciler`; при сбое второй строки нет, ошибка — во ВНИМАНИЕ); «создаю эфир» / «исправляю эфир» (исполнитель в `runner`); «отправляю ключ в форму» перед каждой отправкой; «пишу отчёт». В `--dry-run` строк создания, исправления и отправки ключа нет, строки пакетов, дат формы, каналов и отчёта есть; в `--status` — каналы и отчёт. Прогресс передаётся параметром: `run(..., progress=)`, `Reconciler(..., progress=)`.
3. **Пустая строка** — отделяет прогресс от итога.
4. **Итог и блоки** (`output\console.py`, `render_console` начинается со строки «Итог», заголовка в нём нет — двух заголовков в прогоне не бывает). Строки «Итога» — `report.summary_lines`, одни и те же в консоли и отчёте: «Итог по эфирам (всего N): опубликовано N, исправлено N, уже стояло N, не допущено N, ошибок N.» — только пары «слот × канал» (`PairOutcome.is_broadcast`), слагаемые в сумме дают N (`RunTotals.broadcasts`); сбой канала или файла планера (исход без слота) в неё не входит — он в `RunTotals.failures` и в причинах кода выхода (dry-run — «опубликуем … исправим …», `--status` — «уже стояло N, ошибок N»); «Слоты вне работы: N — <причины>.» — раздел «Пропущено» (`report.skip_groups`), только если такие есть; «Код выхода 0 — выполнено всё.» / «Код выхода 1 — не всё выполнено: <причины>.» — всегда; затем блоки.
5. **Подвал** — пути к `keys.txt`, отчёту и логу.

Блоки итога. Блок начинается разделителем фиксированной ширины (`CONSOLE_RULE_WIDTH` в `messages_ru`) из «=» с названием и счётчиком внутри; у ВНИМАНИЕ счётчика нет. Блоков шесть, строго в таком порядке:
1. **ВНИМАНИЕ** — ошибки (отказ или сбой канала — одной строкой на канал), ключ не дошёл до стримера, в форме два ключа на один слот (`CONSOLE_ATTENTION_TWO_KEYS`: «… -> канал: прежний эфир на времени слота не найден — поставлен новый; в форме на эту дату два ключа: действующий ****-xxxx, прежний ****-yyyy»), не допущенные объекты («не допущено: <префикс> — <причины>; эфир на канале есть — ключ стримеру не передан | эфира нет | канал не подтверждён…»), проблемы пакетов, в форме ключей нет дат запуска (`WARNING_FORM_DATES_MISSING`, одна строка на форму, предстартовая проверка), предупреждения запуска и объектов: что планер вернул к пакету (видимость, категория, метка — «было / стало»; аудитория), что исправить не может (`REPORTED_FIELDS`), AMBIGUOUS со ссылками (строкой ошибки не дублируется), замечания площадки о каналах (выравнивание ника и названия, `PlatformNoticeKind.CHANNEL`). Служебный эфир площадки без времени старта во ВНИМАНИЕ не идёт — он в «Особенностях площадки» отчёта (ниже). Особенности площадки (`PLATFORM_NOTE_LINES` и `RunReport.platform_notes`) в консоль не идут.
2. **ОПУБЛИКОВАЛИ** — созданные эфиры и эфиры с привязанным потоком.
3. **ИСПРАВИЛИ** — только эфиры, у которых этот запуск что-то действительно исправил (`fixed_fields`; `report.outcome_from_planned`: UPDATE без исправленного — исход MATCHED, «уже стояло», ключ и ссылка прежние; не удалось — хвост «; обложка не поставлена», `UNFIXED_FIELD_TEXT` / `OUTCOME_UNFIXED`, `report.unfixed_text`, так же в отчёте; причина — в предупреждении; в `--dry-run` — по `changed_fields`). К строке эфира добавляется, что обновлено (только `fixed_fields`), но только из содержимого эфира — название, описание и обложка (названия полей — как в отчёте). Настройки (видимость, категория, метка) здесь не называются: они во ВНИМАНИЕ с «было / стало». Изменились только настройки — строка эфира без хвоста «обновлено», эфир всё равно в блоке и в счётчике «исправлено».
4. **КЛЮЧИ СТРИМЕРУ** — все эфиры, у которых в этом запуске `should_send_key`, дошёл ключ или нет: вместо названия ключ **маской** (`mask_stream_key`, последние четыре символа, как в логе) и состояние отправки. Полный ключ в консоли не печатается никогда; путь к `keystreams\keys.txt`, где он лежит, печатается один раз — строкой подвала.
5. **УЖЕ СТОЯЛО** — совпавшие эфиры.
6. **НЕ ПУБЛИКОВАЛИ** — пропуски, сгруппированные по причине (уже прошло; до старта меньше N минут; нет канала для языка X), под причиной — строки слотов.

Пустой блок не печатается совсем: нули видны в «Итоге». В блоках 2–5 строки группируются по каналу: шапка группы — название канала, ник и почта аккаунта в скобках, один раз на группу; группа — по нику (`channel.key`), каналы с одним названием не смешиваются; каналы — в порядке `channels.json`, внутри канала — по дате и времени. Строка эфира: дата, время, язык, название целиком (уже обрезано спекой до 100 символов). `--dry-run` — те же блоки, но ОПУБЛИКУЕМ и ИСПРАВИМ («вернём к пакету» во ВНИМАНИЕ), блока КЛЮЧИ СТРИМЕРУ нет — ничего не отправлялось. `--status` — шапка, строки прогресса, итог, ВНИМАНИЕ и УЖЕ СТОЯЛО.

**Отчёт** — сначала то, ради чего открывают: заголовок «# Planer <версия> — отчёт <дата время>», «Итог», Ключ не дошёл до стримера, В форме два ключа на один слот, Не допущено к публикации, Ошибки, Предупреждения, Расхождения с платформой, Создано, Исправлено, Уже запланировано, Перенесён или отменён, Пропущено, Пакеты, Особенности площадки. **Пустой раздел не печатается.** «Не допущено к публикации (N)» (`OutcomeKind.NOT_ADMITTED`, в «Ошибки» не входит, код выхода 1): одним текстом с консолью (`report.not_admitted_text`, `NOT_ADMITTED_LINE`): чего не хватает — что из-за этого не сделано — что делать и что планер сделает сам, например «18-03-2027 20:00 en -> Nick Moss @NickMoss85 — в форме в вопросе «Время стрима ( Stream time )» нет варианта «18.03.2027»: эфир не создан, ключ стримеру не передан. Добавьте вариант в форму — планер создаст эфир на следующем запуске.»; чего не хватает — `report.admission_texts` (их же цитирует `keys.txt`), что делать — `report.admission_actions`, по причине свой текст (`ADMISSION_*`, `ADMISSION_CHANNEL_PROBLEM` / `ADMISSION_CHANNEL_ACTION`); вопрос и значение — отдельные поля (`MissingAnswer.question` / `.value`, `AdmissionReason.question` / `.value`); что не сделано — эфира нет / эфир есть, но не исправлялся / канал не проверялся (`NOT_ADMITTED_CONSEQUENCE_*`, `NOT_ADMITTED_NEXT_*`); полный текст отказа канала — один раз на канал в «Ошибки» (`runner._channel_refusal_outcomes`). «Итог» отчёта — те же строки, что «Итог» консоли (`summary_lines`), плюс «Файл ключей: …».

- «Ключ не дошёл до стримера» — ключ, который должен был уйти в этом запуске, а форма отправку не подтвердила: сразу под «Итогом», с причиной и указанием передать ключ из `keys.txt` вручную; счётчики от раздела не меняются.
- «В форме два ключа на один слот (N)» — сразу после «Ключ не дошёл до стримера»: эфир слота создан заново (прежний удалён или перенесён владельцем), а запись памяти этой пары помнила другой эфир планера с подтверждённым формой ключом. Объект — `PlannedBroadcast.replaced` (`ReplacedBroadcast`: прежний `broadcast_id`, ссылка, подтверждённый ключ), заполняет `PlannedBroadcast.remember_replaced` в `runner._Executor._create` сразу после `take_new_key`, до записи `published` (новая запись заменяет прежнюю); INFO `broadcast_replaced slot_id=… previous_broadcast_id=… previous_stream_key=<маска> broadcast_id=… stream_key=<маска>`; в исход — `PairOutcome.replaced`, строки — `report.two_keys_texts` (`TWO_KEYS_LINE`, ключи маской) и `console._two_keys_lines`. Решения сверки, создание и отправка ключа не меняются; прежнего подтверждения нет — раздела нет.
- «Уже запланировано, совпадает (N)»: если ключ хотя бы одного совпавшего эфира форма подтверждала раньше и повторно он не отправлялся (`report.has_kept_keys` → `RunReport.has_kept_keys`), сразу под заголовком — строка-пояснение `WARNING_KEPT_KEY` (не пункт списка; `_append_section(..., lead=)`). Это поведение планера, а не особенность площадки: в `PLATFORM_NOTE_LINES` и «Особенностях площадки» её нет.
- Предупреждения запуска (обложка, язык, аудитория была «для детей», 18+, настройки видео, перечитывание фактов, сохранённый ответ формы, неисправимый параметр эфира — хотели и на YouTube, несколько эфиров без метки на минуту — со ссылками на всех кандидатов) — и в консоль, и в отчёт. В `PLATFORM_NOTE_LINES` они не кладутся: там только постоянные особенности площадки.
- Особенности площадки — **только в отчёте**, последним разделом (`RunReport.notes`): сначала общие, одна строка на особенность за запуск (живой чат у эфиров YouTube; `PLATFORM_NOTE_LINES`), затем строки по каналам (`RunReport.platform_notes`, `report.build_notice_note_lines`, одна строка на канал и эфир, повтор — одна строка): служебный эфир площадки без времени старта — `NOTE_UNDATED_BROADCAST` («на канале … есть служебный эфир площадки без даты и времени — «…». YouTube заводит такой эфир сам при заходе в панель трансляций канала; планер его со слотами не сверяет и не трогает, в списке трансляций Студии он не виден»). Раздел есть и в отчёте `--status`. **Служебный эфир** — эфир «Начать эфир сейчас», который YouTube заводит сам поверх бессрочного ключа канала; признак — только отсутствие `snippet.scheduledStartTime` (`youtube.py::_broadcast_from_item`: такой эфир в список для сверки не попадает и даёт замечание `PlatformNoticeKind.UNDATED_BROADCAST` → `take_notices`); флаг `isDefaultBroadcast` и видимость в признак не входят — флаг пишется в лог как факт (INFO `broadcast_without_start` с полями `is_default`, `lifecycle`, `privacy`, `bound_stream_id`, `published_at`, отсутствующее — `LOG_MISSING`). Удалить такой эфир можно пробником `app\tools\broadcast_probe.py --remove`, но YouTube заводит его заново при следующем заходе в панель трансляций; планер его не удаляет (инвариант 8). Сырые элементы выгружает `broadcast_probe.py --dump-undated` в `logs\{DD-MM-YYYY}_{HHMMSS}_undated_broadcast_{id}.json`.
- Факты платформы: после действий каждый свой эфир перечитывается один раз (`videos.list(part=snippet,status,contentDetails,liveStreamingDetails)` + поток); в лог — `broadcast_expected` (из пакета) / `broadcast_found` (каким эфир нашёлся в списке до правки; до 5n-B — `broadcast_actual`; у созданного этим запуском эфира найденного нет — строки нет) / `broadcast_facts` (что лежит после действий); в отчёт — только расхождения: поля спеки тем же `BroadcastSpec.diff`, что решает сверку (название, описание — длина и начало, категория, видимость, маркер, автостарт, автостоп, задержка), плюс старт, язык и аудитория. Маркер у эфира, созданного или привязанного в этом же запуске, не сравнивается: перечитывание может ещё не видеть поток (ложное расхождение 14-09-2026). Поле, записанное этим же запуском через `apply_video_settings` (язык, категория, видимость, аудитория), берётся в снимок фактов из ответа `videos.update`, а не из перечитывания: реплика площадки изменение может ещё не видеть (ложное расхождение по языку 15-09-2026 — записали `uk`, `videos.list` через секунду отдал `ru`). Ответ записи несёт `VideoFixes.applied` (`AppliedVideo`), подстановку делает `VideoFixes.apply_to_facts`, вызывает её `runner._Executor._read_facts`. Ответу записи верим, но сверяем с отправленным: вернула площадка не то, что просили, — расхождение настоящее и показывается сразу. Независимое чтение того же поля делает следующий запуск, там гонки уже нет. Расхождение — не ошибка.
- Строки исходов: «дата время язык -> название ник — …», например «эфир создан, ключ передан в форму», «на YouTube отличалось: видимость; исправлено, ключ и ссылка прежние, ключ передан в форму».

**Обрыв и падение** (`main.py::run_cli` → `_run_guarded`): Ctrl+C — WARNING `run_interrupted`, в консоль `RUN_INTERRUPTED`, код 1; любое другое необработанное исключение — `LOGGER.exception("run_crashed …")` (трассировка — в лог), в консоль `RUN_CRASHED` с путём к логу, код 1; `run_finished` пишется в обоих случаях. Перехватов `Exception` в планере два: этот и `main._finish_stats_guarded` — непредвиденный сбой статистики в конце запуска (`to_json`, форматирование, запись `runs`) даёт ERROR `run_stats_crashed` с трассировкой в лог и одну строку `RUN_STATS_CRASHED` в терминал; код выхода прежний, `run_finished` пишется всегда. Известное ограничение: закрытие окна консоли крестиком не ловится — лог обрывается на последней строке.

**Коды выхода:** решение и причины — одно место, `runner.decide_exit` → `RunExit` (`code`, `reasons`: `ExitReasonKind` — ошибки по эфирам, ошибки каналов и файлов планера, ключ не дошёл до стримера, не допущено, пакет не прочитан); консоль и отчёт печатают его строкой «Код выхода …» (`report.exit_text`, `EXIT_REASON_TEXT`), лог — `run_report … exit_code=<n> reason=<вид:число,…|none>`. `0` — всё, что можно, сделано; `1` — есть ошибки (в том числе неподтверждённая отправка ключа, который должен был уйти); `2` — ошибка конфигурации/авторизации, ничего не делалось; `3` — в `bcast\` нет пакетов (к каналам не обращались).

### Статистика запуска

Принцип: мерять всё — время, обращения к YouTube и форме, единицы квоты — и хранить замеры; скорость и расход квоты правятся по статистике, а не на глаз. Замеры поведение не меняют: порядок и состав запросов — прежние (пауза `youtube_pause_seconds` с 5p — 0.5 в поставке, решение принято по этим замерам).

- **Объект** — `app\observability\run_stats.py::RunStats`, один на запуск: создаёт его `main.run_cli` первым делом (сразу после разбора флагов) и передаёт параметром — `build_platform` → `YouTubePlatform(stats=)`, `build_form_sender` → `FormDiscovery(stats=)` и `GoogleFormSender(stats=)`, `runner.run(..., stats=)`; у параметров умолчание — новый объект (тесты не меняются). Часы — `time.monotonic`, в тестах свои. Режим — `RunKind` (`full`, `dry_run`, `status`, `check`, `auth`), версия — `APP_VERSION`.
- **Что копит.** По каждому методу YouTube (имя операции, как в `_execute`; `MethodStats`): попытки (`calls` — каждая попытка), повторы, пустые ответы по id (`notListed`), окончательные отказы, секунды внутри `execute()` (без пауз, `_timed_execute`), единицы квоты. Отдельно — секунды фактического ожидания паузы (`_wait_pause`) и сна перед повторами (`_sleep_before_retry`). Картинки обложек с CDN (`_picture_sha`): скачиваний и секунд. Форма: чтений страницы (GET, `FormDiscovery._timed_get`) и отправок (POST, `GoogleFormSender._timed_post`) — каждая попытка, число и секунды. Этапы (`RunStage`, `stats.stage(...)`, не вкладываются): `start` (конфиги и сверка каналов в `main`), `packages` (пакеты и отбор объектов), `form` (`prepare` и проверка дат), `logins` (входы: ожидание браузера — здесь, чтобы не портить остальные цифры; в `--check` и `--auth` — тоже), `reconcile` (допуск, память, сверка; в `--check` — чтение каналов), `actions` (действия, ключи, `keys.txt`), `report` (итоги, отчёт, чистка); `other` = общее время минус этапы. Время объекта в этапе действий — по итоговому решению (`Decision.value`: число, сумма, максимум; `ObjectTimes`). Итоги по объектам — `build_totals` (`RunStats.record_totals`, `runner._write_outcome`), если отчёт был. Общее время, код выхода — `RunStats.finish`.
- **Цены квоты** — `platforms\youtube.py::QUOTA_UNITS` рядом с именами операций (`*_OPERATION`), единственный источник: `channels.list`, `liveBroadcasts.list`, `liveStreams.list`, `videos.list` — 1; `liveBroadcasts.insert`, `.update`, `.bind`, `liveStreams.insert`, `.update` — 1; `videos.update`, `thumbnails.set` — 50. Цены — по факту Google Cloud Console («Queries per day») за 20-09-2026 и 21-09-2026 (задача 5p): 21-09 Console показала 1 025 ед. при двух запусках (502 чтения по 1 + 23 записи трансляций по 1 + 10 записей по 50), таблица с ценой 50 за все записи насчитала 2 152; 20-09 — около 3 950 против ≈ 10 400. Документация Google даёт 50 за все записи — считаем по факту. Какая из четырёх записей создания эфира стоит 50, по этим дням не различить (число вызовов одинаковое) — отнесено к `thumbnails.set`; уточнить по дню, где обложек больше или меньше, чем созданий. Строки `runs`, записанные до 5p, не пересчитаны: в `stats_json` есть вызовы по методам, пересчитать можно потом. Начисляются за каждую попытку по цене метода — оценка сверху (Google берёт минимум 1 ед. и за отказ); владельцу — со знаком «≈». Операция без цены — 0 ед. и одна строка WARNING `quota_units_unknown operation=…` за запуск; тест проверяет, что у каждой операции, которую площадка передаёт в `_execute`, цена есть.
- **Квотные сутки YouTube** начинаются в полночь по Тихоокеанскому времени: `core\dates.py::youtube_quota_day` (дата суток момента) и `youtube_quota_day_start` (их начало, UTC); на stdlib, по правилу США (UTC−7 со второго воскресенья марта 02:00 до первого воскресенья ноября 02:00 местного, иначе UTC−8), без tzdata. По Киеву сутки обычно начинаются в 10:00.
- **Хранение** — таблица `runs` в `secrets\planer.sqlite3` (`app\records\run_record.py`: `RunRecord`, `RunStore`), одна строка на запуск: `run_id` — отметка из имени файла лога (`logging_setup.run_id_from_log`, например `21-09-2026_094926`), `started_utc` (ISO), `quota_day` (`DD-MM-YYYY`, квотные сутки момента конца запуска), `quota_units`, `elapsed_sec`, `exit_code`, `mode`, `version`, `stats_json` — всё остальное (`RunStats.to_json`: методы, этапы, объекты, форма, картинки, итоги; моменты — `DD-MM-YYYY HH:MM:SS` по часам машины). Пишет `main._finish_stats` отдельным коротким соединением в конце запуска, в любом режиме и на любом пути: `--dry-run`, `--status`, `--check`, `--auth`, код 2, Ctrl+C, падение. Это замер, а не память о слотах: таблица `slots` в read_only-режимах не трогается. Сбой записи — WARNING `run_stats_write_failed`, в терминале «нет данных»; код выхода не меняется, запуск не падает. Строки `runs` по `keep_days` не чистятся — история для анализа. Сумма квоты за текущие квотные сутки — по строкам `runs` этого компьютера, включая строку этого запуска. **Квота проекта Google общая** для всех владельцев с одним `client_secret.json` (и для броадкастера оператора, пока проект общий), а планер видит только свой компьютер: сумма — нижняя граница расхода проекта.
- **Терминал** — последними строками любого запуска, после итогового вывода и пустой строки (`main._finish_stats`): «Время работы: 9 мин 43 сек» (дольше часа — «1 ч 05 мин 12 сек»; `RUN_ELAPSED`, `DURATION_MINUTES`, `DURATION_HOURS`), затем «YouTube: обращений 265, квота ≈ 230 ед.; за квотные сутки на этом компьютере (с 10:00) ≈ 10 370 ед.» (`RUN_YOUTUBE`; начало суток — по часам машины; строка не записалась — `RUN_YOUTUBE_NO_DAY_DATA`); обращений к YouTube не было — строки YouTube нет.
- **Лог** — перед `run_finished` (`RunStats.log_summary`): `run_stats elapsed_sec=… youtube_calls=… youtube_units=… quota_day=… quota_day_units=… request_sec=… pause_sec=… retry_sleep_sec=… pictures=… picture_sec=… form_reads=… form_posts=… form_sec=…`, по строке `run_stats_method` на метод, `run_stats_stage` на этап (и `other`), `run_stats_objects` на решение; секунды — с одной цифрой после точки. `run_finished exit_code=… elapsed_sec=…`. Отчёт в `logs\` не меняется.

### Чистка старья

Единственное место, где планер удаляет файлы: на каждом запуске, кроме `--dry-run`, из `bcast\` и `logs\` удаляются файлы старше `keep_days`. Вложенные папки и `keystreams\`, `secrets\` не трогаются. В полном запуске из памяти планера удаляются записи слотов, начавшихся раньше «сейчас − `keep_days`» (`RecordStore.delete_started_before`, INFO `records_cleaned removed=<n>`). Чистка — до записи отчёта, чтобы свой отчёт под неё не попал.

## Алгоритм

### Сбор слотов из `bcast\`

1. Все `*.bcast` из `bcast\`, без подпапок. Битый архив/манифест — «пакет повреждён», файл не трогается.
2. Пакеты читаются от старого `generated_at` к новому; один `slot_id` в двух пакетах — побеждает более новый. Слот получает форму своего пакета (`Slot.form`).
3. Слоты с `start <= сейчас` выбрасываются. Пакет, у которого все слоты в прошлом, — строка в отчёте.
4. Пакеты остаются на месте; разбирает папку владелец (или чистка по `keep_days`).
5. Пакетов нет — код 3, вход в Google не начинается.

### Отбор слотов под каналы

- `start - сейчас < min_lead_minutes` → объект с признаком **too_late**: сверка только на чтение (опознать эфир, взять ключ и ссылку); не создаёт, не исправляет, не привязывает поток, не трогает настройки, в форму не шлёт; в отчёте — «пропущено», ключ — в `keys.txt`.
- Язык слота не входит ни в один `channels[].languages` → «нет канала для языка», пропуск.
- Иначе — объект на **каждый** канал с этим языком (два канала на язык → два эфира).
- Слоты сливаются по `slot_id` **до** размножения по каналам.

Слои объекта: из пакета (слот, пакет-источник, канал, ожидаемая спека); с площадки (найденный эфир, поток, фактическая спека); результат (`broadcast_id`, ссылка, `stream_url`, ключ, «ключ новый», статус формы этого запуска, ошибка).

### Допуск к публикации

После фазы входов, до сверки (`runner._admit_all`), по каждому объекту: объект канала — `ChannelLogins.channel(config)` (`ChannelBook.channel`), объект формы — `FormSender.form_for(spec)` (`KeyForm`; не прочиталась — `FormError`, второго чтения нет; тестовые отправители — `None`, форма не проверяется). Решает сам объект — `PlannedBroadcast.admit(channel_object, key_form, form_failure)`, единственное место правила; причины `AdmissionReason` (`kind`, `code`, `field`, `text`) по порядку:
1. `CHANNEL` — канал не `READY` (код — статус канала);
2. `FORM_UNREADABLE` — форма не прочиталась (код и сообщение `FormError`);
3. `FORM_FIELD` — каждое незаполненное поле ответа без ключа и адреса (`KeyForm.answers(stream_key=None, stream_url=None)` → `FormAnswers.missing`: `missingOption` — в форме нет варианта даты, языка, площадки; `requiredMissing` — обязательный вопрос без ответа). Ключ и адрес потока «ожидаются» (`pending`) — не причина. Времени в форме нет — только дата.
Причины есть — `Decision.NOT_ADMITTED`. Объект too_late допуск не проходит: поля заполняются, причин нет. Лог: INFO `slot_admitted slot_id=… channel="…" handle=… form_url=…`; WARNING `slot_not_admitted … reasons=<kind:code:field,…>` и строка `slot_not_admitted_reason … kind=… code=… field=… text="…"` на причину. Не допущенный объект: на YouTube ничего не создаётся и не исправляется, настройки видео и факты не читаются, в форму ничего не уходит; ключ его эфира, если эфир на канале есть, — в `keys.txt`; код выхода 1.

### Сверка с платформой

1. По каждому каналу с объектами: вход и проверка канала (ник → id → название) — уже в фазе входов, к сверке канал подтверждён или его объекты — ошибка; затем `liveBroadcasts.list(broadcastStatus=upcoming, part=snippet,contentDetails,status)` с пагинацией, без `mine` (иначе 400 `incompatibleParameters`, проверено 12-09-2026). Канал не `READY` (объекты не допущены по каналу) — к площадке по нему не обращаемся вовсе (ни `list_upcoming`, ни `get_stream`), INFO `channel_skipped_not_ready`, объекты остаются `NOT_ADMITTED`. Недоступный подтверждённый канал — ошибка его допущенных объектов. Объект, не допущенный по форме, на подтверждённом канале — только опознание эфира и ключ со ссылкой (как too_late): ничего не исправляется, AMBIGUOUS не ставится, решение остаётся `NOT_ADMITTED`.
2. Совпадение — минута старта в UTC. Несколько эфиров на минуту — различает маркер `slot_id` в названии привязанного потока (`liveStreams.list(id=boundStreamId)`, кеш по каналу и потоку). Маркер — это имя ключа потока в Студии (Создать -> Управление ключами трансляции), зрителям он не виден; у ключа есть и описание, которое планер заполняет: канал, дата и время слота, язык, когда записано (`messages_ru.STREAM_DESCRIPTION`). Эфир без маркера при единственном кандидате — опознан и усыновлён (метка — исправимое поле), при нескольких — AMBIGUOUS: планер не выбирает и не удаляет, но пишет в лог, в «внимание:» и в отчёт дату, время, язык, канал и ссылки на всех кандидатов. Маркер другого слота на той же минуте — мимо, независимо от того, сколько языков у канала: у многоязычного канала эфиры uk и ru в одну минуту опознаются каждый своим маркером. Известные слоты для сирот — будущие и прошедшие (`scan.slot_map` и `scan.past_slots`, в `Reconciler.reconcile` — `known_slots`: `slot_id` → момент старта): эфир прошедшего слота на своей минуте, который ещё не начался, — в «Пропущено … уже прошло», не в «Перенесён или отменён?» (прогон 17-09-2026 18:01, Maria Kamenskay 17-09-2026 18:00 uk). Эфир с меткой известного слота на другой минуте — **перенесён** (время менял владелец в Студии; прогон 21-09-2026 09:49, Osvald.X 24-09-2026 19:00 ru): планер его не трогает и не возвращает, слот получает новый эфир (CREATE), а перенесённый идёт в тот же список сирот (`OrphanBroadcast.kind` / `OrphanLine.kind` = `OrphanKind.MOVED`, `OrphanLine.actual_start` — `DD-MM-YYYY HH:MM` местного времени; INFO `broadcast_moved`) и в «Перенесён или отменён?» своей строкой `ORPHAN_MOVED_LINE` («… — стоит на <время>: время эфира менял владелец, планер его не трогает»). Эфиры, уже показанные в других разделах (опознанные объектами, кандидаты AMBIGUOUS), сиротами не считаются.
3. Решения:

| На YouTube | Действие |
|---|---|
| эфира нет | создать; новый ключ в форму |
| есть, с нашей меткой, все исправимые поля совпадают | копия; ключ и ссылка с площадки; в форму — только если память не хранит подтверждения этой тройки |
| есть, исправимое поле отличается (в том числе обложки нет) | исправить на месте только нужными вызовами (`FIX_CALLS`); ключ прежний; в форму — если ответы или форма другие, чем в подтверждении |
| есть, без метки планера (ручной), единственный на минуту | усыновить: `set_stream_marker` + прочие исправления; ключ прежний; подтверждения нет — уходит в форму |
| есть, отличается только неисправимое поле | решение не меняется; лог, «внимание:», строка расхождения в отчёте |
| есть, привязанного потока нет | создать поток с маркером и привязать; новый ключ в форму |
| эфир на время, которого нет ни в одном слоте, без маркера | не трогать, в отчёт не попадает |
| эфир с маркером планера, чьего слота нет | не удалять; в отчёт «Перенесён или отменён?» |
| эфир с маркером известного слота на другой минуте (перенёс владелец) | не трогать; слоту — новый эфир; в отчёт «Перенесён или отменён?» строкой «стоит на …»; была подтверждённая запись — «В форме два ключа на один слот» |

Сравниваются две спеки, построенные по одним правилам: название — `strip()`, описание — CRLF/CR → LF, хвостовые пробелы и края сняты, затем **обрезка по лимитам площадки для обеих сторон** (иначе длинное название правилось бы бесконечно). Сравниваются все диктуемые поля (`BroadcastSpec` — единственное место, задающее «одинаковый»; спека из слота берёт видимость из канала, категорию и автостарт из `planer.json`, автостоп и задержку — от площадки). Время старта не сравнивается: по нему эфир опознают. Поле, которое площадка не вернула (`None`), сравнивать не с чем: так список эфиров YouTube ведёт себя с категорией — её расхождение видно у ресурса `videos` в `apply_video_settings` и тоже считается исправлением (UPDATE, ключ в форму).

Поля делятся в одном месте — `plan.py`:
- **исправляем** (`FIXABLE_FIELDS`) — название, описание, категория, видимость, маркер, обложка: расхождение даёт UPDATE, а UPDATE — **только вызовы, которых требуют разошедшиеся поля** (`runner._Executor._fix` / `_resend`). Вызов каждого исправимого поля задан там же, где поле объявлено, — `plan.py::FIX_CALLS` (`FixCall`), из него же `FIXABLE_FIELDS`; объект отвечает `PlannedBroadcast.fix_calls` / `fields_fixed_by`: название и описание — `liveBroadcasts.update` (`BROADCAST`; с ними уходят время и категория); метка — `set_stream_marker` (`STREAM`, `liveStreams.update(part=snippet)`, snippet читается и пишется целиком); обложка — `thumbnails.set` (`THUMBNAIL`, `_set_thumbnail`, если `set_thumbnail` и у слота есть превью); видимость и категория — `videos.update` (`VIDEO`, обычный проход настроек видео `apply_video_settings` в `_finish`: видимость, категория, язык, аудитория). Разошлась только обложка — `liveBroadcasts.update` не вызывается (прогон 18-09-2026 14:04: четыре лишние записи по 50 единиц квоты); строка `planer.youtube | broadcast_updated` — только при реальном вызове, `planer.runner | broadcast_updated … fields=` — на каждое исправление. Уйдёт ли ключ — решает `decide_key_delivery` (инвариант 1a). Совпало всё — MATCH, эфир не трогается. Если MATCH превратился в UPDATE у ресурса видео (видимость или категория), других вызовов нет — поля видео уже исправил проход настроек. **Категория сверяется только в полном запуске:** `categoryId` живёт у ресурса `videos`, в ответе `liveBroadcasts.list` его нет, поэтому в спеке с площадки он всегда пуст и сверкой пропускается (строка лога `spec_fields_not_compared`); расхождение ловит только второй проход — `apply_video_settings`, а он в `--dry-run` не выполняется. В `--dry-run` расхождение по категории не видно.
- **обложка** (`ChangedField.THUMBNAIL`, поле спеки `has_own_thumbnail`). Признака «своя обложка» в API нет, поэтому «обложки нет» = картинка эфира (размер `default`, `UpcomingBroadcast.thumbnail_sha` — `base.picture_sha`, 12 hex sha256; скачивается в `list_upcoming` без паузы `youtube_pause_seconds` (CDN, не API), квоту не тратит) совпадает с заглушкой своего канала. Заглушки канала (`reconciler._channel_placeholders`, лог `channel_placeholders`): отпечаток `thumb0=<sha>` из описания потока (`PLACEHOLDER_TOKEN`; планер пишет его при `create_broadcast` по картинке из ответа `liveBroadcasts.insert`, лог `thumbnail_placeholder_captured`; `attach_stream` не пишет, `set_stream_marker` сохраняет) и картинка, одинаковая у двух и более эфиров одного канала (так находятся эфиры, созданные до 5k); одинаковая картинка на разных каналах заглушкой не считается. Из слота — `True`, если `set_thumbnail` и у слота есть превью, иначе `None` (не сверяется); картинка не скачалась — `None`, поле в `spec_fields_not_compared`; в фактах после записи — `None` (картинка может ещё не смениться, сверку делает список следующего запуска). **Память главнее картинки**: `thumbnail_broadcast_id` записи равен id найденного эфира — обложку ему ставил планер, `has_own_thumbnail = True` у фактической спеки (`PlannedBroadcast.apply_recorded_thumbnail`, вызывается в `reconciler._decide` сразу после `BroadcastSpec.from_platform`, до `diff`; INFO `thumbnail_from_memory … broadcast_id=… set_at=…`); записи нет или эфир другой — по картинке. Наблюдение 17-09-2026: картинка эфира после `thumbnails.set` обновляется с задержкой — 4–5 минут не хватило (Паша Экскаватощик и Українка я, обложки 17:36, сверка 17:40 увидела заглушку, повторная загрузка 17:52). В отчёте «было / стало» у обложки — «заглушка канала» / «из пакета», в консоли обложка — в ИСПРАВИЛИ, не во ВНИМАНИЕ. Следствие правила дублей: две одинаковые свои обложки на одном канале тоже читаются как заглушка — такие эфиры переотправляются на каждом запуске.
- **только сообщаем** (`REPORTED_FIELDS`) — автостарт, автостоп, задержка: они в `contentDetails`, а `liveBroadcasts.update` шлёт только `snippet` — `contentDetails` у update требует `monitorStream`. Гонять их через UPDATE значило бы на каждом запуске «исправлять» неисправимое и слать стримеру ключ заново. Проверено 13-09-2026: YouTube возвращает описание байт в байт и код языка как записан (`ru`).

**Итог исправления — по факту** (`PlannedBroadcast.fixed_fields` / `unfixed_fields`, меняются только `mark_fixed` / `mark_unfixed`): `liveBroadcasts.update` прошёл — исправлены поля группы `BROADCAST` (`fields_fixed_by(FixCall.BROADCAST)`); метка поставлена — MARKER; обложка поставлена — THUMBNAIL, не поставлена — THUMBNAIL в `unfixed_fields` (предупреждение `WARNING_STEP_THUMBNAIL` — как раньше); видимость и категория из `_mark_video_fixes` — исправлены. **Пропуск пустой переотправки**: `BroadcastPlatform.thumbnail_refusal(channel)` — отказ `thumbnails.set`, запомненный в этом запуске по каналу или проекту (`YouTubePlatform._refusals`, без сети; `VerifiedPlatform` — канал не READY — `None`); `_Executor._set_thumbnail` спрашивает отказ до вызова: отказ есть — `set_thumbnail` не зовётся, THUMBNAIL в `unfixed_fields`, предупреждение с кодом и текстом отказа; `update_broadcast` зовётся, только если разошлись название или описание (отдельной проверки «только обложка» и строки `broadcast_fix_skipped` больше нет — это следует из `FIX_CALLS`). Следующий запуск пробует загрузку заново (прогон 17-09-2026 18:01: четыре пустых `liveBroadcasts.update` Maria Kamenskay после 429). Наблюдение 17-09-2026: у Maria Kamenskay 11-я загрузка обложки за ~17 часов получила 429 `uploadRateLimitExceeded`, у каналов с 8 загрузками отказов не было; YouTube число не публикует.

Исправление текстов — `liveBroadcasts.update(part=snippet)`: вместе с названием и описанием всегда отправляются `scheduledStartTime` и `categoryId` из спеки; `contentDetails` не включается (потребовал бы `monitorStream`).

### Создание эфира (YouTube)

1. `liveBroadcasts.insert` — `title` (≤100, безопасная обрезка), `description` (≤5000), `scheduledStartTime` = `start` в RFC3339, `privacyStatus` = `channel.privacy`, `selfDeclaredMadeForKids = false`, `enableAutoStart` = `auto_start`, `enableAutoStop = true`, `latencyPreference = "normal"`, `categoryId` = `category_id`.
2. `liveStreams.insert` — `snippet.title = slot_id` (маркер), `snippet.description` — описание ключа (`STREAM_DESCRIPTION`), `cdn` rtmp / variable / variable; ключ `cdn.ingestionInfo.streamName` проверяется `^[a-z0-9]{4}(-[a-z0-9]{4}){3,4}$` — несовпадение = ошибка пары, форма не отправляется. У чужих эфиров ключ неожиданного вида — только предупреждение в лог.
3. `liveBroadcasts.bind`. На каждый эфир — свой поток и свой ключ.
4. `thumbnails.set` — если `set_thumbnail` и у слота есть превью: случайное; при создании и при исправлении эфира, у которого разошлась обложка (обложка — сверяемое поле, пропущенную доставит следующий запуск). Сбой не фатален — предупреждение с текстом причины (`THUMBNAIL_REASON_TEXT`); `uploadRateLimitExceeded` и `forbidden` — остальные обложки канала в этом запуске не ставятся. ≈ 50 единиц квоты.
5. Настройки ресурса `videos` одним проходом: одно `videos.list(part=snippet,status)`, не больше одного `videos.update(part=snippet,status)` — `defaultLanguage` и `defaultAudioLanguage` = язык слота, `categoryId` = `category_id`, `privacyStatus` = видимость канала, `selfDeclaredMadeForKids = false`. Части отправляются **целиком** (частичная затирает `privacyStatus` и `title`). На каждом запуске у каждого своего эфира (создан, привязан, исправлен, подтверждён); у найденного эфира исправленные категория и видимость — это UPDATE и ключ в форму, аудитория — предупреждение; сбой не фатален.
6. Время старта у ресурса `videos` — в `liveStreamingDetails.scheduledStartTime`, не в `snippet`.
7. 18+ (`contentRating.ytRating == ytAgeRestricted`) только читается — предупреждение со ссылкой.
8. `broadcast_url = https://www.youtube.com/watch?v={broadcast_id}` — только через `broadcast_url_for`.

Все обращения к API идут через `YouTubePlatform._execute` — единственная точка паузы, повторов и памяти отказов; вход в браузере оттуда — только для `describe_channel(allow_login=True)` (`api_retry.py` удалён 16-09-2026). Перед каждым запросом API выжидается остаток `youtube_pause_seconds` от конца предыдущего обращения к API (число, можно дробное; картинки i.ytimg.com паузу не ждут и не сдвигают). Поведение отказа — `_error_behavior(операция, HTTP-код, причина)` по таблицам `REASON_BEHAVIORS` / `OPERATION_REASON_BEHAVIORS`; причины нет в таблицах — 5xx и 429 повторяются, прочее нет; сетевой сбой повторяется. RETRY — по `core\retry.py::RetryPolicy` (первое обращение и до 4 повторов, паузы 2–3, 4–5, 8–9, 16–17 с; лог `request_retry` с `delay_sec`); `youtube_pause_seconds` — отдельная вещь, паузы повторов входят в неё; попытки исчерпаны — `transportFailed` для 5xx и сети (живой прогон 13-09-2026 00:33 упал на 503), лимит частоты сохраняет свою причину. **Создающие вызовы не повторяются вслепую** (прогон 18-09-2026 15:29: `request_retry operation=liveBroadcasts.insert … reason=transportFailed` у Oktavian.X — задвоения не случилось случайно): `liveBroadcasts.insert` и `liveStreams.insert` — `CREATING_OPERATIONS` рядом с именами операций в `platforms\youtube.py`; отказ с неизвестным исходом (`_is_unknown_outcome`: обрыв связи `transportFailed` или любой 5xx) у них — CALL, решает то же `_error_behavior`; ошибка — `transportFailed`, строка `youtube_refused` прежняя, объект — ошибка пары (ВНИМАНИЕ и «Ошибки» отчёта); эфир без потока или без эфира доделает следующий запуск (шаги 1–3 ниже). Явный отказ сервера (лимиты частоты `rateLimitExceeded`, `userRateLimitExceeded`, `userRequestsExceedRateLimit`, 429) — объект точно не создан — повторяется как у всех. Сетевой сбой — такая же причина таблицы (`ERROR_TRANSPORT` → RETRY в `REASON_BEHAVIORS`), читающие вызовы повторяются, как раньше. CALL — не повторять, следующий такой же вызов идёт как обычно (`invalidImage`, `videoNotFound`, `forbidden` вне обложки…). OPERATION — эта операция на этом канале до конца запуска не вызывается (`uploadRateLimitExceeded`, `liveStreamingNotEnabled`, `(thumbnails.set, forbidden)`…). CHANNEL — канал до конца запуска не запрашивается (`authError`, `insufficientPermissions`, закрыт/заблокирован, отказ входа `authFailed` — браузер повторно не открывается). PROJECT — к YouTube до конца запуска не обращаемся (`quotaExceeded`). Запомненный отказ поднимается без сети и без паузы (лог `request_skipped`); окончательный отказ — WARNING `youtube_refused`. **Пустой ответ чтения по id** (прогон 20-09-2026 23:37, «Українка я» @TheImpact-r2b, ouOV1qoprBI: `videos.list` через 2 с после успешного `videos.update` вернул пустой `items`, следующий запуск прочитал эфир целиком) — задержка площадки после записи, а не «объекта нет»: все чтения по id (`read_facts`, `_video_item`, `_broadcast_of`, `get_stream`, `set_stream_marker`) идут через `YouTubePlatform._read_by_id`, пустой `items` повторяется по той же `RETRY_POLICY` с кодом планера `ERROR_NOT_LISTED` = `notListed` (RETRY в `REASON_BEHAVIORS`; пауза и `request_retry … reason=notListed` — `_sleep_before_retry`); после всех попыток — WARNING `read_not_listed operation=… object_id=… attempts=…` и пустой результат: `read_facts`, `_video_item`, `set_stream_marker` поднимают `PlatformError(notListed)` (в сообщении метод, id и число попыток; текст владельцу — `YOUTUBE_REASON_TEXT["notListed"]`), `get_stream` и `_broadcast_of` возвращают `None`. Списки по статусу (`list_upcoming`) пустой ответ не повторяют — он нормален. `channelNotFound` — только у `channels.list(mine=true)` в `describe_channel`. Причины с текстом для владельца — `messages_ru.YOUTUBE_REASON_TEXT` и `THUMBNAIL_REASON_TEXT` (для шага обложки главнее); неизвестная причина — код и сообщение Google. Оборвалось посередине шагов 1–3 — следующий запуск увидит эфир без потока и доделает.

### Отправка в форму

1. **URL** — только `form.url` слота. **Формы читаются в начале запуска** (`FormSender.prepare`): `runner._run_bcast` сразу после `scan_bcast` (полный запуск и `--dry-run`; в `--status` форм нет), до входов и до обращений к YouTube, `GET viewform` — один раз на уникальный URL. Прочитанная форма — объект `form\key_form.py::KeyForm` (`url`, `spec`, `structure`, `questions`: поле пакета → вопрос формы или `None`); INFO `form_ready url=… questions=… pages=… dates=<даты формы в date_format> languages=<коды языков пакета с вариантом> stream_urls=<n>`. Не прочиталась — WARNING `form_unreadable url=… code=…`, отправка по этой форме возвращает ту же ошибку. `GoogleFormSender.send` берёт готовую `KeyForm`, второго чтения нет. GET повторяется по `RetryPolicy` на сетевые сбои и 5xx (лог `form_get_retry`), на 4xx — нет.
   **Предстартовая проверка дат** (`runner._check_form_dates`, задача 5n-D): сразу после `build_planned` и строго до фазы входов (`_log_in`) — формы уже прочитаны, ни браузер, ни YouTube ещё не тронуты; сети не нужно. Берутся объекты, которые запуск собирается публиковать (не too_late), группируются по `form.url` (несколько пакетов с одной ссылкой — одна форма); на форму — одна проверка `KeyForm.date_coverage(starts)` → `DateCoverage` (`form_url`, `question_title`, `is_checkable`, `wanted`, `missing`, `missing_dates`, `accepted_count`; `is_complete`, `missing_text` — даты `DD-MM-YYYY`). Даты сопоставляются тем же кодом, что при отправке (`KeyForm._date_option`): что проверка назвала недостающим, то при допуске даст `missingOption`, и наоборот. Вопрос даты — текст: `is_checkable` False, принимается любая. Форма не прочиталась (`FormError`) или отправитель форму не проверяет (`None`) — проверки нет. Лог — INFO `form_dates_checked url=… question="…" wanted=<n> missing=<n> dates=<недостающие даты в формате формы | ->` (вопроса даты нет вовсе — DEBUG `form_dates_not_checked`, строки прогресса нет); строка прогресса `form_dates_checked`; непокрытые даты — одна строка `WARNING_FORM_DATES_MISSING` на форму в ВНИМАНИЕ консоли и в «Предупреждения» отчёта (в списке предупреждений запуска — после `channel_warnings`, перед строками памяти). Механизм недопуска, решения, счётчики и код выхода не меняются: объект без варианта даты по-прежнему не допущен сам (`FORM_FIELD` / `missingOption`), остальная работа идёт как обычно; в `--status` проверки нет.
2. **Структура** — из скрипта `FB_PUBLIC_LOAD_DATA_`: элементы `payload[1][1]`, разделы разделяются разрывами (тип 8), раздел 0 — до первого разрыва. Переход у варианта (`option[2]`) — **идентификатор** целевого раздела (`item[0]` разрыва), переводится в номер через карту; отрицательные значения — служебные коды, не переходы. Не прочиталось — форма не отправляется, HTML сохраняется в `logs\{DD-MM-YYYY}_{HHMMSS}_form_page_{хеш}.html`.
3. **Значения** — методы `KeyForm.answers(language, start, account_name, stream_key, stream_url)` → `FormAnswers` (ответы, посещаемые разделы, незаполненные поля `MissingAnswer` с кодом `missingOption` / `requiredMissing` и текстом «вопрос: значение», ожидаемые поля). Ключа и адреса потока ещё нет (`None`) — поля «ожидаются после публикации», это не ошибка. Времени в форме нет — только дата. Текстовые — как есть (`account_name`, `stream_key`); радио — только текст варианта: `language` → `form.values.language[язык]`, `platform` → `form.values.platform["youtube"]`, `date` → вариант, начинающийся с даты в `form.date_format`, `stream_url` → вариант, равный `ingestionAddress` после нормализации (нижний регистр, без хвостового слэша). Нет варианта — ошибка пары, повтора нет. Перед отправкой у каждого обязательного вопроса пройденных разделов есть значение.
4. **POST `formResponse`** конечного URL: `entry.*` пройденных разделов, `fvv=1`, `fbzx`, `pageHistory` — **номера разделов с нуля** (для тренировочной формы `0,1`; идентификатор даёт 400), номер вне диапазона отбрасывается. `Accept-Language: en` и `hl=en`. `requests`, таймаут 30 с, повторы на сеть и 5xx — по `RetryPolicy` (лог `form_post_retry`), на 4xx повтора нет. Тела запросов и тексты отказов — прежние.
5. **Подтверждение** — структурное, от языка не зависит (`form/submitter.py::read_confirmation`): HTTP 200, в теле есть `FB_PUBLIC_LOAD_DATA_`, нет ни одного `entry.<цифры>`, нет `fbzx`. Текстовые маркеры — только сигнал в лог. Не подтверждено — тело в `logs\{DD-MM-YYYY}_{HHMMSS}_form_response_{хеш}.html`, путь в отчёт, код выхода 1.

**Память планера** (`app\records\`). `SlotRecord` — ключ (`slot_id`, `youtube_channel_id` — id канала из `Channel.info`; без объекта канала, только тесты, — ключ канала), `slot_start_utc`, `stage` (`SlotStage`: `admitted` — допущен и записан до действий, `published` — эфир и ключ взяты с площадки, `key_confirmed` — форма подтвердила текущий ключ; стадия не откатывается для того же ключа), `updated_at`, `results` (`RecordResults`: `broadcast_id`, `broadcast_url`, `stream_id`, `stream_url`, `stream_key`, `published_at`, `confirmed_stream_key`, `confirmed_form_url`, `confirmed_answers` — `ConfirmedAnswer(entry_id, title, value)`, `confirmed_at`, `is_bootstrap`, `thumbnail_broadcast_id` и `thumbnail_set_at` — какому эфиру и когда планер поставил обложку) и `snapshot` (`RecordSnapshot` для людей: дата, время, язык, канал, ник, заголовок, форма, решение, причины недопуска, `last_error`, предупреждения — обратно не читается). JSON записи — `{"schema": 1, "snapshot": …, "results": …}`; чтение терпимое: неизвестные ключи игнорируются, отсутствующие — `None`, другой `schema` не ошибка. `RecordStore` (stdlib `sqlite3`; путь — `PlanerPaths.records_file`): таблицы `slots` (PRIMARY KEY (`slot_id`, `youtube_channel_id`), индекс по `slot_start_utc`) и `meta` (`schema_version`, `created_utc` — когда появилась память, ISO-8601 UTC); `open(path, read_only=, now_local=)` → `is_new` (файла не было), `created_utc` (у новой базы — момент открытия; у базы без этой строки — пишется при первом открытии на запись: в `slots` есть записи — самый ранний `updated_at` (местное `DD-MM-YYYY HH:MM` → UTC через `core\dates.py::parse_local_datetime_text_utc`), база пустая — текущее время; INFO `records_created_utc_initialized value=… source=min_updated_at|now`; read_only без строки — то же правило в памяти, без файла — текущее время. Прогон 18-09-2026: `created_utc` = 12:25 UTC первого прогона, а запись Maria Kamenskay от 17-09 16:39 старше — отметка «сейчас» сдвигала границу `bootstrap_confirmation` вперёд); `find`, `save` (upsert одной транзакцией, INFO `record_saved`), `delete_started_before`, `take_warnings`, `close`. Не открылась (`sqlite3.DatabaseError`) — переименовать, создать новую, WARNING `records_broken`, строка `WARNING_RECORDS_BROKEN`; в read_only (`--dry-run`, `--status`) — без записей, `WARNING_RECORDS_BROKEN_READ_ONLY`, на диск ничего не пишется (файла нет — пустая база в памяти). **Исключение** — строка статистики запуска в таблице `runs` (раздел «Статистика запуска»): она пишется в любом режиме отдельным соединением, таблицу `slots` не трогает. `schema_version` в `meta` — `2` (`record_store.SCHEMA_VERSION`, с 5o-B: появилась таблица `runs`); у существующих баз поднимается при открытии на запись и при записи строки `runs` (`SCHEMA_VERSION_SQL`), строки `slots` не меняются. Сбой записи — WARNING `records_write_failed`, одна строка `WARNING_RECORDS_WRITE_FAILED` за запуск, объект работает дальше. Ключи в памяти — полностью, в логах — маской. **Время событий** — из часов запуска (`run(..., clock=)`, по умолчанию `runner.utc_now`; тесты передают свои) в момент события, а не время старта: `published_at` — момент записи `published` сразу после действий по объекту (новый ключ; тот же ключ сохраняет прежний момент), `confirmed_at` и `form_sent_at` — когда форма подтвердила (`_Executor._send_key` возвращает этот момент), `updated_at` — когда запись пишется; формат `DD-MM-YYYY HH:MM` местного времени; `keys.txt` («отправлен в форму …», «передан в форму …») показывает эти моменты. Время старта (`now_utc`) — для отчёта, имён файлов, отбора too_late и чистки. **Запись — только при изменении**: `PlannedBroadcast.record_to_save` сравнивает новую запись с последней записанной (`PlannedBroadcast.record` — прочитанная из памяти или записанная этим запуском, `remember_record`) через `SlotRecord.has_same_content` (всё, кроме `updated_at`; у прочитанной из базы — JSON как лежит, `SlotRecord.stored_json`); совпала — записи нет, DEBUG `record_unchanged slot_id=… youtube_channel_id=… stage=…`. Снимок для людей входит в сравнение: сменилось решение (создан → совпал) — одна запись, дальше запуски без изменений в память не пишут. `record_saved … stage=<легла в базу>` и ` requested=<просил код>`, если они разные (`RecordStore.save(record, requested=)`); правило «стадия не откатывается для того же ключа» — прежнее. `main._run_pipeline` открывает память перед `run(..., store=)` и закрывает в `finally` (обрыв и падение тоже); без `store` (тесты) — пустая память первого запуска. В `runner`: после `_admit_all` — `_load_records` (только каналы READY), после сверки — `_bootstrap_records` (каждый запуск; N > 0 — строка `WARNING_RECORDS_CREATED` «N эфиров с меткой планера, созданных до появления памяти планера, записаны как уже переданные стримеру» во ВНИМАНИЕ и в «Предупреждения»), в полном запуске — запись `admitted` перед действиями, в `--dry-run` — `decide_key_delivery` по памяти без отправок (у совпавшего эфира в отчёте — «ключ будет передан в форму», `FormState.PLANNED`); в `--status` строка «форма» берётся из памяти. **Факт обложки**: `set_thumbnail` прошёл (создание или исправление) — `PlannedBroadcast.remember_thumbnail(broadcast_id, now)` (время события из часов); в записи `thumbnail_broadcast_id` / `thumbnail_set_at` переносятся, пока эфир тот же, у другого эфира (удалён и создан заново) — сбрасываются (`PlannedBroadcast._thumbnail_results`). Ключ, отправленный для совпавшего эфира, виден в блоке КЛЮЧИ консоли и в отчёте у его исхода («…; ключ передан в форму»); счётчики «Итога» не меняются.

## Режимы запуска

`planer.exe` через `planer.bat` в корне программы; окно не закрывается до Enter. `planer.bat` один на оба случая: рядом `planer.exe` — запускает его, иначе — `python -m app.main` из `.venv_planers`.

- без аргументов — полный цикл;
- `--dry-run` — читает пакеты и сверяется с YouTube (только чтение), ничего не создаёт и в форму не шлёт; `keys.txt` не меняется;
- `--check` — по каждому каналу `channels.json` тем же путём, что запуск: сверка каналов при старте, вход при необходимости, проверка канала (ник, id, название), канал за токеном и его ник, язык канала на YouTube (справочно), языки из конфига, число запланированных эфиров; ноль — не ошибка;
- `--auth <handle>` или `--auth all` — принудительный вход (ник — с «@» или без, регистр не важен); неизвестный ник — код 1 и список ников с названиями;
- `--status` — сверка эфиров с маркером планера + `keys.txt` и отчёт без пакетов;
- `--debug` — подробный лог; `--version` — «Planer <APP_VERSION>», код 0, ничего не читает.

## Сборка и поставка

`build_release.bat` и `build_local.bat` различаются только тем, кладутся ли в сборку данные разработчика (`IncludeSecrets` в `planer.iss`): вся папка `secrets\` (`client_secret.json`, `channels.json`, `planer.json` и токены каналов `<handle>.token.json`, а с ними и `channels_passport.json`). Её кладёт в `dist\planer\` подпрограмма `:copy_local_data` скрипта `build_release.bat`, оттуда же их берёт Inno Setup: источник один. Память планера `secrets\planer.sqlite3*` в сборку не попадает (после копирования удаляется из `dist\planer\secrets\`): у каждой установки своя память, чужая дала бы ложные подтверждения. Собранная программа делает прогон сразу — без OAuth и ручного копирования; такой инсталлятор не публикуется. Нет `secrets\client_secret.json` или `secrets\channels.json` — local-сборка не начинается (код 1). ## Приоритет ООП

- Данные живут в объектах: Форма, Канал, Слот. Функции заполняют, читают и сравнивают поля объекта; своих данных у них нет.
- Изменилась форма, канал или площадка — меняется структура объекта в одном месте, а не цепочка функций.
- Объект с незаполненными полями не выбрасывается: причина — подробно в лог, кратко в терминал; дальше по конвейеру он не допускается.
- Новая проверка = новое поле объекта и правило в самом объекте, а не новая функция по месту использования.
- Правило, которое переводит значение одного объекта в значение другого (слот → ответ формы, ответ YouTube → канал), — метод объекта-владельца правила.
- Модуль-функция вне объекта допустима только как чистое преобразование без знания о предметных объектах; иначе — строкой-обоснованием в отчёте задачи.
- В отчёте каждой задачи — какие объекты и какие их поля добавлены или изменены.

## Стандарты кода

- `from __future__ import annotations` в каждом файле; аннотации `X | None`, lowercase generics; явные типы возвращаемых значений и переменных.
- Имена английские: функции `verb_noun`, булевы `is_`/`has_`/`should_`. Папки во множественном числе, файлы в единственном, первое слово имени файла = домен папки.
- Функции ~30 строк, одна ответственность, guard clauses. Классы вместо функций с длинными списками аргументов. Явная обработка ошибок, без «голых» `except`.
- Никакого хардкода: константы — в конфиг или enum; единый источник истины для каждой константы.
- Повторы сетевых обращений — только по `app\core\retry.py::RetryPolicy` (4 повтора после первого обращения, пауза `2 * 2^(n-1)` с плюс случайная добавка до 1 с, потолок 32 с; `rng` передаётся параметром, в тестах — фиксированный). Что повторять, решает вызывающий; своих констант повторов в модулях нет.
- Иерархические имена логгеров под `"planer"` (`"planer.youtube"`, `"planer.form"`); структурированные сообщения `key=value`, имя канала — в кавычках (`channel="Osvald.X"`).
- Все тексты для владельца (консоль, отчёт, `keys.txt`) — только в `app/ui/messages_ru.py`. В коде — английские идентификаторы сообщений.
- Тесты `pytest` в `app/tests/`, тест-файл = `test_<модуль>.py`. Тесты гоняют реальный production-путь (JSON-конфиги во временном корне), а не переписывают логику inline. Платформа и `requests` подменяются фейками. Обязательное покрытие: чтение пакета; сбор и отбор слотов с подменённым «сейчас»; сверка на фейковой платформе (нет / совпадает / отличается / удалён / два на минуту); `keys.txt` и отчёт по фиксированному состоянию; разбор формы на сохранённом HTML; сопоставление значений (дата есть / нет, `stream_url` с другим регистром и слэшем); регулярка ключа (5 и 4 группы — ок, 3 группы и заглавные — ошибка); submitter с подменённым `requests`.

## Как работать с задачами

- Ветка — `feature/planers`. После сессии Claude Code: `git checkout feature/planers` (Code переключает ветки). Коммиты без trailer `Co-Authored-By`.
- Каждая задача приходит со SCOPE LOCK и списком DO NOT TOUCH. Границы — буквально. Файлы вне области — не трогать, даже если «заодно».
- Все технические вопросы агент решает сам, до конца: символ не найден — ищет фактический эквивалент grep'ом; тест падает — разбирается и чинит в своей области; неясен вызов — читает код и выбирает решение, совместимое с текущим. Наверх выносятся только три вещи: (а) нужно изменить контракт из этого файла; (б) нужно править файл из DO NOT TOUCH; (в) не решается ни одним из испробованных способов — тогда в отчёте перечень попыток. Каждое самостоятельное решение — строкой в отчёте.
- Перед правкой — `grep` по текущему коду на точные имена символов; не писать по памяти (stale-coordinate rule).
- Перед правкой назвать объект и поля, которые меняются; решение "добавить функцию рядом" вместо поля/метода объекта — только с обоснованием в отчёте.
- Не хардкодить число тестов в отчётах; формулировка — «новых падений относительно baseline нет».
- В конце каждой задачи — отчёт об изменённых файлах: каждый файл и что в нём изменилось.
- Все правки — кода, конфигов и документов (CLAUDE.md, README) — делает агент по промту. Артур ставит задачи, контролирует и проверяет; руками ничего не правит.
