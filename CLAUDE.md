## Что это

Планер — локальная Windows-программа у владельца YouTube-канала, машина №2 в пайплайне broadcaster → **planer** → стример. Берёт пакет `*.bcast` от броадкастера, сверяет его с эфирами, уже запланированными на каналах владельца, создаёт недостающие эфиры (и исправляет те, у которых изменились название/описание), получает ключи потока, пишет их в `keystreams\keys.txt` и отправляет в Google-форму ключей, в конце — отчёт. Подробно: ТЗ §1–4.

Площадки v1 — только YouTube. Facebook — этап 6. Rumble — нет.

## Инварианты — не нарушать без явного согласования с Артуром

0. **Рабочая единица — объект запланированного эфира** (`app\pipeline\plan.py`): один объект = один эфир одного слота на одном канале. Из пакета — слот, канал и спека; со сверки — найденный эфир и его спека; дальше — результаты. `state\registry.json` — запись о сделанном: конвейер его не читает ни для одного решения, битый файл только останавливает запуск (ТЗ §5.4, §7.2).
1. **Истина об эфирах — на YouTube; ключ потока и ссылка на эфир читаются только с площадки, никогда из журнала.** Перед любым созданием — сверка `liveBroadcasts.list(broadcastStatus=upcoming)` (без `mine` — фильтры взаимоисключающие); совпадение по минуте старта (UTC) + маркер `slot_id` в `liveStreams.snippet.title`. Эфира нет — создание, что бы ни помнил журнал; решения «создать заново» нет. Слот внутри `min_lead_minutes` сверяется только на чтение, ради ключа (ТЗ §5.4, §7.2, §7.3).
1a. **В форму уходит только новый ключ** — полученный в этом запуске при создании эфира или привязке потока. Совпавший или исправленный эфир с прежним ключом в форму не отправляется никогда, даже если прошлая отправка не подтвердилась: повтор задвоил бы ключ у стримера (ТЗ §7.5).
2. **Google-форма — единственный канал передачи ключей стримеру.** Никаких обходных путей. URL формы, названия вопросов и тексты вариантов — только из пакета, у каждого слота своя форма (пакета-победителя его `slot_id`): в коде и в `planer.yaml` ссылок на формы нет. `entry.*`-ID не хардкодятся и не конфигурируются — читаются из HTML формы; отправка только после проверки, что для всех обязательных вопросов есть данные (ТЗ §7.5). Названия вопросов и тексты вариантов — только из пакета (`form.fields` / `form.values` / `form.date_format`), никогда из кода. Поля с `null` в `form.fields` не отправляются. Планер никогда не отправляет значение, которого нет среди вариантов вопроса: нет даты в «Время стрима» → ошибка пары; повтора в следующий запуск нет — ключ прежний, передаётся из `keys.txt` вручную (ТЗ §7.5).
3. **Пакет — только чтение.** Все решения — по `manifest.json`, никогда по имени файла. Читаются все пакеты из `promo\` — сколько бы их там ни было, подпапок нет; слоты сливаются в одну карту по `slot_id`, более новый пакет побеждает, прошлое отбрасывается. Планер пакеты не двигает и не переписывает; удаляет только старьё по `keep_days` (ТЗ §5.1, §7.1, §5.7).
4. **Даты `DD-MM-YYYY`, время `HH:MM` по Киеву** — во всех файлах, именах и отчётах планера. Два исключения: `start` в манифесте — ISO-8601 со смещением, только для сравнения моментов; значения, уходящие в форму, — в `form.date_format` из пакета, и отчёт, цитируя вариант формы, приводит дату как в форме (ТЗ §5, §7.5).
5. **Никаких паролей.** Авторизация — OAuth, скоуп только `https://www.googleapis.com/auth/youtube`, один токен на канал: `secrets\<ключ канала>.token.json`, ключ — из `config\channels.yaml`. Привязка ключа к настоящему `youtube_channel_id` живёт в `state\channels.json` и при расхождении останавливает запуск. `client_secret.json` — общий, поставляется с exe (ТЗ §5.3).
6. **Ключи потока в логах маскируются** (последние 4 символа). В `keys.txt` — полностью. Формат ключа YouTube проверяется по `YOUTUBE_STREAM_KEY_PATTERN` в `platforms/youtube.py` (ТЗ §7.4).
7. **Настройки эфира задаёт планер, а не канал.** Аудитория — всегда «не для детей», категория — из `channels.yaml` (`category_id`), язык — из слота. Все три правятся одним проходом по ресурсу `videos` (`part=snippet,status`, read-modify-write целиком) у каждого своего эфира на каждом запуске; совпало всё — записи нет. Живой чат и модерация комментариев в API отсутствуют — это настройки Студии (ТЗ §6.2, §7.4). Возрастное ограничение 18+ через API **только читается**: попытка записать `contentDetails.contentRating` даёт 400, снимать его владелец должен руками в Студии (ТЗ §7.4).
8. **Эфиры не удаляются автоматически.** Эфиры без соответствия слоту (ручные/чужие) не трогаются и в отчёт не попадают. Исправление изменившегося эфира — `liveBroadcasts.update` на месте, ключ и ссылка сохраняются (ТЗ §7.3).
9. **Один сбой не валит запуск.** Ошибка изолируется в объект и уходит в отчёт; остальные обрабатываются. Временная недоступность площадки (5xx) — не сбой: вызов повторяется с нарастающей паузой (ТЗ §7.4).
10. **`state\` — только runtime-данные; `logs\` — диагностика и отчёты запусков.** Смешивать `state\` с `logs\` нельзя. Отчёт — такой же производный файл, как лог: имя по шаблону «дата_время_наименование», старьё уходит по `keep_days` (ТЗ §5.6, §5.7).
11. **Новые зависимости — только с явного согласования.** Разрешённый набор: `google-api-python-client`, `google-auth`, `google-auth-oauthlib`, `requests`, `PyYAML` + stdlib.
12. **Форма и канал для разработки — тренировочные** (копия боевой формы, тестовый канал). Тренировочная форма — https://forms.gle/UjVo2gftZdHsEdpZ7, таблица ответов — https://docs.google.com/spreadsheets/d/1YM1ydbTrpU1T7Vgp6oUreNDpJK-Khwle3RJXL8wbASE/edit. Боевая форма — только на этапе 5.

## Стандарты кода

- `from __future__ import annotations` в каждом файле; аннотации `X | None`, lowercase generics; явные типы возвращаемых значений и переменных.
- Имена английские: функции `verb_noun`, булевы `is_`/`has_`/`should_`. Папки во множественном числе, файлы в единственном, первое слово имени файла = домен папки.
- Функции ~30 строк, одна ответственность, guard clauses. Классы вместо функций с длинными списками аргументов. Явная обработка ошибок, без «голых» `except`.
- Никакого хардкода: константы — в конфиг или enum; единый источник истины для каждой константы.
- Иерархические имена логгеров под `"planer"` (`"planer.youtube"`, `"planer.form"`); структурированные сообщения `key=value`.
- Все тексты для владельца (консоль, отчёт) — только в `app/ui/messages_ru.py`. В коде — английские идентификаторы сообщений.
- Тесты `pytest` в `app/tests/`, тест-файл = `test_<модуль>.py`. Тесты гоняют реальный production-путь, а не переписывают логику inline. Платформа и `requests` подменяются фейками.
- Переводы строк: репо хранит LF (`.gitattributes: * text=auto eol=lf`), `.bat`/`.ps1` — CRLF. В workspace `"files.eol": "\n"`.

## Как работать с задачами

- Ветка — `feature/planers`. После сессии Claude Code: `git checkout feature/planers` (Code переключает ветки). Коммиты без trailer `Co-Authored-By`.
- Каждая задача приходит со SCOPE LOCK и списком DO NOT TOUCH. Границы — буквально. Файлы вне области — не трогать, даже если «заодно».
- Все технические вопросы агент решает сам, до конца: символ не найден — ищет фактический эквивалент grep'ом; тест падает — разбирается и чинит в своей области; неясен вызов — читает код и выбирает решение, совместимое с текущим. Наверх выносятся только три вещи: (а) нужно изменить контракт из ТЗ; (б) нужно править файл из DO NOT TOUCH; (в) не решается ни одним из испробованных способов — тогда в отчёте перечень попыток. Каждое самостоятельное решение — строкой в отчёте.
- Перед правкой — `grep` по текущему коду на точные имена символов; не писать по памяти (stale-coordinate rule).
- Не хардкодить число тестов в отчётах; формулировка — «новых падений относительно baseline нет».
- В конце каждой задачи — отчёт об изменённых файлах: каждый файл и что в нём изменилось.
- Все правки — кода, конфигов и документов (ТЗ, CLAUDE.md) — делает агент по промту. Артур ставит задачи, контролирует и проверяет; руками ничего не правит.
