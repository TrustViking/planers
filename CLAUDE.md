# CLAUDE.md — planers (планер)

Инструкции для агента (Claude Code / Cowork / Codex), работающего в `D:\_projects\planers`.
Этот файл — единственный документ требований и правил работы: отдельного технического задания в репо нет (удалено 14-09-2026). Расхождение кода с этим файлом — доложить, не решать молча.

## Что это

Планер — локальная Windows-программа у владельца YouTube-канала, машина №2 в пайплайне broadcaster → **planer** → стример. Берёт пакет `*.bcast` от броадкастера, сверяет его с эфирами, уже запланированными на каналах владельца, создаёт недостающие эфиры (и исправляет те, у которых изменились название/описание), получает ключи потока, пишет их в `keystreams\keys.txt` и отправляет в Google-форму ключей, в конце — отчёт.

Площадки v1 — только YouTube. Facebook — этап 6. Rumble — нет.

Планер **не**: стримит и не трогает расписание (источник — Google Sheets броадкастера); не обходит Google-форму; не трогает эфиры, которые не соответствуют ни одному слоту (ручные/чужие); не хранит логины и пароли площадок; сам ничего не скачивает и в Telegram не ходит (пакет владельцу пересылает оператор руками).

| # | Машина | Кто | Делает | Проект |
|---|--------|-----|--------|--------|
| 1 | Броадкастер | оператор (Артур) | Sheets → yt-dlp → LLM → анонсы в Docs/Telegram → после всех анонсов пакет для планера в Telegram | `broadcaster` |
| 2 | Планер | владелец канала | пакет → сверка с YouTube → эфиры → ключи → `keys.txt` → форма → отчёт | `planers` |
| 3 | Стример | оператор | берёт ключи из ответов формы → стримит | вне проекта |

## Сквозной сценарий

1. Оператор запускает броадкастер; после публикации всех дат он отправляет пакет документом в тот же Telegram-канал, куда ушли анонсы.
2. Оператор пересылает пакет владельцу. Владелец сохраняет файл в `bcast\` папки планера.
3. Владелец запускает `planer.bat`. Планер:
   1. читает `config\channels.json` и `config\planer.json`; к каналам ещё не обращается;
   2. читает **все** пакеты в `bcast\`, сливает слоты в одну карту по `slot_id`, выбрасывает прошедшие; пакетов нет — код 3, каналы не трогаются;
   3. отбирает будущие слоты под языки своих каналов — объекты запланированных эфиров;
   4. по каждому каналу, у которого есть объекты, при первом обращении: токена нет — вход в браузере, затем проверка привязки; запрашивает у YouTube запланированные эфиры и сверяет все параметры, которые планер диктует эфиру: нет эфира → создать; есть, но исправимое поле отличается → исправить; есть и совпадает → копия; неисправимое расхождение — в лог, консоль и отчёт;
   5. для созданного эфира получает ключ;
   6. отправляет в форму ключи, которые в этом запуске должны дойти до стримера (создан, привязан поток, исправлен, усыновлён), затем перегенерирует `keys.txt`;
   7. выводит результат: сводку — в консоль, отчёт — в `logs\{DD-MM-YYYY}_{HHMMSS}_report.md`, диагностику — в `logs\{DD-MM-YYYY}_{HHMMSS}_planer.log`; попутно удаляет старьё.
4. Владелец смотрит отчёт. Что-то не так с эфиром — правит или удаляет его на YouTube руками; следующий запуск это увидит.

## Инварианты — не нарушать без явного согласования с Артуром

0. **Рабочая единица — объект запланированного эфира** (`app\pipeline\plan.py`): один объект = один эфир одного слота на одном канале. Из пакета — слот, канал и спека; со сверки — найденный эфир и его спека; дальше — результаты. Памяти о прошлых запусках у планера нет: журнала нет, в `app\state\` лежит только `bindings.json`.
1. **Истина об эфирах — на YouTube; ключ потока и ссылка на эфир читаются только с площадки.** Перед любым созданием — сверка `liveBroadcasts.list(broadcastStatus=upcoming)` (без `mine` — фильтры взаимоисключающие); совпадение по минуте старта (UTC) + маркер `slot_id` в `liveStreams.snippet.title`. Опознанный эфир сверяется по **всем** параметрам, которые планер диктует площадке (название, описание, категория, видимость, маркер потока, автостарт, автостоп, задержка): расхождение исправимого поля — исправление на месте, пакет в приоритете; неисправимое — строка в лог, «внимание:» в консоли и строка в отчёте, на ручную правку владельцем планер не рассчитывает. Эфира нет — создание; решения «создать заново» нет. Слот внутри `min_lead_minutes` сверяется только на чтение, ради ключа. К площадке обращаемся только по каналам, у которых есть объекты; вход и проверка привязки — при первом обращении к каналу.
1a. **В форму уходит ключ, который в этом запуске должен дойти до стримера** (`should_send_key`), ровно в четырёх случаях: эфир создан; найденному эфиру без потока поток привязан; найденный эфир исправлен (UPDATE); ручной эфир без метки планера усыновлён — метка проставлена. Совпавший эфир с меткой планера ключ не шлёт, даже если прошлая отправка не подтвердилась. Задвоение строки у стримера допустимо (решение 15-09-2026): стример берёт последнюю строку по дате, каналу и языку — README этапа 5 обязан объяснить это стримеру.
2. **Google-форма — единственный канал передачи ключей стримеру.** Никаких обходных путей. URL формы, названия вопросов и тексты вариантов — только из пакета (`form.url`, `form.fields`, `form.values`, `form.date_format`), у каждого слота своя форма (пакета-победителя его `slot_id`): в коде и в `config\` ссылок на формы нет. `entry.*`-ID не хардкодятся и не конфигурируются — читаются из HTML формы; отправка только после проверки, что для всех обязательных вопросов есть данные. Поля с `null` в `form.fields` не отправляются. Планер никогда не отправляет значение, которого нет среди вариантов вопроса: нет даты в «Время стрима» → ошибка пары; повтора в следующий запуск нет — ключ прежний, передаётся из `keys.txt` вручную.
3. **Пакет — только чтение.** Все решения — по `manifest.json`, никогда по имени файла. Читаются все пакеты из `bcast\` — сколько бы их там ни было, подпапок нет; пакетов нет — код 3, каналы не трогаются; слоты сливаются в одну карту по `slot_id`, более новый пакет побеждает, прошлое отбрасывается. Планер пакеты не двигает и не переписывает; удаляет только старьё по `keep_days`.
4. **Даты `DD-MM-YYYY`, время `HH:MM` по Киеву** — во всех файлах, именах и отчётах планера. Два исключения: `start` в манифесте — ISO-8601 со смещением, только для сравнения моментов; значения, уходящие в форму, — в `form.date_format` из пакета, и отчёт, цитируя вариант формы, приводит дату как в форме.
5. **Никаких паролей.** Авторизация — OAuth, скоуп только `https://www.googleapis.com/auth/youtube`, один токен на канал: `secrets\<account_name>.token.json`, имя канала `account_name` из `config\channels.json` — единственный ключ канала (технического `id` нет). Привязка имени к настоящему `youtube_channel_id` живёт в `app\state\bindings.json`; канал за токеном не тот или этот YouTube-канал записан под другим именем — ошибка объектов этого канала, остальные каналы работают, привязка не переписывается. `client_secret.json` — общий, поставляется с exe.
6. **Ключи потока в логах маскируются** (последние 4 символа). В `keys.txt` — полностью. Формат ключа YouTube проверяется по `YOUTUBE_STREAM_KEY_PATTERN` в `platforms/youtube.py`.
7. **Настройки эфира задаёт планер, а не канал.** Аудитория — всегда «не для детей», категория — из `planer.json` (`category_id`, одна на все каналы; оттуда же `auto_start` и `set_thumbnail`), язык — из слота. Все три и видимость (`privacyStatus` из `channels.json`) правятся одним проходом по ресурсу `videos` (`part=snippet,status`, read-modify-write целиком) у каждого своего эфира на каждом запуске; совпало всё — записи нет. Живой чат и модерация комментариев в API отсутствуют — это настройки Студии. Возрастное ограничение 18+ через API **только читается**: попытка записать `contentDetails.contentRating` даёт 400, снимать его владелец должен руками в Студии.
8. **Эфиры не удаляются автоматически.** Эфиры без соответствия слоту (ручные/чужие) не трогаются и в отчёт не попадают. Исправление изменившегося эфира — `liveBroadcasts.update` на месте, ключ и ссылка сохраняются.
9. **Один сбой не валит запуск.** Ошибка изолируется в объект и уходит в отчёт; остальные обрабатываются. Недоступный канал и отказ привязки канала — ошибка всех объектов этого канала, другие каналы работают. Временная недоступность площадки (5xx) — не сбой: вызов повторяется с нарастающей паузой.
10. **`app\state\` — только runtime-данные; `logs\` — диагностика и отчёты запусков.** Смешивать их нельзя. В корне владелец видит только своё: `config\` (что заполняет), `secrets\` (ключи доступа), `bcast\` (пакеты), `keystreams\` (ключи потоков), `logs\`; всё остальное — в `app\`. Конфиги — два JSON, все поля обязательные, умолчаний в коде и примеров рядом с программой нет; в `config\` планер ничего не пишет. Отчёт — такой же производный файл, как лог: имя по шаблону «дата_время_наименование», старьё уходит по `keep_days`.
11. **Новые зависимости — только с явного согласования.** Разрешённый набор: `google-api-python-client`, `google-auth`, `google-auth-oauthlib`, `requests` + stdlib (PyYAML убран в задаче 5b: конфиги — JSON); инструмент сборки — `pyinstaller==6.19.0` (в том же `.venv_planers`, в код приложения не импортируется).
12. **Форма и канал для разработки — тренировочные** (копия боевой формы, тестовый канал). Тренировочная форма — https://forms.gle/UjVo2gftZdHsEdpZ7, таблица ответов — https://docs.google.com/spreadsheets/d/1YM1ydbTrpU1T7Vgp6oUreNDpJK-Khwle3RJXL8wbASE/edit. Боевая форма — https://forms.gle/MA6D898sT86Tvsyw7, только на этапе 5.

## Форматы данных

### Пакет от броадкастера (`*.bcast`)

ZIP с расширением `.bcast`: `manifest.json` (UTF-8) + `previews/*.jpg`. Имя — `plan_{DD-MM-YYYY}_{DD-MM-YYYY}_gen{DD-MM-YYYY}-{HHMM}.bcast` (первый и последний слот, момент генерации); оно для людей, планер его не парсит.

```json
{
  "schema_version": 1,
  "package_id": "20260913-101502-a1b2c3",
  "generated_at": "13-09-2026 10:15",
  "generator": { "project": "pipeline", "version": "1.4.0", "run_id": "…" },
  "timezone": "Europe/Kyiv",
  "period": { "from": "14-09-2026", "to": "25-09-2026" },
  "form": {
    "url": "https://forms.gle/UjVo2gftZdHsEdpZ7",
    "fields": {
      "language": "Язык стрима ( Language of stream)", "account_name": "Название канала ( Channel name)",
      "date": "Время стрима ( Stream time )", "platform": "Платформа (Platform)",
      "stream_key": "You Tube Stream Key", "stream_url": "Stream-URL (YT)",
      "time": null, "broadcast_url": null, "slot_id": null
    },
    "values": {
      "language": { "uk": "Украинский ( Ukranian)", "ru": "Русский ( Russian)", "en": "Английский ( English)", "hu": "Венгерский (Hungarian, Magyar)" },
      "platform": { "youtube": "You Tube", "facebook": "Facebook", "rumble": "Rumble" }
    },
    "date_format": "%d.%m.%Y"
  },
  "slots": [
    {
      "slot_id": "16-09-2026_1900_uk", "broadcaster_slot_key": "160926_1900_uk",
      "date": "16-09-2026", "time": "19:00", "start": "2026-09-16T19:00:00+03:00", "language": "uk",
      "title": "…", "description": "…",
      "previews": ["previews/16-09-2026_1900_uk_1.jpg", "previews/16-09-2026_1900_uk_2.jpg"],
      "sources": ["https://www.youtube.com/watch?v=…"]
    }
  ]
}
```

- Пакет — весь прогон броадкастера: все даты, все языки; `period` — min/max дат слотов, другого смысла нет.
- `slot_id` = `{DD-MM-YYYY}_{HHMM}_{lang}`; `date` — для людей и формы, `time` — для людей (в форму не уходит), `start` — момент для сравнения с YouTube (UTC) без базы часовых поясов.
- `title`/`description` — ровно те тексты, что ушли в анонс Telegram; в пакет попадает каждая пара (слот, язык), по которой был анонс.
- `previews` — 1..N файлов одного эфира; обложкой ставится **одно случайное**.
- `form.url` — ссылка как есть (forms.gle), планер идёт по редиректу; `form.fields` — названия вопросов символ в символ, `null` — вопроса нет; `form.values` — тексты вариантов радио-вопросов по кодам; `form.date_format` — strftime-формат даты в начале варианта «Время стрима».
- Неизвестная `schema_version` — пакет не читается, строка в отчёте. `generator` — информационное поле. Прошлое планер фильтрует сам, даже если броадкастер уже отфильтровал.

### Конфиги: `config\channels.json` и `config\planer.json`

Оба JSON. **Все поля обязательные, умолчаний в коде нет, примеров рядом с программой нет, планер ничего не копирует.** Неизвестное или повторённое поле — ошибка с его именем.

**`config\channels.json` — заполняет владелец**, ровно пять полей на канал:

```json
{"channels": [
  {"platform": "youtube", "account_name": "Osvald.X", "google_account": "you@gmail.com",
   "languages": ["ru"], "privacy": "unlisted"}
]}
```

- `platform` — только `youtube`; `facebook` — ошибка «появится на этапе 6», прочее — ошибка со списком допустимых.
- `account_name` — имя канала ровно как в форме регистрации ключей: уходит в форму, им подписаны отчёт и `keys.txt`, и **оно же — ключ доступа** (имя файла токена). Перед проверками приводится к NFC. Запрещены `\ / : * ? " < > |` и управляющие символы, пробел или точка в начале и в конце, зарезервированные имена Windows (`CON`, `NUL`, `COM1`…), длина больше 100 символов; уникально в файле без учёта регистра; `all` (без учёта регистра) занято режимом `--auth all`.
- `google_account` — почта аккаунта Google, в котором живёт канал: подсказка браузеру при входе (`login_hint`) и строка в консоли перед браузером. Проверка минимальная: непустая строка, ровно один `@`, части вокруг него непустые и без пробелов.
- `languages` — непустой список кодов строчными без повторов. Канал может обслуживать несколько языков (например `["uk", "ru"]`): слот размножается по всем каналам своего языка, единица работы по-прежнему «слот на канале» — у многоязычного канала слоты разных языков одной минуты дают отдельные объекты и отдельные эфиры. Язык стримов назначает **оператор** здесь; язык канала на YouTube только показывается в `--check`. Коды со справочником не сверяются: язык без варианта в форме даст эфир и ключ, но отправка вернёт `missingOption`.
- `privacy` — `public` | `unlisted`.

**`config\planer.json` — технический, поставляется со сборкой заполненным**, действует на все каналы:

```json
{"min_lead_minutes": 60, "keep_days": 30,
 "auto_start": true, "set_thumbnail": true, "category_id": "22"}
```

`min_lead_minutes` (целое ≥ 0) — слоты, до старта которых меньше, не планируются; `keep_days` (целое ≥ 1) — срок хранения файлов в `bcast\` и `logs\`; `auto_start` — эфир стартует сам, когда пошёл поток; `set_thumbnail` — ставить превью из пакета; `category_id` — категория YouTube (`"22"` — People & Blogs), по справочнику не проверяется.

`planer.json` в git — один источник и для dev, и для сборки; `channels.json` — в `.gitignore`. Шаблон каналов для репо и README — `app\examples\channels.example.json` (в коде не упоминается, в сборку не идёт). Нет файла или обязательного поля — код 2, ошибка и точный шаблон файла в консоли («Создайте файл … с таким содержимым и впишите свои значения», для `planer.json` — «Восстановите файл…»); прочая ошибка — код 2 и строка с путём поля (`channels[1].languages`). Сначала читается `channels.json`, затем `planer.json`. Логинов, паролей, URL формы, entry-ID и путей к токенам в конфигах нет.

### Секреты и вход в канал

- **`secrets\client_secret.json` — «паспорт программы»**: OAuth-клиент типа Desktop из GCP-проекта оператора, один на всех владельцев, лежит рядом с exe. Нет файла — код 2, к YouTube планер не обращается.
- **`secrets\<account_name>.token.json` — «пропуск канала»**, появляется при первом обращении к каналу. Перед браузером консоль называет канал («Канал «Osvald.X»: нужен вход в Google — сейчас откроется браузер»), предупреждает про «Google hasn't verified this app» (Advanced → Go to ... (unsafe) → Continue) и говорит, какой аккаунт выбирать. Токен обновляется сам; отозван — снова браузер.
- **Привязка** `app\state\bindings.json` (ключ — `account_name`; `youtube_channel_id`, `title`, `authorized_at`; schema_version 1, запись атомарная). При первом обращении к каналу за запуск — `channels.list(mine=true)` и сверка: имени нет и YouTube-канал свободен — записать; совпал — работать; id другой или YouTube-канал записан под другим именем — ничего не переписывать, все объекты канала — ошибка в отчёт с подсказкой `--auth "<account_name>"`.
- Вход и проверка — только у каналов с объектами; `--check` идёт тем же путём по всем каналам; `--auth` удаляет токен и открывает браузер, привязка сверяется тем же правилом.
- Механика — `InstalledAppFlow.run_local_server` (порт 0), как в броадкастере; скоуп другой, токен — на канал. `secrets\` целиком в `.gitignore`.

### Файл ключей `keystreams\keys.txt`

Нужен, когда форма не сработала и ключ передают руками. Перегенерируется на каждом запуске: блок на каждый будущий эфир с ключом, **включая слоты внутри `min_lead_minutes`**; ключ читается с площадки (у чужих эфиров тоже). Шапка из трёх строк, блоки через пустую строку, сортировка по дате, времени, языку, **ключ — первым полем блока**. Формат `.txt`, значков ✅/❌ нет.

```
# Ключи трансляций. Сгенерировано планером 13-09-2026 12:00.
# Файл перезаписывается на каждом запуске — не править.
# Строка «форма»: «отправлен в форму» — ключ у стримера; «в этом запуске в форму не отправлялся» — эфир с меткой планера совпал, ключ уходил раньше; «НЕ отправлен» — передайте ключ стримеру вручную.

16-09-2026 19:00  uk  Канал UA
  ключ   xxxx-xxxx-xxxx-xxxx-xxxx
  поток  rtmp://a.rtmp.youtube.com/live2
  эфир   https://www.youtube.com/watch?v=abc123
  форма  отправлен в форму 13-09-2026 12:00
```

Строка «форма» говорит только об этом запуске, три состояния (тексты — в `messages_ru`): «отправлен в форму <дата время>»; «в этом запуске в форму не отправлялся: эфир уже стоял с этим ключом» (совпавший эфир с меткой планера, слот внутри `min_lead_minutes` и все блоки `--status`); «НЕ отправлен: <причина> — передайте стримеру вручную» (ключ должен был уйти — создан, привязан, исправлен, усыновлён — и не ушёл).

### Консоль, отчёт и лог

| Поверхность | Читатель | Что в ней |
|---|---|---|
| консоль | владелец, во время и сразу после запуска | шапка при старте и строка на каждый долгий шаг; затем перечень блоками сверху вниз: что требует внимания, что опубликовано, исправлено, какие ключи ушли стримеру, что уже стояло и что не публиковалось; без markdown и значков; один эфир — ровно одна строка без переносов |
| `logs\{DD-MM-YYYY}_{HHMMSS}_report.md` | владелец; можно переслать оператору | то же с подробностями |
| `logs\{DD-MM-YYYY}_{HHMMSS}_planer.log` | разработка | диагностика `key=value` |

Одно и то же в двух местах не печатается. Счётчики считаются один раз (`build_totals`) — для «Итога» отчёта и для консоли.

**Консоль** — порядок вывода сверху вниз:
1. **Шапка** «Planer <версия> — <дата время>» (у `--dry-run` и `--status` — с пометкой режима, у `--check` и `--auth` — обычная): её печатает `main.py` сразу после настройки логов, до чтения конфигов и любого обращения к сети, во всех режимах; время — то же, что в отчёте запуска.
2. **Строки прогресса** (`output\progress.py`: Protocol `RunProgress`, `NoProgress` — умолчание для тестов и вызовов без консоли, `ConsoleProgress` — в `main`; отступ два пробела, `flush=True`, тексты `PROGRESS_*` в `messages_ru`): пакеты прочитаны — сколько пакетов, слотов всего и под мои языки (числа — `build_totals` по `build_package_lines`, тем же подсчётом, что отчёт; `runner` сразу после `scan_bcast` и `build_planned`); по каждому каналу — «запрашиваю» до `list_upcoming` (вход в канал происходит внутри него) и «запланированных эфиров N» после ответа (`reconciler`; при сбое второй строки нет, ошибка — во ВНИМАНИЕ); «создаю эфир» / «исправляю эфир» (исполнитель в `runner`); «отправляю ключ в форму» перед каждой отправкой; «пишу отчёт». В `--dry-run` строк создания, исправления и отправки ключа нет, строки пакетов, каналов и отчёта есть; в `--status` — каналы и отчёт. Прогресс передаётся параметром: `run(..., progress=)`, `Reconciler(..., progress=)`.
3. **Пустая строка** — отделяет прогресс от итога.
4. **Итог и блоки** (`output\console.py`, `render_console` начинается со строки «Итог», заголовка в нём нет — двух заголовков в прогоне не бывает): «Итог: опубликовано N, исправлено N, уже стояло N, не публиковали N, ошибок N» (числа — из `build_totals`), затем блоки.
5. **Подвал** — пути к `keys.txt`, отчёту и логу.

Блоки итога. Блок начинается разделителем фиксированной ширины (`CONSOLE_RULE_WIDTH` в `messages_ru`) из «=» с названием и счётчиком внутри; у ВНИМАНИЕ счётчика нет. Блоков шесть, строго в таком порядке:
1. **ВНИМАНИЕ** — ошибки, ключ не дошёл до стримера, проблемы пакетов, предупреждения запуска и объектов: что планер вернул к пакету (видимость, категория, метка — «было / стало»; аудитория), что исправить не может (`REPORTED_FIELDS`), AMBIGUOUS со ссылками (строкой ошибки не дублируется), эфир без времени старта (канал и название; в лог — INFO `broadcast_without_start`, только диагностика; постоянный эфир канала — `snippet.isDefaultBroadcast`, его заводит сама площадка, «<Имя канала> Live Stream», удалить нельзя — исключён: из списка тоже выпадает, но замечания не даёт, в лог — INFO `default_broadcast_skipped` с каналом, id и названием; владельцу — замечанием площадки, которое приходит данными: `BroadcastPlatform.take_notices()` → `PlatformNotice` → `build_warning_lines` в runner, поэтому строка есть и в консоли, и в отчёте `logs\*_report.md`). Постоянные особенности площадки (`PLATFORM_NOTE_LINES`) в консоль не идут.
2. **ОПУБЛИКОВАЛИ** — созданные эфиры и эфиры с привязанным потоком.
3. **ИСПРАВИЛИ** — к строке эфира добавляется, что обновлено, но только из текстов эфира — название и описание (названия полей — как в отчёте). Настройки (видимость, категория, метка) здесь не называются: они во ВНИМАНИЕ с «было / стало». Изменились только настройки — строка эфира без хвоста «обновлено», эфир всё равно в блоке и в счётчике «исправлено».
4. **КЛЮЧИ СТРИМЕРУ** — все эфиры, у которых в этом запуске `should_send_key`, дошёл ключ или нет: вместо названия ключ **маской** (`mask_stream_key`, последние четыре символа, как в логе) и состояние отправки. Полный ключ в консоли не печатается никогда; путь к `keystreams\keys.txt`, где он лежит, печатается один раз — строкой подвала.
5. **УЖЕ СТОЯЛО** — совпавшие эфиры.
6. **НЕ ПУБЛИКОВАЛИ** — пропуски, сгруппированные по причине (уже прошло; до старта меньше N минут; нет канала для языка X), под причиной — строки слотов.

Пустой блок не печатается совсем: нули видны в «Итоге». В блоках 2–5 строки группируются по каналу: шапка группы — имя канала и почта аккаунта в скобках, один раз на группу; каналы — в порядке `channels.json`, внутри канала — по дате и времени. Строка эфира: дата, время, язык, название целиком (уже обрезано спекой до 100 символов). `--dry-run` — те же блоки, но ОПУБЛИКУЕМ и ИСПРАВИМ («вернём к пакету» во ВНИМАНИЕ), блока КЛЮЧИ СТРИМЕРУ нет — ничего не отправлялось. `--status` — шапка, строки прогресса, итог, ВНИМАНИЕ и УЖЕ СТОЯЛО.

**Отчёт** — сначала то, ради чего открывают: заголовок «# Planer <версия> — отчёт <дата время>», «Итог», Ключ не дошёл до стримера, Ошибки, Предупреждения, Расхождения с платформой, Создано, Исправлено, Уже запланировано, Перенесён или отменён, Пропущено, Пакеты, Особенности площадки. **Пустой раздел не печатается.**

- «Ключ не дошёл до стримера» — ключ, который должен был уйти в этом запуске, а форма отправку не подтвердила: сразу под «Итогом», с причиной и указанием передать ключ из `keys.txt` вручную; счётчики от раздела не меняются.
- Предупреждения запуска (обложка, язык, аудитория была «для детей», 18+, настройки видео, перечитывание фактов, сохранённый ответ формы, неисправимый параметр эфира — хотели и на YouTube, несколько эфиров без метки на минуту — со ссылками на всех кандидатов) — и в консоль, и в отчёт. В `PLATFORM_NOTE_LINES` они не кладутся: там только постоянные особенности площадки.
- Особенности площадки (живой чат у эфиров YouTube; «эфир с меткой планера совпал — ключ уже уходил, повторно не отправляется») — **только в отчёте**, последним разделом, одна строка на особенность за запуск.
- Факты платформы: после действий каждый свой эфир перечитывается один раз (`videos.list(part=snippet,status,contentDetails,liveStreamingDetails)` + поток); в лог — `broadcast_expected` / `broadcast_actual` / `broadcast_facts`; в отчёт — только расхождения: поля спеки тем же `BroadcastSpec.diff`, что решает сверку (название, описание — длина и начало, категория, видимость, маркер, автостарт, автостоп, задержка), плюс старт, язык и аудитория. Маркер у эфира, созданного или привязанного в этом же запуске, не сравнивается: перечитывание может ещё не видеть поток (ложное расхождение 14-09-2026). Поле, записанное этим же запуском через `apply_video_settings` (язык, категория, видимость, аудитория), берётся в снимок фактов из ответа `videos.update`, а не из перечитывания: реплика площадки изменение может ещё не видеть (ложное расхождение по языку 15-09-2026 — записали `uk`, `videos.list` через секунду отдал `ru`). Ответ записи несёт `VideoFixes.applied` (`AppliedVideo`), подстановку делает `VideoFixes.apply_to_facts`, вызывает её `runner._Executor._read_facts`. Ответу записи верим, но сверяем с отправленным: вернула площадка не то, что просили, — расхождение настоящее и показывается сразу. Независимое чтение того же поля делает следующий запуск, там гонки уже нет. Расхождение — не ошибка.
- Строки исходов: «дата время язык -> аккаунт — …», например «эфир создан, ключ передан в форму», «на YouTube отличалось: видимость; исправлено, ключ и ссылка прежние, ключ передан в форму».

**Коды выхода:** `0` — всё, что можно, сделано; `1` — есть ошибки (в том числе неподтверждённая отправка ключа, который должен был уйти); `2` — ошибка конфигурации/авторизации, ничего не делалось; `3` — в `bcast\` нет пакетов (к каналам не обращались).

### Чистка старья

Единственное место, где планер удаляет файлы: на каждом запуске, кроме `--dry-run`, из `bcast\` и `logs\` удаляются файлы старше `keep_days`. Вложенные папки и `keystreams\`, `app\state\`, `secrets\`, `config\` не трогаются. Чистка — до записи отчёта, чтобы свой отчёт под неё не попал.

## Алгоритм

### Сбор слотов из `bcast\`

1. Все `*.bcast` из `bcast\`, без подпапок. Битый архив/манифест — «пакет повреждён», файл не трогается.
2. Пакеты читаются от старого `generated_at` к новому; один `slot_id` в двух пакетах — побеждает более новый. Слот получает форму своего пакета (`Slot.form`).
3. Слоты с `start <= сейчас` выбрасываются. Пакет, у которого все слоты в прошлом, — строка в отчёте.
4. Пакеты остаются на месте; разбирает папку владелец (или чистка по `keep_days`).
5. Пакетов нет — код 3, вход в Google не начинается.

### Отбор слотов под каналы

- `start - сейчас < min_lead_minutes` → объект с признаком **too_late**: сверка только на чтение (опознать эфир, взять ключ и ссылку); не создаёт, не исправляет, не привязывает поток, не трогает настройки, в форму не шлёт; в отчёте — «пропущено», ключ — в `keys.txt`.
- Язык слота не входит ни в один `channels[].languages` → «нет канала для языка», пропуск.
- Иначе — объект на **каждый** канал с этим языком (два канала на язык → два эфира).
- Слоты сливаются по `slot_id` **до** размножения по каналам.

Слои объекта: из пакета (слот, пакет-источник, канал, ожидаемая спека); с площадки (найденный эфир, поток, фактическая спека); результат (`broadcast_id`, ссылка, `stream_url`, ключ, «ключ новый», статус формы этого запуска, ошибка).

### Сверка с платформой

1. По каждому каналу с объектами: вход и привязка при первом обращении; затем `liveBroadcasts.list(broadcastStatus=upcoming, part=snippet,contentDetails,status)` с пагинацией, без `mine` (иначе 400 `incompatibleParameters`, проверено 12-09-2026). Отказ привязки или недоступный канал — ошибка всех объектов канала.
2. Совпадение — минута старта в UTC. Несколько эфиров на минуту — различает маркер `slot_id` в названии привязанного потока (`liveStreams.list(id=boundStreamId)`, кеш по каналу и потоку). Маркер — это имя ключа потока в Студии (Создать -> Управление ключами трансляции), зрителям он не виден; у ключа есть и описание, которое планер заполняет: канал, дата и время слота, язык, когда записано (`messages_ru.STREAM_DESCRIPTION`). Эфир без маркера при единственном кандидате — опознан и усыновлён (метка — исправимое поле), при нескольких — AMBIGUOUS: планер не выбирает и не удаляет, но пишет в лог, в «внимание:» и в отчёт дату, время, язык, канал и ссылки на всех кандидатов. Маркер другого слота на той же минуте — мимо, независимо от того, сколько языков у канала: у многоязычного канала эфиры uk и ru в одну минуту опознаются каждый своим маркером.
3. Решения:

| На YouTube | Действие |
|---|---|
| эфира нет | создать; новый ключ в форму |
| есть, с нашей меткой, все исправимые поля совпадают | копия; ключ и ссылка с площадки, в форму не отправляются |
| есть, исправимое поле отличается | исправить на месте; ключ прежний, уходит в форму |
| есть, без метки планера (ручной), единственный на минуту | усыновить: `set_stream_marker` + прочие исправления; ключ прежний, уходит в форму |
| есть, отличается только неисправимое поле | решение не меняется; лог, «внимание:», строка расхождения в отчёте |
| есть, привязанного потока нет | создать поток с маркером и привязать; новый ключ в форму |
| эфир на время, которого нет ни в одном слоте, без маркера | не трогать, в отчёт не попадает |
| эфир с маркером планера, чьего слота нет | не удалять; в отчёт «Перенесён или отменён?» |

Сравниваются две спеки, построенные по одним правилам: название — `strip()`, описание — CRLF/CR → LF, хвостовые пробелы и края сняты, затем **обрезка по лимитам площадки для обеих сторон** (иначе длинное название правилось бы бесконечно). Сравниваются все диктуемые поля (`BroadcastSpec` — единственное место, задающее «одинаковый»; спека из слота берёт видимость из канала, категорию и автостарт из `planer.json`, автостоп и задержку — от площадки). Время старта не сравнивается: по нему эфир опознают. Поле, которое площадка не вернула (`None`), сравнивать не с чем: так список эфиров YouTube ведёт себя с категорией — её расхождение видно у ресурса `videos` в `apply_video_settings` и тоже считается исправлением (UPDATE, ключ в форму).

Поля делятся в одном месте — `plan.py`:
- **исправляем** (`FIXABLE_FIELDS`) — название, описание, категория, видимость, маркер: расхождение даёт UPDATE. Название, описание и категория — `liveBroadcasts.update`; видимость (и категория у ресурса видео) — `apply_video_settings`; маркер — `set_stream_marker` (`liveStreams.update(part=snippet)`, snippet читается и пишется целиком). **Категория сверяется только в полном запуске:** `categoryId` живёт у ресурса `videos`, в ответе `liveBroadcasts.list` его нет, поэтому в спеке с площадки он всегда пуст и сверкой пропускается (строка лога `spec_fields_not_compared`); расхождение ловит только второй проход — `apply_video_settings`, а он в `--dry-run` не выполняется. В `--dry-run` расхождение по категории не видно.
- **только сообщаем** (`REPORTED_FIELDS`) — автостарт, автостоп, задержка: они в `contentDetails`, а `liveBroadcasts.update` шлёт только `snippet` — `contentDetails` у update требует `monitorStream`. Гонять их через UPDATE значило бы на каждом запуске «исправлять» неисправимое и слать стримеру ключ заново. Проверено 13-09-2026: YouTube возвращает описание байт в байт и код языка как записан (`ru`).

Исправление текстов — `liveBroadcasts.update(part=snippet)`: вместе с названием и описанием всегда отправляются `scheduledStartTime` и `categoryId` из спеки; `contentDetails` не включается (потребовал бы `monitorStream`).

### Создание эфира (YouTube)

1. `liveBroadcasts.insert` — `title` (≤100, безопасная обрезка), `description` (≤5000), `scheduledStartTime` = `start` в RFC3339, `privacyStatus` = `channel.privacy`, `selfDeclaredMadeForKids = false`, `enableAutoStart` = `auto_start`, `enableAutoStop = true`, `latencyPreference = "normal"`, `categoryId` = `category_id`.
2. `liveStreams.insert` — `snippet.title = slot_id` (маркер), `snippet.description` — описание ключа (`STREAM_DESCRIPTION`), `cdn` rtmp / variable / variable; ключ `cdn.ingestionInfo.streamName` проверяется `^[a-z0-9]{4}(-[a-z0-9]{4}){3,4}$` — несовпадение = ошибка пары, форма не отправляется. У чужих эфиров ключ неожиданного вида — только предупреждение в лог.
3. `liveBroadcasts.bind`. На каждый эфир — свой поток и свой ключ.
4. `thumbnails.set` — если `set_thumbnail` и у слота есть превью: случайное. Сбой не фатален — предупреждение.
5. Настройки ресурса `videos` одним проходом: одно `videos.list(part=snippet,status)`, не больше одного `videos.update(part=snippet,status)` — `defaultLanguage` и `defaultAudioLanguage` = язык слота, `categoryId` = `category_id`, `privacyStatus` = видимость канала, `selfDeclaredMadeForKids = false`. Части отправляются **целиком** (частичная затирает `privacyStatus` и `title`). На каждом запуске у каждого своего эфира (создан, привязан, исправлен, подтверждён); у найденного эфира исправленные категория и видимость — это UPDATE и ключ в форму, аудитория — предупреждение; сбой не фатален.
6. Время старта у ресурса `videos` — в `liveStreamingDetails.scheduledStartTime`, не в `snippet`.
7. 18+ (`contentRating.ytRating == ytAgeRestricted`) только читается — предупреждение со ссылкой.

### Отправка в форму

1. **URL** — только `form.url` слота; структура читается `GET viewform` один раз на уникальный URL за запуск и кэшируется.
2. **Структура** — из скрипта `FB_PUBLIC_LOAD_DATA_`: элементы `payload[1][1]`, разделы разделяются разрывами (тип 8), раздел 0 — до первого разрыва. Переход у варианта (`option[2]`) — **идентификатор** целевого раздела (`item[0]` разрыва), переводится в номер через карту; отрицательные значения — служебные коды, не переходы. Не прочиталось — форма не отправляется, HTML сохраняется в `logs\{DD-MM-YYYY}_{HHMMSS}_form_page_{хеш}.html`.
3. **Значения**: текстовые — как есть (`account_name`, `stream_key`); радио — только текст варианта: `language` → `form.values.language[язык]`, `platform` → `form.values.platform["youtube"]`, `date` → вариант, начинающийся с даты в `form.date_format`, `stream_url` → вариант, равный `ingestionAddress` после нормализации (нижний регистр, без хвостового слэша). Нет варианта — ошибка пары, повтора нет. Перед отправкой у каждого обязательного вопроса пройденных разделов есть значение.
4. **POST `formResponse`** конечного URL: `entry.*` пройденных разделов, `fvv=1`, `fbzx`, `pageHistory` — **номера разделов с нуля** (для тренировочной формы `0,1`; идентификатор даёт 400), номер вне диапазона отбрасывается. `Accept-Language: en` и `hl=en`. `requests`, таймаут 30 с, 3 попытки на сеть и 5xx, на 4xx повтора нет.
5. **Подтверждение** — структурное, от языка не зависит (`form/submitter.py::read_confirmation`): HTTP 200, в теле есть `FB_PUBLIC_LOAD_DATA_`, нет ни одного `entry.<цифры>`, нет `fbzx`. Текстовые маркеры — только сигнал в лог. Не подтверждено — тело в `logs\{DD-MM-YYYY}_{HHMMSS}_form_response_{хеш}.html`, путь в отчёт, код выхода 1.

Коды исходов: `structureUnreadable`, `missingOption`, `requiredMissing`, `transportFailed`, `notConfirmed`. Отправка — отдельный финальный проход после действий, до записи `keys.txt`; только ключи с `should_send_key` (инвариант 1a).

## Как работать с задачами

- Ветка — `feature/planers`. После сессии Claude Code: `git checkout feature/planers` (Code переключает ветки). Коммиты без trailer `Co-Authored-By`.
- Каждая задача приходит со SCOPE LOCK и списком DO NOT TOUCH. Границы — буквально. Файлы вне области — не трогать, даже если «заодно».
- Все технические вопросы агент решает сам, до конца: символ не найден — ищет фактический эквивалент grep'ом; тест падает — разбирается и чинит в своей области; неясен вызов — читает код и выбирает решение, совместимое с текущим. Наверх выносятся только три вещи: (а) нужно изменить контракт из этого файла; (б) нужно править файл из DO NOT TOUCH; (в) не решается ни одним из испробованных способов — тогда в отчёте перечень попыток. Каждое самостоятельное решение — строкой в отчёте.
- Перед правкой — `grep` по текущему коду на точные имена символов; не писать по памяти (stale-coordinate rule).
- Не хардкодить число тестов в отчётах; формулировка — «новых падений относительно baseline нет».
- В конце каждой задачи — отчёт об изменённых файлах: каждый файл и что в нём изменилось.
- Все правки — кода, конфигов и документов (CLAUDE.md, README) — делает агент по промту. Артур ставит задачи, контролирует и проверяет; руками ничего не правит.

Каждая сборка (`build_release.bat`, а через него и `build_local.bat`) перед PyInstaller зовёт `python -m app.version --bump`: patch +1 прямо в `app\version.py` (0.1.0 → 0.1.1), новый номер уходит в exe, лог сборки и имя инсталлятора; изменённый `version.py` остаётся в рабочей копии и коммитится вместе со сборкой. Сборка упала после повышения — номер всё равно израсходован. Major и minor меняются руками. Название рядом с номером — латиницей: «Planer <версия>» (шапка консоли, `--version`, заголовок отчёта, `UninstallDisplayName` в `planer.iss`).
