# CLAUDE.md — planers (планер)

Инструкции для агента (Claude Code / Cowork / Codex), работающего в `D:\_projects\planers`.
Требования — в `TZ_planer.md` (версия 0.4, 11-09-2026). Этот файл — краткая выжимка и правила работы; при расхождении прав ТЗ, а расхождение надо доложить, не решать молча.

## Что это

Планер — локальная Windows-программа у владельца YouTube-канала, машина №2 в пайплайне broadcaster → **planer** → стример. Берёт пакет `*.bcast` от броадкастера, сверяет его с эфирами, уже запланированными на каналах владельца, создаёт недостающие эфиры (и исправляет те, у которых изменились название/описание), получает ключи потока, пишет их в `out\keys.txt` и отправляет в Google-форму ключей, в конце — отчёт. Подробно: ТЗ §1–4.

Площадки v1 — только YouTube. Facebook — этап 6. Rumble — нет.

## Инварианты — не нарушать без явного согласования с Артуром

1. **Истина об эфирах — на YouTube, не в локальных файлах.** Перед любым созданием — сверка `liveBroadcasts.list(mine=true, broadcastStatus=upcoming)`; совпадение по минуте старта (UTC) + маркер `slot_id` в `liveStreams.snippet.title`. Журнал `state\registry.json` — только память о ключах и отправках формы (ТЗ §5.4, §7.3).
2. **Google-форма — единственный канал передачи ключей стримеру.** Никаких обходных путей. `entry.*`-ID не хардкодятся и не конфигурируются — читаются из HTML формы; отправка только после проверки, что для всех обязательных вопросов есть данные (ТЗ §7.5). Названия вопросов и тексты вариантов — только из пакета (`form.fields` / `form.values` / `form.date_format`), никогда из кода. Поля с `null` в `form.fields` не отправляются. Планер никогда не отправляет значение, которого нет среди вариантов вопроса: нет даты в «Время стрима» → ошибка пары, повтор в следующий запуск (ТЗ §7.5).
3. **Пакет — только чтение.** Все решения — по `manifest.json`, никогда по имени файла. Читаются все пакеты из `inbox\`, слоты сливаются в одну карту по `slot_id`, более новый пакет побеждает, прошлое отбрасывается (ТЗ §5.1, §7.1).
4. **Даты `DD-MM-YYYY`, время `HH:MM` по Киеву** — во всех файлах, именах, отчётах, форме. Единственное исключение — `start` в манифесте: ISO-8601 со смещением, только для сравнения моментов (ТЗ §5).
5. **Никаких паролей.** Авторизация — OAuth, скоуп только `https://www.googleapis.com/auth/youtube`, один токен на канал: `secrets\<channel_id>.token.json`. `client_secret.json` — общий, поставляется с exe (ТЗ §5.3).
6. **Ключи потока в логах маскируются** (последние 4 символа). В `keys.txt` — полностью. Формат ключа YouTube проверяется по `YOUTUBE_STREAM_KEY_PATTERN` в `platforms/youtube.py` (ТЗ §7.4).
7. **Эфиры не удаляются автоматически.** Эфиры без соответствия слоту (ручные/чужие) не трогаются и в отчёт не попадают. Исправление изменившегося эфира — `liveBroadcasts.update` на месте, ключ и ссылка сохраняются (ТЗ §7.3).
8. **Один сбой не валит запуск.** Ошибка изолируется в пару (слот, канал) и уходит в отчёт; остальные пары обрабатываются.
9. **`state\` — только runtime-данные, `logs\` — только диагностика.** Смешивать нельзя (инвариант унаследован от broadcaster).
10. **Новые зависимости — только с явного согласования.** Разрешённый набор: `google-api-python-client`, `google-auth`, `google-auth-oauthlib`, `requests`, `PyYAML` + stdlib.
11. **Форма и канал для разработки — тренировочные** (копия боевой формы, тестовый канал). Тренировочная форма — https://forms.gle/UjVo2gftZdHsEdpZ7, таблица ответов — https://docs.google.com/spreadsheets/d/1YM1ydbTrpU1T7Vgp6oUreNDpJK-Khwle3RJXL8wbASE/edit. Боевая форма — только на этапе 5.

## Стандарты кода

- `from __future__ import annotations` в каждом файле; аннотации `X | None`, lowercase generics; явные типы возвращаемых значений и переменных.
- Имена английские: функции `verb_noun`, булевы `is_`/`has_`/`should_`. Папки во множественном числе, файлы в единственном, первое слово имени файла = домен папки.
- Функции ~30 строк, одна ответственность, guard clauses. Классы вместо функций с длинными списками аргументов. Явная обработка ошибок, без «голых» `except`.
- Никакого хардкода: константы — в конфиг или enum; единый источник истины для каждой константы.
- Иерархические имена логгеров под `"planer"` (`"planer.youtube"`, `"planer.form"`); структурированные сообщения `key=value`.
- Все тексты для владельца (консоль, отчёт) — только в `app/ui/messages_ru.py`. В коде — английские идентификаторы сообщений.
- Тесты `pytest` в `app/tests/`, тест-файл = `test_<модуль>.py`. Тесты гоняют реальный production-путь, а не переписывают логику inline. Платформа и `requests` подменяются фейками.
- Переводы строк: репо хранит LF (`.gitattributes: * text=auto eol=lf`), `.bat`/`.ps1` — CRLF. В workspace `"files.eol": "\n"`.

## Как работать с задачами

- Ветка — `feature/planers`. После сессии Claude Code: `git checkout feature/planers` (Code переключает ветки). Коммиты без trailer `Co-Authored-By`.
- Каждая задача приходит со SCOPE LOCK и списком DO NOT TOUCH. Границы — буквально. Файлы вне области — не трогать, даже если «заодно».
- Все технические вопросы агент решает сам, до конца: символ не найден — ищет фактический эквивалент grep'ом; тест падает — разбирается и чинит в своей области; неясен вызов — читает код и выбирает решение, совместимое с текущим. Наверх выносятся только три вещи: (а) нужно изменить контракт из ТЗ; (б) нужно править файл из DO NOT TOUCH; (в) не решается ни одним из испробованных способов — тогда в отчёте перечень попыток. Каждое самостоятельное решение — строкой в отчёте.
- Перед правкой — `grep` по текущему коду на точные имена символов; не писать по памяти (stale-coordinate rule).
- Не хардкодить число тестов в отчётах; формулировка — «новых падений относительно baseline нет».
- В конце каждой задачи — отчёт об изменённых файлах: каждый файл и что в нём изменилось.
- Все правки — кода, конфигов и документов (ТЗ, CLAUDE.md, plan.md) — делает агент по промту. Артур ставит задачи, контролирует и проверяет; руками ничего не правит.

.\.venv_planers\Scripts\python.exe -m app.main --status            # сверка + keys.txt + отчёт
