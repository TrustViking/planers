## 1. Назначение

Планер — локальная Windows-программа у владельца канала. Она берёт пакет с расписанием эфиров от броадкастера, сверяет его с тем, что уже запланировано на YouTube-каналах владельца, создаёт недостающие трансляции (и исправляет те, у которых изменились название/описание), получает ключи потока, записывает их в человеко-читаемый файл и отправляет в Google-форму ключей. В конце — отчёт: что создано, что уже было, что пропущено, что не удалось.

Планер **не**:

- не стримит и не трогает расписание (источник расписания — Google Sheets броадкастера);
- не обходит Google-форму: форма — единственный канал передачи ключей от владельца к стримеру;
- не трогает эфиры, которые не соответствуют ни одному слоту из пакетов (чужие/ручные эфиры владельца остаются как есть);
- не хранит логины и пароли площадок (§5.3).

## 2. Три машины пайплайна

| # | Машина | Кто | Делает | Проект |
|---|--------|-----|--------|--------|
| 1 | Броадкастер | оператор (Артур) | Sheets → yt-dlp → LLM → анонсы в Docs/Telegram → **после всех анонсов выдаёт пакет для планера в Telegram** | `broadcaster` |
| 2 | Планер | владелец канала | пакет → сверка с YouTube → трансляции → ключи → файл ключей → Google-форма → отчёт | `planers` |
| 3 | Стример | оператор | берёт ключи из ответов формы → стримит | вне ТЗ |

Распространение пакета от оператора к владельцам — руками. Планер сам ничего не скачивает и в Telegram не ходит.

## 3. Термины

- **Слот** — один эфир: дата + время (по Киеву) + язык. В броадкастере это `slot_key = {ddmmyy}_{HHMM}_{lang}` (`app/planning/slots.py::planned_video_slot_key`, `app/pipeline/slot_processing.py::process_slot`). У слота одно название, одно описание и 1..N превью (по числу исходных видео, объединённых в этот эфир).
- **Пакет** — файл `*.bcast`: весь результат одного прогона броадкастера — все даты, все языки, все слоты (§5.1).
- **Канал** — YouTube-канал владельца: имя аккаунта для формы + список языков, за которые канал отвечает. У владельца может быть несколько каналов.
- **Сверка** — сравнение слотов из пакетов с эфирами, реально запланированными на канале. Истина — на платформе (§7.3).
- **Регистрация** — пара (слот, канал), для которой на платформе есть эфир, а у планера — ключ. Единица работы.
- **Файл ключей** — человеко-читаемое представление текущего состояния (§5.5). Производный, руками не правится.
- **Форма** — Google-форма ключей. URL уже есть в конфиге броадкастера (`AppConfig.google.form_url`) и уходит в Telegram через `build_telegram_key_form_reminder`.

## 4. Сквозной сценарий

1. Оператор запускает броадкастер. После публикации всех дат броадкастер собирает пакет и отправляет его документом в тот же Telegram-канал, куда ушли анонсы (`TelegramBotClient.send_document_as_file_bytes`).
2. Оператор пересылает пакет владельцу. Владелец сохраняет файл в `promo\` папки планера.
3. Владелец запускает `planer.bat`. Планер:
   1. читает `config\planer.yaml`, проверяет токен каждого канала (при первом запуске — авторизация в браузере, §5.3);
   2. читает **все** пакеты в `promo\`, раскладывает их слоты в единую карту по `slot_id`, выбрасывает прошедшие (§7.1);
   3. отбирает будущие слоты под языки своих каналов (§7.2);
   4. для каждого канала запрашивает у YouTube список запланированных эфиров и сверяет с картой слотов (§7.3): нет эфира → создать; есть, но название/описание отличаются → исправить; есть и совпадает → пропустить как копию;
   5. для каждого созданного эфира получает ключ (§7.4);
   6. читает форму, проверяет, что для всех её полей есть данные, отправляет новые ключи (§7.5), затем перегенерирует файл ключей (§5.5);
   7. выводит результат по трём поверхностям (§5.6): короткую сводку — в консоль, подробный отчёт — в `logs\{DD-MM-YYYY}_{HHMMSS}_report.md`, диагностику `key=value` — в `logs\{DD-MM-YYYY}_{HHMMSS}_planer.log`; попутно удаляет старьё (§5.7).
4. Владелец смотрит отчёт. Если что-то не так с эфиром — правит или удаляет его на YouTube руками; следующий запуск планера это увидит и пересоздаст (§7.3).

## 5. Форматы данных

Все даты в файлах, именах и отчётах планера — `DD-MM-YYYY`, время — `HH:MM` по Киеву. Два исключения: `start` в манифесте (§5.1) и значения, уходящие в Google-форму, — там дата в `form.date_format` из пакета (сейчас `DD.MM.YYYY`, §7.5); когда отчёт цитирует вариант формы («в форме нет варианта на дату 13.09.2026»), дата приводится как в форме.

### 5.1. Пакет от броадкастера (`*.bcast`)

Контейнер — ZIP с расширением `.bcast` (утверждено). Один файл, внутри текст и картинки, читается `zipfile` из stdlib, «не-zip» расширение отбивает желание править в блокноте; оператор при желании открывает его любым архиватором.

Имя файла: `plan_{DD-MM-YYYY}_{DD-MM-YYYY}_gen{DD-MM-YYYY}-{HHMM}.bcast`
Пример: `plan_14-09-2026_25-09-2026_gen13-09-2026-1015.bcast` — дата первого и последнего слота в пакете, затем момент генерации. Имя — для людей и для быстрой сортировки глазами; **все решения планер принимает по манифесту**, имя файла не парсит (владелец может переименовать при сохранении).

Правила:

- Пакет — весь прогон: все даты, все языки. «Период» — просто минимальная и максимальная дата слотов, никакого другого смысла у него нет.
- `slot_id` = `{DD-MM-YYYY}_{HHMM}_{lang}` — ключ, по которому планер ничего не путает: два эфира различаются хотя бы одним из трёх. Совпадает по смыслу с `slot_key` броадкастера (`160926_1900_uk`), но с однозначной датой.
- `date` — для людей, отчётов и формы (в форму — в `form.date_format`); `time` — для людей и отчётов, в форму не уходит: время эфира стример берёт из объявления. `start` — та же метка в ISO-8601 со смещением, **[РЕШЕНИЕ]** исключение из формата дат для сравнения моментов (второе исключение — значения для формы, §5): по ней планер сравнивает моменты с YouTube (там время в UTC) без базы часовых поясов на машине владельца. Человек её не читает.
- `title`/`description` — ровно те тексты, что ушли в анонс Telegram (`app/publish/telegram_batch_sender.py`), через `resolve_slot_publish_texts` (`app/publish/slot_publish_texts.py`): `SanitizedPublishBlock.title_text` / `description_text`, если блок есть и `is_blocked == False`; иначе для нескольких видео — merge-payload живой санитации, а при её блокировке или отсутствии merge — nomerge-композиция (`numbered_original_titles` + `build_descriptions_summary`); для одного видео — `metadata.title` + `fallback_source_description_text`. В пакет попадает каждая пара (слот, язык), по которой был анонс.
- `previews` — 1..N файлов, все принадлежат этому одному эфиру (по одному на исходное видео). Планер берёт **одно случайное** как обложку трансляции (утверждено: владельцу, как правило, всё равно).
- `form.url` — ссылка из конфига броадкастера как есть (сейчас короткая forms.gle); планер идёт по редиректу и строит адрес formResponse от конечного URL.
- `form.fields` — названия вопросов формы символ в символ; `null` — такого вопроса в форме нет: поле не отправляется и в отчёт не попадает.
- `form.values` — тексты вариантов радио-вопросов по кодам пайплайна (язык, платформа).
- `form.date_format` — strftime-формат даты, с которой начинается вариант вопроса «Время стрима».
- entry-ID по-прежнему не конфигурируются — планер читает их из HTML формы (§7.5).
- `schema_version` — планер отказывается читать пакет с неизвестной мажорной версией и пишет об этом в отчёт.
- `generator` — информационное поле: `project` = значение переменной окружения `LOGGER_NAME` броадкастера (в песочнице restreamer — `pipeline`), `version` — константа экспортера. Планер по этим полям ничего не решает.
- Броадкастер уже отфильтровал прошлое по `now_for_filter` (`app/planning/sheet_loader.py`), но планер фильтрует снова — между генерацией и запуском могут пройти дни.

### 5.2. Конфиг планера: `config\planer.yaml` и `config\channels.yaml`

Два файла, которые владелец редактирует руками: в `planer.yaml` — настройки запуска, в `channels.yaml` — каналы. Разделены потому, что список каналов меняется чаще настроек и его удобно править отдельно.

Язык стримов назначает **оператор** в `channels.yaml` (`languages`). Язык канала на YouTube планер читает только для показа в `--check` и на решения не использует; менять его планер не будет.

Остальное про оба файла: шаблоны `config\planer.example.yaml` и `config\channels.example.yaml` в репо; при первом запуске планер копирует недостающий файл из примера целиком (как описано в `README.config.txt` броадкастера).

**`channels.example.yaml` — единственный шаблон каналов.** В его комментариях по каждому ключу канала: что он делает, какие значения допустимы, что будет при каждом и какое значение действует, если ключ не писать. Значения берутся из кода (`Platform`, `Privacy`, `CHANNEL_ID_PATTERN`, `DEFAULT_*` в `app/config/loader.py`), коды языков — из `form.values.language` пакета. Рабочий `channels.yaml` отличается от примера только значениями и списком каналов, пояснения в нём те же.

```yaml
min_lead_minutes: 60               # слоты, до старта которых меньше — не планировать
keep_days: 30                      # сколько дней хранить пакеты в promo\ и файлы в logs\ (§5.7)

channels:
  - id: yt_ua                      # короткий ключ, латиница; имя файла токена
    platform: youtube
    account_name: "Іван UA"        # ровно так, как должно попасть в форму
    languages: [uk]
    privacy: public                # public | unlisted
    auto_start: true               # эфир стартует сам, когда стример начнёт слать поток
    set_thumbnail: true            # ставить превью из пакета (нужен подтверждённый канал)

  - id: yt_ru
    platform: youtube
    account_name: "Иван RU"
    languages: [ru, en]
```

Чего здесь нет и не будет: логинов, паролей, URL формы, entry-ID, путей к токенам (они выводятся из `id`).

### 5.3. Секреты `secrets\` — как устроена авторизация

В папке два вида файлов, и они принципиально разные.

**`client_secret.json` — «паспорт программы».** Чтобы любая программа могла обращаться к YouTube API, у Google должна быть зарегистрирована сама *программа* (в Google Cloud, в проекте оператора). Результат регистрации — этот файл. Он один на всех владельцев, лежит в дистрибутиве рядом с exe, владелец его не создаёт и не трогает. Для программ типа Desktop Google не считает его секретом (его нельзя не отдать вместе с exe), поэтому ничего страшного в распространении нет.

**`<channel_id>.token.json` — «пропуск канала».** Появляется на машине владельца сам, при первом запуске. Ровно так, как ты описал:

1. Планер видит в `channels.yaml` канал `yt_ua`, ищет `secrets\yt_ua.token.json` — нет.
2. Открывает браузер на странице Google: «Планер просит доступ к управлению вашими трансляциями YouTube». Владелец выбирает нужный Google-аккаунт и, если у аккаунта несколько каналов, — нужный канал. Нажимает «Разрешить».
3. Google возвращает планеру токен, планер сохраняет его как `secrets\yt_ua.token.json`. Единственное право в токене — `https://www.googleapis.com/auth/youtube` (управление своим каналом); к почте, диску и прочему доступа нет.
4. Для канала `yt_ru` — то же самое, файл `secrets\yt_ru.token.json`. Токены лежат рядом и никак не пересекаются: имя файла = `id` канала из конфига.
5. Дальше браузер не нужен: токен обновляется сам. Если Google его отозвал (владелец сменил пароль, удалил доступ) — планер снова откроет браузер для этого канала.

Защита от ошибки «выбрал не тот аккаунт»: сразу после авторизации планер спрашивает у YouTube, какой это канал (`channels.list(mine=true)`), показывает название и записывает `youtube_channel_id` в `state\channels.json` (schema_version 1, запись атомарная). Дальше:

- привязки для ключа нет — она записывается;
- привязка есть и id совпал — обновляются название канала и время авторизации;
- привязка есть и id **другой** — планер ничего не переписывает, говорит владельцу, что токен ведёт на другой канал, и предлагает либо авторизоваться заново, выбрав правильный канал, либо исправить `channels.yaml`.

Перед `--dry-run` и `--status` привязки проверяются по всем каналам; расхождение — остановка с кодом 2, ничего не читается и не записывается. Переавторизовать канал принудительно: `planer.exe --auth yt_ua` (удаляет токен и открывает браузер), все каналы сразу — `planer.exe --auth all`.

На экране согласия Google показывает «Google hasn't verified this app» (§6.1 п.1) — планер предупреждает об этом **до** открытия браузера и говорит, что нажимать: Advanced → Go to ... (unsafe) → Continue.

Механика та же, что уже работает в броадкастере (`app/google/auth.py::_create_oauth_credentials`: `InstalledAppFlow.run_local_server`), только скоуп другой и токен — на канал, а не один на приложение.

Что должен сделать оператор один раз, чтобы это работало у всех, — §6.1. Вся папка `secrets\` в `.gitignore` (уже есть: `client_secret*.json`, `token*.json`).

### 5.5. Файл ключей `keystreams\keys.txt`

Файл нужен в одном случае: форма не сработала, и ключ передают стримеру руками. Поэтому он устроен вокруг ключа. Полностью перегенерируется при каждом запуске: блок на каждый будущий эфир владельца, у которого есть ключ. **Слоты внутри `min_lead_minutes` сюда входят наравне с остальными** (§7.2): именно перед эфиром файл нужнее всего, и терять из него ключ нельзя. Их ключ, как и любой другой, читается с площадки; эфир для такого слота не найден — ключа нет и блока нет. Ключ эфира, созданного не планером, тоже виден — он читается с платформы (`liveStreams.list(part=cdn)`).

Шапка из трёх строк объясняет, что это за файл и что с ним делать. Дальше — блок на стрим, между блоками пустая строка, сортировка по дате, времени, языку. Первая строка блока — дата, время по Киеву, язык и аккаунт; под ней с отступом четыре поля, **ключ — первым**: он не уезжает за край экрана, какой бы длинной ни была причина в строке «форма».

```
# Ключи трансляций. Сгенерировано планером 13-09-2026 12:00.
# Файл перезаписывается на каждом запуске — не править.
# Если в строке «форма» стоит «НЕ передан» — передайте ключ стримеру вручную.

16-09-2026 19:00  uk  Іван UA
  ключ   xxxx-xxxx-xxxx-xxxx-xxxx
  поток  rtmp://a.rtmp.youtube.com/live2
  эфир   https://www.youtube.com/watch?v=abc123
  форма  передан 13-09-2026 12:00

16-09-2026 21:00  ru  Иван RU
  ключ   yyyy-yyyy-yyyy-yyyy-yyyy
  поток  rtmp://a.rtmp.youtube.com/live2
  эфир   https://www.youtube.com/watch?v=def456
  форма  НЕ передан — форма недоступна (HTTP 503)

17-09-2026 19:00  uk  Іван UA
  ключ   zzzz-zzzz-zzzz-zzzz-zzzz
  поток  rtmp://a.rtmp.youtube.com/live2
  эфир   https://www.youtube.com/watch?v=ghi789
  форма  ключ прежний, в этом запуске не передавался
```

Строка «форма» говорит **только о том, что планер сделал в этом запуске**, — о прошлых запусках планер ничего не утверждает, он их не знает: «передан <время>» — ключ новый и отправлен сейчас; «НЕ передан — <причина>» — ключ новый, отправка не подтвердилась, ключ надо передать вручную; «ключ прежний, в этом запуске не передавался» — эфир совпал или исправлен, а также все блоки режима `--status`. Шапка просит передать вручную только ключи с «НЕ передан»: прежний ключ повторно не передаётся, чтобы не задвоить его у стримера (§7.5).

Формат — `.txt`, а не CSV: читается глазами, не ломается Excel'ем. Значков (✅, ❌) нет: консоль Windows рисует их квадратами, в файлах они ломают выравнивание. Экспорт в `.csv` — при необходимости, отдельным флагом.

### 5.6. Консоль, отчёт и лог

**У каждой поверхности свой читатель, одно и то же в двух местах не печатается.**

| Поверхность | Читатель | Что в ней |
|---|---|---|
| консоль | владелец, сразу после запуска | что произошло и куда смотреть; до 15 строк при обычном прогоне, без markdown |
| `logs\{DD-MM-YYYY}_{HHMMSS}_report.md` | владелец; можно переслать оператору | то же, с подробностями |
| `logs\{DD-MM-YYYY}_{HHMMSS}_planer.log` | разработка | диагностика `key=value`; владельцу не адресован |

Отчёт и лог одного прогона лежат рядом в `logs\` — общий префикс времени связывает их в пару. Счётчики считаются один раз (`build_totals` в `app/output/report.py`) и используются и в строке «Итог» отчёта, и в консоли; двух независимых подсчётов одних и тех же чисел нет. Значков ✅ и ❌ нет ни в консоли, ни в отчёте, ни в `keys.txt` — вместо них слова: «ключ передан в форму», «ключ в форму НЕ передан — <причина>».

**Консоль** (`app/output/console.py`). Заголовок, счётчики, строки внимания, пути:

```
Планер — 13-09-2026 13:20

  пакеты          1   слотов 4, моих 1
  создано         1   17-03-2027 19:00 ru -> Osvald.X, ключ передан в форму
  исправлено      0
  совпадает       0
  пропущено       3   нет канала: en (2), uk (1)
  ошибок          0

  ключи   keystreams\keys.txt
  отчёт   logs\13-09-2026_132051_report.md
  лог     logs\13-09-2026_132050_planer.log
```

Правила: нулевой счётчик печатается (владелец видит, что раздел проверен), но без подробностей; подробность — только у ненулевого: один исход — сам исход, несколько созданных — «ключ передан в форму: N из M», пропуски — сгруппированы по причине, у «нет канала» — число слотов на каждый язык, чтобы сумма сходилась со счётчиком. Ошибки (`ошибка:`), неподтверждённые отправки формы (`форма:`), непрочитанные пакеты (`пакет:`) и предупреждения (`внимание:`) печатаются полным текстом всегда; прочее подробное — только в отчёте. `--dry-run` — тот же рендер со своим заголовком и счётчиками «создать» / «исправить»; `--status` — счётчики «запланировано» и «ошибок».

**Отчёт.** Сначала то, ради чего его открывают, потом справка: заголовок, строка «Итог», Ключ не дошёл до стримера, Ошибки, Предупреждения, Расхождения с платформой, Создано, Исправлено, Уже запланировано, Перенесён или отменён, Пропущено, Пакеты, Особенности площадки. **Раздел без строк не печатается вовсе.**

**Ключ не дошёл до стримера** — самый дорогой сбой: эфир на канале стоит, зрители его видят, а трансляции не будет. Поэтому каждый новый ключ, отправку которого форма не подтвердила, отчёт показывает сразу под «Итогом»: префикс «дата время язык -> аккаунт», причина отказа формы и что делать — передать ключ из `keys.txt` вручную. Счётчики от раздела не меняются: исход остаётся в «Создано», число ошибок в «Итоге» прежнее. В консоли этот случай уже виден строкой `форма:`.

**Предупреждения запуска и особенности площадки.** Предупреждения этого запуска — обложка не встала, язык или категория не записаны, аудитория была «для детей», возрастное ограничение, настройки видео, перечитывание фактов, сохранённый ответ формы — идут и в консоль (`внимание:`), и в отчёт (раздел «Предупреждения»). Постоянные особенности площадки — у эфиров YouTube всегда есть живой чат; у совпавших и исправленных эфиров ключ прежний и повторно в форму не уходит — не про сегодняшний запуск: они печатались бы на каждом запуске и приучили бы владельца не читать блок «внимание». Поэтому они идут **только в отчёт**, последним разделом «Особенности площадки», по строке на особенность.

**Факты платформы.** После действий по каждому эфиру, который планер считает своим, он один раз перечитывает его с платформы (`videos.list(part=snippet,status,contentDetails)` плюс уже прочитанный поток) и кладёт в объект. Это единственный способ увидеть язык, аудиторию и возрастное ограничение: в ответе `liveBroadcasts.list` их нет. В лог по объекту идут три строки `key=value`: `broadcast_expected` (что хотели), `broadcast_actual` (что было в списке эфиров) и `broadcast_facts` (что лежит на платформе). В отчёт эти данные попадают **только** при расхождении — раздел «Расхождения с платформой», строка на поле: название, описание (длина и первые 200 символов, целиком не выводится), момент старта, маркер потока, язык, аудитория. Совпало всё — раздела нет. Расхождение не ошибка и код выхода не меняет: это диагностика, следующий запуск исправит текст штатным путём.

```
# Планер 1.0.0 — отчёт 13-09-2026 12:00

Итог: создано 2, исправлено 1, совпадает 1, пропущено 3, ошибок 1. Файл ключей: keystreams\keys.txt

## Ключ не дошёл до стримера
- 18-09-2026 19:00 uk -> Іван UA — форма не подтвердила запись ответа (notConfirmed); эфир на канале стоит — передайте ключ стримеру из keys.txt вручную

## Ошибки
- 19-09-2026 19:00 uk -> Іван UA — YouTube: liveStreamingNotEnabled (на канале не включены трансляции)

## Создано (2)
- 16-09-2026 19:00 uk -> Іван UA — эфир создан, ключ передан в форму
- 18-09-2026 19:00 uk -> Іван UA — эфир создан, ключ в форму НЕ передан — форма не подтвердила запись ответа (notConfirmed); повторно планер его не отправит, передайте ключ стримеру из keys.txt вручную

## Исправлено (1)
- 17-09-2026 19:00 uk -> Іван UA — на YouTube было другое описание; обновлено. Ключ и ссылка прежние

## Уже запланировано, совпадает (1)
- 16-09-2026 21:00 ru -> Иван RU — https://www.youtube.com/watch?v=def456

## Пропущено
- 14-09-2026 19:00 uk — уже прошло
- 15-09-2026 19:00 en — нет канала для языка en
- 13-09-2026 12:30 uk — до старта меньше 60 минут

## Пакеты
- plan_14-09-2026_25-09-2026_gen13-09-2026-1015.bcast — принят, слотов 24, из них под мои языки 9
- plan_07-09-2026_11-09-2026_gen06-09-2026-1000.bcast — все слоты в прошлом, ничего из него не планируется

## Особенности площадки — так устроена площадка, это не про этот запуск
- у совпавших и исправленных эфиров ключ прежний, повторно в форму он не отправляется: повтор задвоил бы ключ у стримера. Если стример ключа не получил — передайте его из keys.txt вручную или удалите эфир на YouTube: планер создаст его заново с новым ключом и отправит
```

Если в запуске есть совпавшие или исправленные эфиры, в разделе «Особенности площадки» — **одна строка на запуск**, а не по строке на эфир: у таких эфиров ключ прежний и повторно в форму он не отправляется, чтобы не задвоить ключ у стримера; если стример ключа не получил — передать его из `keys.txt` вручную или удалить эфир на YouTube, и планер создаст его заново с новым ключом и отправит.

Коды выхода: `0` — всё, что можно было сделать, сделано; `1` — есть ошибки; `2` — ошибка конфигурации/авторизации (ничего не делалось); `3` — в `promo\` нет пакетов.

### 5.7. Чистка старья

Единственное место, где планер удаляет файлы. На каждом запуске, кроме `--dry-run`, из `promo\` и `logs\` удаляются файлы, изменённые раньше, чем `keep_days` дней назад (§5.2, по умолчанию 30). Вложенные папки не трогаются; остальные папки (`keystreams\`, `state\`, `secrets\`, `config\`) — тоже. Чистка идёт до записи отчёта, чтобы отчёт этого запуска под неё не попал.

Имя файла и лога, и отчёта — по одному шаблону «дата_время_наименование»: `{DD-MM-YYYY}_{HHMMSS}_planer.log`, `{DD-MM-YYYY}_{HHMMSS}_report.md`. Так они лежат в `logs\` одним хронологическим списком.

## 7. Алгоритм

### 7.1. Сбор слотов из `promo\`

1. Берутся все `*.bcast` из `promo\` — сколько бы их там ни было; вложенные папки не сканируются (их там и не должно быть). Битый архив/манифест → отчёт «пакет повреждён», файл не трогается.
2. Пакеты читаются **все**, в порядке `generated_at` от старого к новому, и их слоты складываются в одну карту `slot_id → слот`. Один и тот же `slot_id` в двух пакетах → остаётся версия из более нового пакета (у него свежее название/описание). Так планер ничего не путает: что бы ни лежало в `promo\`, на выходе — один список уникальных (дата, время, язык). При разборе каждый слот получает форму своего пакета (`Slot.form`) — дальше ключ этого слота уходит именно туда, и лишних сопоставлений «слот → пакет → форма» по дороге нет.
3. Из карты выбрасываются слоты с `start <= сейчас` — прошедшее не планируется никогда, из какого бы пакета оно ни пришло.
4. Пакеты остаются в `promo\` как есть: планер их не перемещает, не переписывает и во время работы не удаляет. Единственное исключение — чистка старья по `keep_days` (§5.7), она сносит файлы старше срока независимо от их содержимого. Пакет, у которого все слоты в прошлом, просто отмечается в отчёте строкой «все слоты в прошлом, ничего из него не планируется» — его слоты уже отброшены на шаге 3 и ни на что не влияют. Разбирает папку владелец, когда сочтёт нужным.

Про «пакет 14–25.09, запустили 16.09»: читается, слоты 14–15.09 в отчёт как прошедшие, 16–25.09 идут на сверку. Дублей не будет не потому, что планер помнит, что делал, а потому что перед созданием он спрашивает YouTube, есть ли уже такой эфир (§7.3).

### 7.2. Отбор слотов под каналы

Для каждого слота из карты:

- `start - сейчас < min_lead_minutes` → объект всё равно создаётся, но с признаком **too_late**: сверка по нему идёт **только на чтение** — эфир опознаётся по минуте старта и маркеру, ключ и ссылка берутся из `liveStreams.list` (тот же кеш потоков, `liveBroadcasts.list` — по-прежнему раз на канал). Никаких действий: не создаёт, не исправляет, не привязывает поток, не трогает настройки видео, в форму не отправляет никогда; решение остаётся too_late, даже если эфир не найден. В отчёте он в разделе «пропущено», ключ — в `keys.txt` (§5.5); эфир не найден — ключа нет и строки нет. Выбрасывать такой слот нельзя: ключ исчез бы из файла ровно перед эфиром;
- язык слота не входит ни в один `channels[].languages` → «нет канала для языка», пропуск (нормально: у владельца может не быть канала под каждый язык);
- иначе для **каждого** канала, у которого язык в списке, создаётся **объект запланированного эфира**. Два канала на один язык → два объекта, то есть два эфира.

**Объект — единственная рабочая единица планера: один объект = один эфир одного слота на одном канале.** Он рождается здесь и живёт до отчёта, накапливая три слоя:

1. *из пакета* — слот, пакет-источник (превью и `package_id`), канал и «как эфир должен выглядеть» (спека). Задаётся при рождении и дальше не меняется;
2. *с площадки* — найденный эфир, его поток и «как он выглядит сейчас» (спека). Заполняет сверка;
3. *результат* — `broadcast_id`, ссылка, `stream_url`, ключ, признак «ключ новый», статус формы этого запуска, ошибка. Ключ и ссылку заполняет только площадка: сверка — из найденного эфира, действия — из ответа на создание и привязку потока. Памяти о прошлых запусках у планера нет.

Порядок важен: слоты сливаются по `slot_id` (§7.1 п.2) **до** размножения по каналам. Сливать объекты нельзя — один слот из двух пакетов дал бы два эфира на один канал.

### 7.3. Сверка с платформой

Истина об эфирах — на YouTube. **Ключ потока и ссылка на эфир всегда читаются с площадки**: своей памяти о прошлых запусках у планера нет. Планер связывает YouTube и форму через ключ потока и больше ничего не видит. Поэтому перед любым созданием:

1. Для каждого канала запрашивается список запланированных эфиров: `liveBroadcasts.list(broadcastStatus=upcoming, part=snippet,contentDetails,status)`, с пагинацией. Параметр `mine` сюда не добавляется: у `liveBroadcasts.list` фильтры `id` / `mine` / `broadcastStatus` взаимоисключающие, вместе дают 400 `incompatibleParameters` (проверено 12-09-2026); `broadcastStatus` и так возвращает эфиры авторизованного пользователя. Для каждого — `snippet.scheduledStartTime` (UTC), `snippet.title`, `snippet.description`, `contentDetails.boundStreamId`.
2. Слот считается **совпавшим** с эфиром, если совпадает момент старта с точностью до минуты (`slot.start` и `scheduledStartTime` сравниваются в UTC). Если на канале в одну минуту несколько эфиров (канал обслуживает `[ru, en]`, оба слота на 19:00) — различает **маркер**: планер всегда пишет `slot_id` в название привязанного потока (`liveStreams.snippet.title`, зрителям не видно) и читает его через `liveStreams.list(id=boundStreamId)`. Эфир без маркера (создан руками) при единственном кандидате на эту минуту считается совпавшим, при нескольких — в отчёт «не могу различить, разберитесь вручную», слот не трогается.
3. По результату сверки для каждой пары (слот, канал):

| На YouTube | Действие |
|---|---|
| эфира нет | **создать** (§7.4); новый ключ в форму |
| эфир есть, название и описание совпадают | **копия — пропустить**; ключ и ссылка — с площадки, в форму не отправляются; в отчёт «уже запланировано» |
| эфир есть, название или описание отличаются | **исправить** (см. ниже); ключ прежний, в форму не отправляется; в отчёт «исправлено» |
| эфир есть, привязанного потока нет | **создать поток с маркером и привязать** к этому эфиру (§7.4 п.2–3), новый ключ в форму; в отчёт «эфир был без потока, поток привязан». Не удалось привязать — ошибка пары |
| на YouTube эфир на время, которого нет ни в одном слоте | не трогать; в отчёт **не** попадает (это чужой/ручной эфир) |

**Сравниваются не слот и ответ площадки, а два объекта одного типа — спеки.** Спека строится из слота и из ответа площадки по одним и тем же правилам: название — `strip()`, описание — CRLF/CR → LF, хвостовые пробелы строк и края снимаются, затем обрезка по лимитам площадки (§7.4 п.1). **Обрезка применяется к обеим сторонам обязательно**: иначе слот с названием длиннее лимита считался бы отличающимся на каждом запуске и эфир правился бы бесконечно. Различия ищутся только в названии и описании: по времени и маркеру эфир опознают, а не исправляют. Проверено живым прогоном 13-09-2026: **YouTube возвращает описание байт в байт таким, каким оно отправлено** — отправлено 1198 символов, получено 1198, начало совпадает. Дополнительной нормализации на стороне планера не нужно, текущей (переводы строк и края) достаточно.

Проверено живым прогоном 13-09-2026: **код языка возвращается в том же виде, в каком записан** — записали `ru`, прочитали `ru`, без региона и без приведения регистра. Сопоставлять коды языка слота и площадки можно напрямую, нормализация не нужна. `videos.update(part=snippet)` с полным `snippet` отработал на эфире в статусе `upcoming` и остальные поля не сбросил; read-modify-write целиком остаётся обязательным (§7.4 п.5).

Исправление (`liveBroadcasts.update`, `part=snippet`) заменяет переданную часть ресурса целиком, поэтому вместе с названием и описанием всегда отправляются `scheduledStartTime` и `categoryId` найденного эфира; `contentDetails` в `part` не включается — он потребовал бы обязательный `monitorStream`.

**Как исправлять — [РЕШЕНИЕ].** Ты предложил отменить старый эфир и запланировать новый. Предлагаю по умолчанию делать иначе — обновлять на месте (`liveBroadcasts.update`, `part=snippet`: название, описание, превью). Результат для зрителя тот же (изменённый эфир), но ключ и ссылка не меняются, значит форму переотправлять не надо, и вопрос «что сделает стример с повторным ключом» просто не возникает. Отмена + пересоздание остаётся запасным путём, если для какого-то поля `update` окажется невозможен **[ПРОВЕРИТЬ]**. Если ты настаиваешь на пересоздании — это одна строчка в конфиге канала (`replace_mode: recreate`), но тогда стример обязан брать последний ответ по `slot_id`.

Перенос времени в Sheets даёт другой `slot_id` → на старое время эфира в слотах нет → по таблице выше он не трогается и в отчёт не попадает. **[РЕШЕНИЕ]** Дополнительно выводить в отчёт эфиры с маркером планера, время которых пропало из слотов, как «перенесён или отменён? эфир не удалён» — чтобы владелец мог убрать их руками. Без маркера (ручные эфиры) — не выводить.

### 7.4. Создание эфира (YouTube)

`platforms/youtube.py`, YouTube Data API v3 через `googleapiclient`, повторы через `app/google/api_retry.py`:

1. `liveBroadcasts.insert` — `snippet.title` (≤100 символов, безопасная обрезка по образцу `app/core/safe_trim.py`), `snippet.description` (≤5000), `snippet.scheduledStartTime` = `slot.start` в RFC3339, `status.privacyStatus` = `channel.privacy`, `status.selfDeclaredMadeForKids = false`, `contentDetails.enableAutoStart = channel.auto_start`, `contentDetails.enableAutoStop = true`, `contentDetails.latencyPreference = "normal"`.
2. `liveStreams.insert` — `snippet.title = slot_id` (маркер, §7.3), `cdn.ingestionType = "rtmp"`, `cdn.resolution = "variable"`, `cdn.frameRate = "variable"`. Из ответа: `cdn.ingestionInfo.streamName` (ключ), `cdn.ingestionInfo.ingestionAddress` (stream_url). Ключ проверяется регулярным выражением `^[a-z0-9]{4}(-[a-z0-9]{4}){3,4}$` (5 групп `xxxx-xxxx-xxxx-xxxx-xxxx` — текущий формат, 4 группы — старые ключи); константа `YOUTUBE_STREAM_KEY_PATTERN` в `platforms/youtube.py` — единственный источник. Несовпадение — ошибка пары (слот, канал): эфир не засчитан, форма не отправляется, в отчёт «ключ неожиданного формата». Та же проверка — при чтении ключей чужих эфиров для `keys.txt` (§5.5): не прошедший ключ выводится с пометкой «формат?».
3. `liveBroadcasts.bind` — привязка потока к эфиру.
4. `thumbnails.set` — если `channel.set_thumbnail` и у слота есть превью: берётся `random.choice(slot.previews)`. Ошибка **не фатальна** (требует подтверждённого канала) — в отчёт предупреждением.
5. **Настройки ресурса видео — одним проходом.** Язык, категория и аудитория у `liveBroadcast` не лежат: они у ресурса `videos` с тем же id. Планер делает **одно** чтение `videos.list(part=snippet,status)` и **не больше одной** записи `videos.update(part=snippet,status)`: выставляет `snippet.defaultLanguage` и `snippet.defaultAudioLanguage` = язык слота, `snippet.categoryId` = категория канала, `status.selfDeclaredMadeForKids = false`. Совпало всё — записи не делается вовсе. Обе части отправляются целиком: частичная часть затирает непереданные поля, в том числе `status.privacyStatus` и `snippet.title`. Проход выполняется у каждого эфира, который планер считает своим (создан, привязан, исправлен, подтверждён), на каждом запуске — настройка канала в Студии может перебить и аудиторию, и категорию. Что именно пришлось поправить, уходит в отчёт предупреждением. Сбой не фатален: эфир и ключ остаются.

   **Категория эфира** берётся из `channels.yaml` (`category_id`, по умолчанию `22` — People & Blogs) и отправляется в `snippet.categoryId` при создании и при каждом исправлении. Справочника категорий у планера нет: неизвестный идентификатор вернёт ошибку площадки, и она попадёт в отчёт обычным путём. Категория участвует в сравнении с платформой (§5.6).

   Прежний **язык эфира** — часть того же прохода, отдельного вызова больше нет. У `liveBroadcast` поля языка нет: оно у ресурса `videos` с тем же id. Строго read-modify-write: `videos.list(part=snippet, id=broadcast_id)` → взять **весь** `snippet` → добавить `defaultLanguage` и `defaultAudioLanguage` = язык слота → `videos.update(part=snippet)` целиком, вместе с `title` и `categoryId`. Частичный `snippet` затирает непереданные поля — отправлять неполный запрещено. Ошибка **не фатальна**: эфир и ключ в силе, в отчёт предупреждением.
6. **Аудитория эфира — всегда «не для детей».** При создании уходит `status.selfDeclaredMadeForKids = false`, но настройка аудитории всего канала в Студии может его перебить, а у найденного чужого эфира флага может не быть вовсе. Поэтому на **каждом** запуске у любого эфира, который планер считает своим (создан, привязан, исправлен, подтверждён), флаг проверяется и при необходимости снимается. `liveBroadcasts.update` это поле не принимает — только `videos.update(part=status)`, и строго read-modify-write: `videos.list(part=status)` → взять **весь** `status` → выставить `selfDeclaredMadeForKids = false` → отправить `status` целиком. Частичный `status` затирает непереданные поля, в том числе `privacyStatus`. Факт правки — строка в лог и предупреждение в отчёт: владелец должен знать, что настройка канала расходится с тем, что делает планер.
   Запланированное время старта у ресурса `videos` лежит в части **`liveStreamingDetails`** (`liveStreamingDetails.scheduledStartTime`), а не в `snippet`: у `liveBroadcasts` оно в `snippet.scheduledStartTime`, и перепутать эти два места легко. Прогон 13-09-2026 01:21 показывал из-за этого ложное расхождение «время старта — на платформе: -». Часть обязана быть в списке частей запроса `read_facts`.
7. **Возрастное ограничение 18+ (`contentDetails.contentRating.ytRating == ytAgeRestricted`) через YouTube Data API только читается.** Передача `contentDetails.contentRating` в `insert` или `update` даёт 400. Программно снять ограничение нельзя: планер видит его при чтении фактов и пишет в отчёт предупреждение со ссылкой на эфир — снимать вручную в Студии. Не пытаться ставить это поле.
8. `broadcast_url = https://www.youtube.com/watch?v={broadcast_id}` — только через `broadcast_url_for`, второго шаблона в коде нет.

**Временная недоступность.** Живой прогон 13-09-2026 00:33 упал на HTTP 503 в `liveBroadcasts.list`: канал целиком ушёл в ошибку, эфир не создался. Исчерпали попытки — `transportFailed`, канал в ошибку, остальные каналы обрабатываются.

На каждый эфир — свой `liveStream` (свой ключ), а не общий ключ канала: при `enableAutoStart` и нескольких эфирах на одном ключе неоднозначно, какой стартует. `enableAutoStart = true` по умолчанию: стримеру достаточно начать слать поток.

Если шаги 1–3 упали посередине — созданные объекты записываются в `last_error`, следующий запуск при сверке увидит незавершённый эфир без маркера или без потока и доделает/пересоздаст; уборка «сирот» — по отчёту вручную (v1).

### 7.5. Отправка в форму

Порядок — ровно как ты описал: сначала форма, потом проверка, потом отправка.

1. **URL формы** — только из пакета (`form.url`), и ниоткуда больше: в коде и в `planer.yaml` ссылок на формы нет. У каждого слота форма своя — та, что лежит в пакете-победителе этого `slot_id` (§7.1 п.2), так что два пакета рядом могут вести в разные формы, и это нормально. `GET viewform` делается по одному разу на каждый уникальный `form.url` запуска, структура кэшируется по URL — не «раз в запуск».
2. **Какие поля есть** — из HTML формы: Google кладёт структуру вопросов в скрипт `FB_PUBLIC_LOAD_DATA_` на странице; из него для каждого вопроса берутся название, `entry.NNN`, обязательность, тип (текст / радио), тексты вариантов и номер раздела, плюс переходы «вариант вопроса «Платформа» → раздел». Раскладка подтверждена живым прогоном 13-09-2026 (13 вопросов, 5 разделов): элементы формы — `payload[1][1]`; разделы разделяются элементами-разрывами (тип 8), раздел 0 — всё до первого разрыва; у разрыва, как и у вопроса, в `item[0]` лежит идентификатор. **Переход у варианта (`option[2]`) задан идентификатором целевого раздела — это `item[0]` его разрыва (у «You Tube» тренировочной формы — `1281939289`), а не порядковым номером.** Поэтому при разборе ведётся карта «идентификатор разрыва → номер раздела», и переход переводится через неё; идентификатор, которого в карте нет, переходом не считается — вариант остаётся без цели. Отрицательные значения — служебные коды Google («следующий раздел», «отправить форму»; у разрывов тренировочной формы встречается `-3`), а не разделы, переходом они тоже не считаются. Это и есть причина, по которой entry-ID нигде не конфигурируются: форма сама говорит, что у неё есть. Если структуру прочитать не удалось — форма не отправляется вообще, в отчёт «не смог прочитать форму», ключи при этом уже в `keys.txt`. Скачанный HTML сохраняется в `logs\{DD-MM-YYYY}_{HHMMSS}_form_page_{хеш URL}.html`, путь — строкой в разделе «Предупреждения». Без этого файла раскладку `FB_PUBLIC_LOAD_DATA_` нечем разобрать. Структура читается по одному разу на каждый уникальный `form.url` запуска и кэшируется по URL: два пакета рядом могут вести в разные формы.
3. **Сопоставление и значения** — название вопроса ↔ поле данных через `form.fields` из пакета (§5.1); поля с `null` не отправляются и в отчёт не попадают. Значение — по типу вопроса:
   - текстовый — как есть: `account_name`, `stream_key`;
   - радио — только текст одного из вариантов этого вопроса:
     - `language` → `form.values.language[<язык слота>]`;
     - `platform` → `form.values.platform["youtube"]`;
     - `date` → вариант, текст которого начинается с даты слота в формате `form.date_format`;
     - `stream_url` → вариант, равный `ingestionAddress` из API после нормализации обеих строк (нижний регистр, без хвостового слэша).

   Правило: планер **никогда** не отправляет значение, которого нет среди вариантов вопроса. Нет варианта (например, даты слота нет в «Время стрима») — ошибка пары (слот, канал): в отчёт «в форме нет варианта на дату DD.MM.YYYY, попросите владельца формы добавить», в `keys.txt` — «не удалось передать». Повтора в следующий запуск **нет**: эфир уже создан, и следующий запуск найдёт его с прежним ключом (п. «Когда отправлять» ниже) — ключ стримеру передаётся из `keys.txt` вручную.

   Перед отправкой: у каждого обязательного вопроса пройденных разделов (раздел 1 и раздел YouTube) есть значение, `stream_key` прошёл проверку §7.4. Вопросы непройденных разделов (Facebook / Rumble / другое) игнорируются.
4. **Отправка** — `POST formResponse` конечного URL формы (после редиректа forms.gle) с `entry.*` вопросов пройденных разделов, плюс `fvv=1`, `pageHistory` и `fbzx` со страницы. **Пройденные разделы** считаются так: раздел вопроса-развилки («Платформа») и раздел, на который ведёт выбранный вариант по карте переходов из п.2; карта пуста или перехода нет — раздел 0 и разделы всех заполненных вопросов. `pageHistory` принимает **только порядковые номера разделов с нуля**, а не идентификаторы из п.2: живой прогон 13-09-2026 отправил `pageHistory=0,1281939289` и получил HTTP 400, правильно для этой формы — `0,1`. Защита независимо от перевода в п.2: номер, попадающий в `pageHistory`, обязан лежать в диапазоне от 0 до числа разделов минус один; номер вне диапазона отбрасывается, и работает запасное правило. Вычисленные номера пишутся в лог отдельной строкой вместе с исходными значениями: вопрос-развилка, выбранный вариант, прочитанный идентификатор перехода и номер, в который он превратился. Форма многостраничная: в POST передаётся `pageHistory` с номерами пройденных разделов (раздел 1 и раздел YouTube). Проверено живой отправкой 13-09-2026 03:01: значение `0,1` принято, ответ записан в таблицу ответов тренировочной формы. `requests`, таймаут 30 с, 3 попытки с нарастающей паузой на сетевые ошибки и 5xx.
5. **Подтверждение** — по структуре страницы ответа, не по её языку (опыт ниже). Ответ записан, если одновременно: HTTP 200; это страница Google Forms (в теле есть `FB_PUBLIC_LOAD_DATA_` — пустой или чужой ответ 200 доставкой ключа не считается); в теле нет ни одного `entry.<цифры>`; в теле нет `fbzx`. Функция одна — `read_confirmation` в `form/submitter.py`. Текстовые маркеры «ответ записан» (`CONFIRMATION_MARKERS`: «your response has been recorded», «відповідь було записано», «ответ записан») остаются, но **только как сигнал в лог**, решения они не принимают. Строки `form_confirmed` / `form_not_confirmed` печатают оба сигнала: `http_status`, `entry_fields`, `fbzx`, `form_page`, `marker` (какой совпал или `None`); у `form_not_confirmed` — ещё заголовок страницы и путь сохранённого тела. POST на `formResponse` по-прежнему уходит с `Accept-Language: en` и `hl=en` (GET страницы формы — без изменений): это безвредно, но язык страницы Google не гарантирует, поэтому проверка от него не зависит. Не подтверждено — ключ не передан (в `keys.txt` — «НЕ передан»), повтора не будет (см. «Когда отправлять»), а тело ответа сохраняется в `logs\{DD-MM-YYYY}_{HHMMSS}_form_response_{хеш URL}.html`, путь — в отчёт.

**Коды исходов отправки** (в лог, в отчёт и в `keys.txt`): `structureUnreadable` — форму не прочитали; `missingOption` — нужного варианта в вопросе нет (дата, язык, площадка, Stream-URL); `requiredMissing` — обязательный вопрос пройденного раздела остался без значения; `transportFailed` — форма недоступна (сеть или 5xx, 3 попытки с нарастающей паузой; на 4xx повтора нет); `notConfirmed` — страница ответа не прошла структурную проверку п.5 (отказ формы или не страница формы). Любой из них — не ошибка эфира: эфир создан, ключ в `keys.txt`. Но **неподтверждённая отправка даёт код выхода 1**: стример ключа не получил, и молчать об этом нельзя.

Операционное следствие: дубль в таблице у стримера возникает штатно — когда владелец удалил эфир и планер создал новый с новым ключом, в таблице появляется вторая строка по тем же дате, каналу и языку. Планер чистить форму не может и не должен, поэтому правило «брать последнюю строку по дате, каналу и языку» — правило стороны стримера; оно идёт в README этапа 5.

Когда отправлять: отправка идёт **отдельным финальным проходом** по всем объектам запуска, после действий, до записи `keys.txt`. **В форму уходит только новый ключ — полученный в этом запуске**: при создании эфира и при привязке потока к эфиру без потока. Эфир на площадке уже есть и ключ прежний (совпал или исправлен) — в форму не отправляется **никогда**, даже если прошлая отправка не подтвердилась, даже если эфир создан руками. Статус отправки живёт только внутри запуска.

Почему так: повторная отправка задвоила бы ключ у стримера, а отличить «стример ключ получил» от «не получил» планер не может — он видит только YouTube и форму. Разбираться с этим — дело оператора, а не планера. Если стример ключа не получил, у владельца два пути: передать ключ из `keys.txt` вручную или удалить эфир на YouTube — следующий запуск создаст его с новым ключом и отправит (§5.6, раздел отчёта «Особенности площадки»). Код выхода: неподтверждённая отправка нового ключа — `1` (стример ключа не получил); отсутствие отправки по совпавшему эфиру ошибкой не считается и код выхода не меняет.

Как стример поведёт себя с ключом по тому же слоту, пришедшим после удаления и пересоздания эфира, — вне ТЗ (решено: проблема стримера). `slot_id` в форму не уходит (§6.1 п.2): различать ответы стример может только по дате, языку и названию канала, последний ответ по этой тройке — актуальный.

### 7.6. Режимы запуска

`planer.exe` через `planer.bat` — оба в корне программы, ничего не спрятано в подпапках (как `bot_main.bat` в броадкастере); окно не закрывается до Enter. `planer.bat` один на оба случая: если рядом лежит `planer.exe` (установленная программа), запускается он; иначе (репо) — `python -m app.main` из `.venv_planers`:

- без аргументов — полный цикл §4;
- `--dry-run` — читает пакеты и **сверяется с YouTube** (только чтение), но ничего не создаёт, не исправляет и в форму не шлёт; в отчёте — что было бы сделано; `keys.txt` не меняется;
- `--check` — по каждому каналу: есть ли токен, на какой канал он ведёт, совпадает ли с привязкой, язык канала на YouTube (справочно), языки из channels.yaml и число запланированных эфиров; ноль эфиров — не ошибка;
- `--auth <ключ>` или `--auth all` — принудительная переавторизация канала из channels.yaml (или всех каналов подряд);
- `--status` — сверка + перегенерация `keys.txt` и отчёта без пакетов из `promo\` (что сейчас запланировано и с какими ключами);
- `--debug` — подробный лог;
- `--version` — номер версии планера (`Планер 1.0.0`) и выход с кодом 0; ничего не читает и не создаёт. Номер — единственная константа `APP_VERSION` в `app\version.py`; он же в строке лога `run_started` и в заголовке отчёта («# Планер 1.0.0 — отчёт …»), в консоль не печатается.

Первый запуск без `config\planer.yaml` или `config\channels.yaml` → копирует недостающее из примеров, завершается с кодом 2 и подсказкой. Нет `secrets\client_secret.json` — код 2 и просьба взять файл у оператора; к YouTube планер при этом не обращается.

Что ставит инсталлятор. Папка и права — как в `installer.iss` броадкастера: мастер спрашивает «для всех пользователей / только для меня» и всегда показывает страницу выбора папки; по умолчанию `{autopf}\Planer` — для «только для меня» это `%LOCALAPPDATA%\Programs\Planer`, для «для всех» — `C:\Program Files\Planer` (с запросом прав администратора). Кладутся: `planer.exe` (с иконкой `planers.ico`) и `_internal\`, `planer.bat`, `planers.ico`, `config\planer.example.yaml` и `config\channels.example.yaml` (рабочие yaml создаёт программа при первом запуске и инсталлятор их не трогает), для local — `secrets\client_secret.json`; создаётся пустая `promo\`. Иконка установщика — тоже `planers.ico`. Ярлыки: на рабочем столе — «Планер» на `planer.bat` с иконкой `planers.ico` (не на exe: окно закрылось бы сразу) и «Планер — пакеты» на `promo\`; в меню «Пуск» — «Планер» на `planer.bat` с той же иконкой. Удаление снимает только положенное инсталлятором: рабочие yaml, токены в `secrets\`, `promo\`, `state\`, `keystreams\`, `logs\` остаются.
