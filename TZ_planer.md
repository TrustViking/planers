## 1. Назначение

Планер — локальная Windows-программа у владельца канала. Она берёт пакет с расписанием эфиров от броадкастера, сверяет его с тем, что уже запланировано на YouTube-каналах владельца, создаёт недостающие трансляции (и исправляет те, у которых изменились название/описание), получает ключи потока, записывает их в человеко-читаемый файл и отправляет в Google-форму ключей. В конце — отчёт: что создано, что уже было, что пропущено, что не удалось.

Планер **не**:

- не стримит и не трогает расписание (источник расписания — Google Sheets броадкастера);
- не обходит Google-форму: форма — единственный канал передачи ключей от владельца к стримеру;
- не трогает эфиры, которые не соответствуют ни одному слоту из пакетов (чужие/ручные эфиры владельца остаются как есть);
- не хранит логины и пароли площадок (§5.3).

## 2. Три машины пайплайна

| # | Машина | Кто | Делает | Проект |
|---|--------|-----|--------|--------|
| 1 | Броадкастер | оператор (Артур) | Sheets → yt-dlp → LLM → анонсы в Docs/Telegram → **после всех анонсов выдаёт пакет для планера в Telegram** | `broadcaster` |
| 2 | Планер | владелец канала | пакет → сверка с YouTube → трансляции → ключи → файл ключей → Google-форма → отчёт | `planers` |
| 3 | Стример | оператор | берёт ключи из ответов формы → стримит | вне ТЗ |

Распространение пакета от оператора к владельцам — руками. Планер сам ничего не скачивает и в Telegram не ходит.

## 3. Термины

- **Слот** — один эфир: дата + время (по Киеву) + язык. В броадкастере это `slot_key = {ddmmyy}_{HHMM}_{lang}` (`app/planning/slots.py::planned_video_slot_key`, `app/pipeline/slot_processing.py::process_slot`). У слота одно название, одно описание и 1..N превью (по числу исходных видео, объединённых в этот эфир).
- **Пакет** — файл `*.bcast`: весь результат одного прогона броадкастера — все даты, все языки, все слоты (§5.1).
- **Канал** — YouTube-канал владельца: имя аккаунта для формы + список языков, за которые канал отвечает. У владельца может быть несколько каналов.
- **Сверка** — сравнение слотов из пакетов с эфирами, реально запланированными на канале. Истина — на платформе (§7.3).
- **Регистрация** — пара (слот, канал), для которой на платформе есть эфир, а у планера — ключ. Единица работы.
- **Журнал** — локальный машинный файл о том, что планер создал и что отправил в форму (§5.4). Не источник истины об эфирах — только память о ключах и отправках.
- **Файл ключей** — человеко-читаемое представление текущего состояния (§5.5). Производный, руками не правится.
- **Форма** — Google-форма ключей. URL уже есть в конфиге броадкастера (`AppConfig.google.form_url`) и уходит в Telegram через `build_telegram_key_form_reminder`.

## 4. Сквозной сценарий

1. Оператор запускает броадкастер. После публикации всех дат броадкастер собирает пакет и отправляет его документом в тот же Telegram-канал, куда ушли анонсы (`TelegramBotClient.send_document_as_file_bytes`).
2. Оператор пересылает пакет владельцу. Владелец сохраняет файл в `inbox\` папки планера.
3. Владелец запускает `planer.bat`. Планер:
   1. читает `config\planer.yaml`, проверяет токен каждого канала (при первом запуске — авторизация в браузере, §5.3);
   2. читает **все** пакеты в `inbox\`, раскладывает их слоты в единую карту по `slot_id`, выбрасывает прошедшие (§7.1);
   3. отбирает будущие слоты под языки своих каналов (§7.2);
   4. для каждого канала запрашивает у YouTube список запланированных эфиров и сверяет с картой слотов (§7.3): нет эфира → создать; есть, но название/описание отличаются → исправить; есть и совпадает → пропустить как копию;
   5. для каждого созданного эфира получает ключ (§7.4), пишет в журнал, перегенерирует файл ключей (§5.4, §5.5);
   6. читает форму, проверяет, что для всех её полей есть данные, отправляет новые ключи (§7.5);
   7. пишет отчёт в `reports\` и в консоль (§5.6).
4. Владелец смотрит отчёт. Если что-то не так с эфиром — правит или удаляет его на YouTube руками; следующий запуск планера это увидит и пересоздаст (§7.3).

## 5. Форматы данных

Все даты в файлах, именах и отчётах планера — `DD-MM-YYYY`, время — `HH:MM` по Киеву. Два исключения: `start` в манифесте (§5.1) и значения, уходящие в Google-форму, — там дата в `form.date_format` из пакета (сейчас `DD.MM.YYYY`, §7.5); когда отчёт цитирует вариант формы («в форме нет варианта на дату 13.09.2026»), дата приводится как в форме.

### 5.1. Пакет от броадкастера (`*.bcast`)

Контейнер — ZIP с расширением `.bcast` (утверждено). Один файл, внутри текст и картинки, читается `zipfile` из stdlib, «не-zip» расширение отбивает желание править в блокноте; оператор при желании открывает его любым архиватором.

Имя файла: `plan_{DD-MM-YYYY}_{DD-MM-YYYY}_gen{DD-MM-YYYY}-{HHMM}.bcast`
Пример: `plan_14-09-2026_25-09-2026_gen13-09-2026-1015.bcast` — дата первого и последнего слота в пакете, затем момент генерации. Имя — для людей и для быстрой сортировки глазами; **все решения планер принимает по манифесту**, имя файла не парсит (владелец может переименовать при сохранении).

Содержимое:

```
manifest.json
previews/
  16-09-2026_1900_uk_1.jpg
  16-09-2026_1900_uk_2.jpg      # в слоте два исходных видео → два превью одного эфира
  16-09-2026_2100_ru_1.jpg
  ...
```

`manifest.json` (UTF-8):

```json
{
  "schema_version": 1,
  "package_id": "20260913-101502-a1b2c3",
  "generated_at": "13-09-2026 10:15",
  "generator": { "project": "pipeline", "version": "1.4.0", "run_id": "…" },
  "timezone": "Europe/Kyiv",
  "period": { "from": "14-09-2026", "to": "25-09-2026" },
  "form": {
    "url": "https://forms.gle/UjVo2gftZdHsEdpZ7",
    "fields": {
      "language":      "Язык стрима ( Language of stream)",
      "account_name":  "Название канала ( Channel name)",
      "date":          "Время стрима ( Stream time )",
      "platform":      "Платформа (Platform)",
      "stream_key":    "You Tube Stream Key",
      "stream_url":    "Stream-URL (YT)",
      "time":          null,
      "broadcast_url": null,
      "slot_id":       null
    },
    "values": {
      "language": { "uk": "Украинский ( Ukranian)", "ru": "Русский ( Russian)", "en": "Английский ( English)", "hu": "Венгерский (Hungarian, Magyar)" },
      "platform": { "youtube": "You Tube", "facebook": "Facebook", "rumble": "Rumble" }
    },
    "date_format": "%d.%m.%Y"
  },
  "slots": [
    {
      "slot_id": "16-09-2026_1900_uk",
      "broadcaster_slot_key": "160926_1900_uk",
      "date": "16-09-2026",
      "time": "19:00",
      "start": "2026-09-16T19:00:00+03:00",
      "language": "uk",
      "title": "…",
      "description": "…",
      "previews": ["previews/16-09-2026_1900_uk_1.jpg", "previews/16-09-2026_1900_uk_2.jpg"],
      "sources": ["https://www.youtube.com/watch?v=…", "https://www.youtube.com/watch?v=…"]
    }
  ]
}
```

Правила:

- Пакет — весь прогон: все даты, все языки. «Период» — просто минимальная и максимальная дата слотов, никакого другого смысла у него нет.
- `slot_id` = `{DD-MM-YYYY}_{HHMM}_{lang}` — ключ, по которому планер ничего не путает: два эфира различаются хотя бы одним из трёх. Совпадает по смыслу с `slot_key` броадкастера (`160926_1900_uk`), но с однозначной датой.
- `date` — для людей, отчётов и формы (в форму — в `form.date_format`); `time` — для людей и отчётов, в форму не уходит: время эфира стример берёт из объявления. `start` — та же метка в ISO-8601 со смещением, **[РЕШЕНИЕ]** исключение из формата дат для сравнения моментов (второе исключение — значения для формы, §5): по ней планер сравнивает моменты с YouTube (там время в UTC) без базы часовых поясов на машине владельца. Человек её не читает.
- `title`/`description` — ровно те тексты, что ушли в анонс Telegram (`app/publish/telegram_batch_sender.py`), через `resolve_slot_publish_texts` (`app/publish/slot_publish_texts.py`): `SanitizedPublishBlock.title_text` / `description_text`, если блок есть и `is_blocked == False`; иначе для нескольких видео — merge-payload живой санитации, а при её блокировке или отсутствии merge — nomerge-композиция (`numbered_original_titles` + `build_descriptions_summary`); для одного видео — `metadata.title` + `fallback_source_description_text`. В пакет попадает каждая пара (слот, язык), по которой был анонс.
- `previews` — 1..N файлов, все принадлежат этому одному эфиру (по одному на исходное видео). Планер берёт **одно случайное** как обложку трансляции (утверждено: владельцу, как правило, всё равно).
- `form.url` — ссылка из конфига броадкастера как есть (сейчас короткая forms.gle); планер идёт по редиректу и строит адрес formResponse от конечного URL.
- `form.fields` — названия вопросов формы символ в символ; `null` — такого вопроса в форме нет: поле не отправляется и в отчёт не попадает.
- `form.values` — тексты вариантов радио-вопросов по кодам пайплайна (язык, платформа).
- `form.date_format` — strftime-формат даты, с которой начинается вариант вопроса «Время стрима».
- entry-ID по-прежнему не конфигурируются — планер читает их из HTML формы (§7.5).
- `schema_version` — планер отказывается читать пакет с неизвестной мажорной версией и пишет об этом в отчёт.
- `generator` — информационное поле: `project` = значение переменной окружения `LOGGER_NAME` броадкастера (в песочнице restreamer — `pipeline`), `version` — константа экспортера. Планер по этим полям ничего не решает.
- Броадкастер уже отфильтровал прошлое по `now_for_filter` (`app/planning/sheet_loader.py`), но планер фильтрует снова — между генерацией и запуском могут пройти дни.

### 5.2. Конфиг планера `config\planer.yaml`

Единственный файл, который владелец редактирует руками. Шаблон `config\planer.example.yaml` в репо; при первом запуске планер копирует его в `planer.yaml`, если файла нет (как описано в `README.config.txt` броадкастера).

```yaml
owner: "Иван"                      # как подписывать отчёты
min_lead_minutes: 60               # слоты, до старта которых меньше — не планировать
inbox_keep_days: 14                # сколько дней держать отработанные пакеты в inbox\done

channels:
  - id: yt_ua                      # короткий ключ, латиница; имя файла токена
    platform: youtube
    account_name: "Іван UA"        # ровно так, как должно попасть в форму
    languages: [uk]
    privacy: public                # public | unlisted
    auto_start: true               # эфир стартует сам, когда стример начнёт слать поток
    set_thumbnail: true            # ставить превью из пакета (нужен подтверждённый канал)

  - id: yt_ru
    platform: youtube
    account_name: "Иван RU"
    languages: [ru, en]
```

Чего здесь нет и не будет: логинов, паролей, URL формы, entry-ID, путей к токенам (они выводятся из `id`).

### 5.3. Секреты `secrets\` — как устроена авторизация

В папке два вида файлов, и они принципиально разные.

**`client_secret.json` — «паспорт программы».** Чтобы любая программа могла обращаться к YouTube API, у Google должна быть зарегистрирована сама *программа* (в Google Cloud, в проекте оператора). Результат регистрации — этот файл. Он один на всех владельцев, лежит в дистрибутиве рядом с exe, владелец его не создаёт и не трогает. Для программ типа Desktop Google не считает его секретом (его нельзя не отдать вместе с exe), поэтому ничего страшного в распространении нет.

**`<channel_id>.token.json` — «пропуск канала».** Появляется на машине владельца сам, при первом запуске. Ровно так, как ты описал:

1. Планер видит в `planer.yaml` канал `yt_ua`, ищет `secrets\yt_ua.token.json` — нет.
2. Открывает браузер на странице Google: «Планер просит доступ к управлению вашими трансляциями YouTube». Владелец выбирает нужный Google-аккаунт и, если у аккаунта несколько каналов, — нужный канал. Нажимает «Разрешить».
3. Google возвращает планеру токен, планер сохраняет его как `secrets\yt_ua.token.json`. Единственное право в токене — `https://www.googleapis.com/auth/youtube` (управление своим каналом); к почте, диску и прочему доступа нет.
4. Для канала `yt_ru` — то же самое, файл `secrets\yt_ru.token.json`. Токены лежат рядом и никак не пересекаются: имя файла = `id` канала из конфига.
5. Дальше браузер не нужен: токен обновляется сам. Если Google его отозвал (владелец сменил пароль, удалил доступ) — планер снова откроет браузер для этого канала.

Защита от ошибки «выбрал не тот аккаунт»: сразу после авторизации планер спрашивает у YouTube, какой это канал (`channels.list(mine=true)`), показывает название и записывает `channel_id` YouTube в `state\channels.json`. Если при следующем запуске токен вдруг ведёт на другой канал — планер останавливается и говорит об этом. Переавторизовать канал принудительно: `planer.exe --auth yt_ua` (удаляет токен и открывает браузер).

Механика та же, что уже работает в броадкастере (`app/google/auth.py::_create_oauth_credentials`: `InstalledAppFlow.run_local_server`), только скоуп другой и токен — на канал, а не один на приложение.

Что должен сделать оператор один раз, чтобы это работало у всех, — §6.1. Вся папка `secrets\` в `.gitignore` (уже есть: `client_secret*.json`, `token*.json`).

### 5.4. Журнал `state\registry.json`

Машинный файл. Помнит то, чего нет на платформе: какой ключ у какого эфира планер получил и отправлена ли форма. Запись атомарная (temp-файл → `os.replace`). Ключ записи — `"{slot_id}|{channel_id}"`.

```json
{
  "schema_version": 1,
  "registrations": {
    "16-09-2026_1900_uk|yt_ua": {
      "slot_id": "16-09-2026_1900_uk",
      "channel_id": "yt_ua",
      "account_name": "Іван UA",
      "language": "uk",
      "date": "16-09-2026",
      "time": "19:00",
      "broadcast_id": "abc123",
      "broadcast_url": "https://www.youtube.com/watch?v=abc123",
      "stream_url": "rtmp://a.rtmp.youtube.com/live2",
      "stream_key": "xxxx-xxxx-xxxx-xxxx-xxxx",
      "package_id": "20260913-101502-a1b2c3",
      "created_at": "13-09-2026 12:00",
      "form_status": "sent",
      "form_sent_at": "13-09-2026 12:00",
      "previous_broadcast_ids": [],
      "last_error": null
    }
  },
  "packages": {
    "20260913-101502-a1b2c3": { "file": "plan_14-09-2026_25-09-2026_gen13-09-2026-1015.bcast", "first_seen": "13-09-2026 12:00" }
  }
}
```

`form_status`: `pending` (ключ есть, форма не подтверждена — повторить) → `sent` (подтверждено). Если эфир пересоздан (§7.3), старый `broadcast_id` уходит в `previous_broadcast_ids`, `form_status` снова `pending`.

Журнал — не источник истины об эфирах. Если журнал говорит «создано», а на YouTube эфира нет (владелец удалил) — прав YouTube, планер создаёт заново.

### 5.5. Файл ключей `out\keys.txt`

Полностью перегенерируется при каждом запуске из результата сверки (§7.3) + журнала: все будущие эфиры каналов владельца, сопоставленные слотам, с ключами и статусом формы. Ключ эфира, созданного не планером, тоже виден — он читается с платформы (`liveStreams.list(part=cdn)`). Текст, одна строка на эфир, поля через ` | `, сортировка по дате, времени, языку:

```
# Ключи трансляций. Сгенерировано планером 13-09-2026 12:00. Файл производный — не править.
# язык | дата | время (Киев) | аккаунт | статус формы | stream_url | stream_key | ссылка на эфир
```

## 7. Алгоритм

### 7.1. Сбор слотов из `inbox\`

1. Берутся все `*.bcast` в корне `inbox\` (`done\`, `archive\` не сканируются). Битый архив/манифест → отчёт «пакет повреждён», файл не трогается.
2. Пакеты читаются **все**, в порядке `generated_at` от старого к новому, и их слоты складываются в одну карту `slot_id → слот`. Один и тот же `slot_id` в двух пакетах → остаётся версия из более нового пакета (у него свежее название/описание). Так планер ничего не путает: что бы ни лежало в `inbox\`, на выходе — один список уникальных (дата, время, язык).
3. Из карты выбрасываются слоты с `start <= сейчас` — прошедшее не планируется никогда, из какого бы пакета оно ни пришло.
4. Пакет, у которого **все** слоты в прошлом, переносится в `inbox\archive\`. Пакет, все слоты которого под языки владельца в терминальном состоянии после этого запуска (эфир есть на платформе и форма подтверждена, либо пропущены как прошедшие/без канала), — в `inbox\done\`. Остальные остаются в `inbox\` для повтора. Через `inbox_keep_days` дней `done\` и `archive\` чистятся.

Про «пакет 14–25.09, запустили 16.09»: читается, слоты 14–15.09 в отчёт как прошедшие, 16–25.09 идут на сверку. Дублей не будет не потому, что планер помнит, что делал, а потому что перед созданием он спрашивает YouTube, есть ли уже такой эфир (§7.3).

### 7.2. Отбор слотов под каналы

Для каждого слота из карты:

- `start - сейчас < min_lead_minutes` → «слишком поздно», пропуск с предупреждением (стримеру нужно время увидеть ключ в форме);
- язык слота не входит ни в один `channels[].languages` → «нет канала для языка», пропуск (нормально: у владельца может не быть канала под каждый язык);
- иначе для **каждого** канала, у которого язык в списке, образуется пара (слот, канал). Два канала на один язык → два эфира.

### 7.3. Сверка с платформой

Истина об эфирах — на YouTube. Журнал планера — только память о ключах и форме. Поэтому перед любым созданием:

1. Для каждого канала запрашивается список запланированных эфиров: `liveBroadcasts.list(mine=true, broadcastStatus=upcoming, part=snippet,contentDetails,status)`, с пагинацией. Для каждого — `snippet.scheduledStartTime` (UTC), `snippet.title`, `snippet.description`, `contentDetails.boundStreamId`.
2. Слот считается **совпавшим** с эфиром, если совпадает момент старта с точностью до минуты (`slot.start` и `scheduledStartTime` сравниваются в UTC). Если на канале в одну минуту несколько эфиров (канал обслуживает `[ru, en]`, оба слота на 19:00) — различает **маркер**: планер всегда пишет `slot_id` в название привязанного потока (`liveStreams.snippet.title`, зрителям не видно) и читает его через `liveStreams.list(id=boundStreamId)`. Эфир без маркера (создан руками) при единственном кандидате на эту минуту считается совпавшим, при нескольких — в отчёт «не могу различить, разберитесь вручную», слот не трогается.
3. По результату сверки для каждой пары (слот, канал):

| На YouTube | Действие |
|---|---|
| эфира нет | **создать** (§7.4), ключ в журнал, форма |
| эфир есть, название и описание совпадают | **копия — пропустить**; в отчёт «уже запланировано» |
| эфир есть, название или описание отличаются | **исправить** (см. ниже); в отчёт «исправлено» |
| журнал говорит «создано», на YouTube эфира нет | владелец удалил — **создать заново**, старый `broadcast_id` в `previous_broadcast_ids`, форма отправляется повторно с новым ключом |
| на YouTube эфир на время, которого нет ни в одном слоте | не трогать; в отчёт **не** попадает (это чужой/ручной эфир) |

Сравнение текстов: название — точное после `strip()`; описание — после нормализации переводов строк и пробелов **[ПРОВЕРИТЬ]** как YouTube хранит описание (не режет ли пробелы/пустые строки), чтобы совпадающие тексты не считались разными при каждом запуске.

**Как исправлять — [РЕШЕНИЕ].** Ты предложил отменить старый эфир и запланировать новый. Предлагаю по умолчанию делать иначе — обновлять на месте (`liveBroadcasts.update`, `part=snippet`: название, описание, превью). Результат для зрителя тот же (изменённый эфир), но ключ и ссылка не меняются, значит форму переотправлять не надо, и вопрос «что сделает стример с повторным ключом» просто не возникает. Отмена + пересоздание остаётся запасным путём, если для какого-то поля `update` окажется невозможен **[ПРОВЕРИТЬ]**. Если ты настаиваешь на пересоздании — это одна строчка в конфиге канала (`replace_mode: recreate`), но тогда стример обязан брать последний ответ по `slot_id`.

Перенос времени в Sheets даёт другой `slot_id` → на старое время эфира в слотах нет → по таблице выше он не трогается и в отчёт не попадает. **[РЕШЕНИЕ]** Дополнительно выводить в отчёт эфиры с маркером планера, время которых пропало из слотов, как «перенесён или отменён? эфир не удалён» — чтобы владелец мог убрать их руками. Без маркера (ручные эфиры) — не выводить.

### 7.4. Создание эфира (YouTube)

`platforms/youtube.py`, YouTube Data API v3 через `googleapiclient`, повторы через `app/google/api_retry.py`:

1. `liveBroadcasts.insert` — `snippet.title` (≤100 символов, безопасная обрезка по образцу `app/core/safe_trim.py`), `snippet.description` (≤5000), `snippet.scheduledStartTime` = `slot.start` в RFC3339, `status.privacyStatus` = `channel.privacy`, `status.selfDeclaredMadeForKids = false`, `contentDetails.enableAutoStart = channel.auto_start`, `contentDetails.enableAutoStop = true`, `contentDetails.latencyPreference = "normal"`.
2. `liveStreams.insert` — `snippet.title = slot_id` (маркер, §7.3), `cdn.ingestionType = "rtmp"`, `cdn.resolution = "variable"`, `cdn.frameRate = "variable"`. Из ответа: `cdn.ingestionInfo.streamName` (ключ), `cdn.ingestionInfo.ingestionAddress` (stream_url). Ключ проверяется регулярным выражением `^[a-z0-9]{4}(-[a-z0-9]{4}){3,4}$` (5 групп `xxxx-xxxx-xxxx-xxxx-xxxx` — текущий формат, 4 группы — старые ключи); константа `YOUTUBE_STREAM_KEY_PATTERN` в `platforms/youtube.py` — единственный источник. Несовпадение — ошибка пары (слот, канал): в журнал не пишется, форма не отправляется, в отчёт «ключ неожиданного формата». Та же проверка — при чтении ключей чужих эфиров для `keys.txt` (§5.5): не прошедший ключ выводится с пометкой «формат?».
3. `liveBroadcasts.bind` — привязка потока к эфиру.
4. `thumbnails.set` — если `channel.set_thumbnail` и у слота есть превью: берётся `random.choice(slot.previews)`. Ошибка **не фатальна** (требует подтверждённого канала) — в отчёт предупреждением.
5. `broadcast_url = https://www.youtube.com/watch?v={broadcast_id}`.

На каждый эфир — свой `liveStream` (свой ключ), а не общий ключ канала: при `enableAutoStart` и нескольких эфирах на одном ключе неоднозначно, какой стартует. `enableAutoStart = true` по умолчанию: стримеру достаточно начать слать поток.

Если шаги 1–3 упали посередине — созданные объекты записываются в `last_error`, следующий запуск при сверке увидит незавершённый эфир без маркера или без потока и доделает/пересоздаст; уборка «сирот» — по отчёту вручную (v1).

**Facebook** — этап 2, после закрытия **[ПРОВЕРИТЬ]**: `POST /{page_id}/live_videos` (`status=SCHEDULED_UNPUBLISHED`, `planned_start_time`, `title`, `description` → `id`, `secure_stream_url`), Page-токен с `publish_video`, `pages_manage_posts`, `pages_read_engagement`; проверить окно старта относительно `planned_start_time`, срок жизни ключа, нужен ли app review или хватает роли tester в приложении оператора. Сверка — по тому же принципу (`GET /{page_id}/live_videos?status=SCHEDULED_UNPUBLISHED`).

### 7.5. Отправка в форму

Порядок — ровно как ты описал: сначала форма, потом проверка, потом отправка.

1. **URL формы** — из пакета (`form.url`). Раз в запуск планер делает `GET viewform`.
2. **Какие поля есть** — из HTML формы: Google кладёт структуру вопросов в скрипт `FB_PUBLIC_LOAD_DATA_` на странице; из него для каждого вопроса берутся название, `entry.NNN`, обязательность, тип (текст / радио), тексты вариантов и номер раздела, плюс переходы «вариант вопроса «Платформа» → раздел» **[ПРОВЕРИТЬ]** на сохранённом HTML тренировочной формы. Это и есть причина, по которой entry-ID нигде не конфигурируются: форма сама говорит, что у неё есть. Если структуру прочитать не удалось — форма не отправляется вообще, в отчёт «не смог прочитать форму», ключи при этом уже в `keys.txt`.
3. **Сопоставление и значения** — название вопроса ↔ поле данных через `form.fields` из пакета (§5.1); поля с `null` не отправляются и в отчёт не попадают. Значение — по типу вопроса:
   - текстовый — как есть: `account_name`, `stream_key`;
   - радио — только текст одного из вариантов этого вопроса:
     - `language` → `form.values.language[<язык слота>]`;
     - `platform` → `form.values.platform["youtube"]`;
     - `date` → вариант, текст которого начинается с даты слота в формате `form.date_format`;
     - `stream_url` → вариант, равный `ingestionAddress` из API после нормализации обеих строк (нижний регистр, без хвостового слэша).

   Правило: планер **никогда** не отправляет значение, которого нет среди вариантов вопроса. Нет варианта (например, даты слота нет в «Время стрима») — ошибка пары (слот, канал): в отчёт «в форме нет варианта на дату DD.MM.YYYY, попросите владельца формы добавить», `form_status` остаётся `pending`, повтор в следующий запуск.

   Перед отправкой: у каждого обязательного вопроса пройденных разделов (раздел 1 и раздел YouTube) есть значение, `stream_key` прошёл проверку §7.4. Вопросы непройденных разделов (Facebook / Rumble / другое) игнорируются.
4. **Отправка** — `POST formResponse` конечного URL формы (после редиректа forms.gle) с `entry.*` вопросов пройденных разделов. Форма многостраничная: в POST передаётся `pageHistory` с индексами пройденных разделов (раздел 1 и раздел YouTube) — точные значения параметра **[ПРОВЕРИТЬ]** отправкой в тренировочную форму: строка в таблице ответов должна совпасть с образцом ниже. `requests`, таймаут 30 с, 3 попытки с нарастающей паузой на сетевые ошибки и 5xx.
5. **Подтверждение** — HTTP 200 и маркер страницы «ответ записан» в теле (`freebirdFormviewerViewResponseConfirmationMessage` / «Ваш ответ записан» / «Your response has been recorded») **[ПРОВЕРИТЬ]**: Google отвечает 200 и на ошибки. Без маркера — `form_status = pending`, повтор в следующий запуск.

**Как выглядит ответ планера в таблице** — критерий приёмки этапа 4. Строка, которую планер оставляет в таблице ответов тренировочной формы, совпадает по виду с тестовым ответом, заполненным вручную 11-09-2026:

```
11.09.2026 12:17:04 | Украинский ( Ukranian) | NameMyChannel | 13.09.2026 Дата стрима (время стрима указано в объявлении) | You Tube | <ключ> | rtmp://A.rtmp.youtube.com/live2/ | далее 7 пустых колонок
```

Колонки: отметка времени (ставит Google), язык, название канала, время стрима, платформа, ключ, Stream-URL; 7 колонок разделов Facebook / Rumble / другое — пустые.

Когда отправлять: после создания эфира (новый ключ) и после пересоздания (новый ключ); после исправления на месте — нет (ключ прежний). Повторная отправка того же ключа — только если предыдущая не подтверждена.

Как стример поведёт себя с повторным ключом по тому же слоту — вне ТЗ (решено: проблема стримера). `slot_id` в форму не уходит (§6.1 п.2): различать ответы стример может только по дате, языку и названию канала, последний ответ по этой тройке — актуальный.

### 7.6. Режимы запуска

`planer.exe` через `planer.bat` (окно не закрывается до Enter):

- без аргументов — полный цикл §4;
- `--dry-run` — читает пакеты и **сверяется с YouTube** (только чтение), но ничего не создаёт, не исправляет и в форму не шлёт; в отчёте — что было бы сделано; журнал не меняется;
- `--check` — только авторизация и проверка прав каждого канала;
- `--auth <channel_id>` — принудительная переавторизация канала;
- `--status` — сверка + перегенерация `keys.txt` и отчёта без пакетов из `inbox\` (что сейчас запланировано и с какими ключами);
- `--debug` — подробный лог.

Первый запуск без `config\planer.yaml` → копирует пример, завершается с кодом 2 и подсказкой.

## 12. Решения, которые нужны от Артура до этапа 1

1. `start` в манифесте остаётся ISO-8601 со смещением — исключение из `DD-MM-YYYY` для сравнения моментов; второе — значения для формы (§5) (§5.1).
2. Закрыто 11-09-2026: форма не меняется, новых вопросов не будет; time, broadcast_url, slot_id в форму не уходят (§6.1 п.2, §7.5).
3. Исправление изменившегося эфира — обновление на месте, а не отмена + пересоздание (§7.3).
4. Эфиры с маркером планера, чьё время пропало из слотов, — показывать в отчёте, не удалять (§7.3).
5. В режиме `audit` броадкастера пакет строится из ветки `merge` (§8).
6. В `form.fields` добавлен ключ `platform` — в боевой форме есть обязательный вопрос «Платформа».
7. Тексты слота в пакете = тексты анонса; в пакет попадает каждая пара (слот, язык), по которой был анонс (§5.1).

Утверждено в 0.1 и не обсуждается повторно: `.bcast` = ZIP; случайное превью; по эфиру на каждый канал языка, свой поток на каждый эфир, `enableAutoStart`; `min_lead_minutes = 60`; файл ключей `.txt`.
